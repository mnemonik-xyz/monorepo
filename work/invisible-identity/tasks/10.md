# Task 10: Golden JSON byte-equality test (Rust + Node)

## Description

A focused unit-level companion to Task 9's integration test. Asserts that the JSON serialization of `KeystoreEntry` produces byte-identical output on both languages for a fixed fixture. If Task 9 catches drift in production, this test catches it at unit-test speed.

Cheap to run, very high signal — must be PR-gating in both languages' test suites.

## What to do

1. **Define the fixture** — a deterministic `KeystoreEntry`:

   ```
   secret = [0x42; 64]
   pubkey_base58 = "<derived from secret via ed25519 keypair-from-seed>"
   ```

   The pubkey is computed once and hardcoded as a constant in both tests.

2. **Compute the expected JSON bytes** — exactly:

   ```
   {"secret":[66,66,66,...,66],"pubkey_base58":"<computed>"}
   ```

   No whitespace, no escapes beyond JSON-required, `secret` key first. Compute this expected string once and hardcode it in both tests.

3. **Rust test** at `core/src/identity/keystore.rs` (or a `tests/golden.rs`):

   ```rust
   #[test]
   fn keystore_json_byte_equal_golden() {
       const SECRET: [u8; 64] = [0x42; 64];
       const PUBKEY: &str = "<computed-once>";
       const EXPECTED: &str = r#"{"secret":[66,66,...],"pubkey_base58":"<...>"}"#;

       let entry = KeystoreEntry { secret: SECRET, pubkey_base58: PUBKEY.to_string() };
       let actual = crate::identity::keystore::serialize_canonical(&entry).unwrap();
       assert_eq!(actual, EXPECTED);
   }
   ```

4. **Node test** at `packages/cli/test/identity/keystore-golden.test.ts`:

   ```ts
   import { describe, it, expect } from 'vitest';
   import { serializeCanonical } from '../../src/identity/keystore';

   describe('keystore JSON byte-equality golden', () => {
     it('produces exact expected bytes', () => {
       const SECRET = Array.from({ length: 64 }, () => 0x42);
       const PUBKEY = '<computed-once>';
       const EXPECTED = '{"secret":[66,66,...],"pubkey_base58":"<...>"}';
       const actual = serializeCanonical({ secret: SECRET, pubkey_base58: PUBKEY });
       expect(actual).toBe(EXPECTED);
     });
   });
   ```

5. **Expose `serialize_canonical` / `serializeCanonical`** as named exports in both languages. They were probably inline helpers in Task 2 / Task 6 — promote to a named function.

6. **Generate the `<computed>` pubkey + `EXPECTED` string** via a one-off script (commit but don't ship in the package). Run it locally; hardcode the output into both test files. If the seed changes later, run the script again to regenerate.

## Notes

- Generating the fixture pubkey: use `ed25519_dalek::SigningKey::from_bytes(&[0x42; 32])` (note: signing key seed is 32 bytes; the "secret" field in our type is the 64-byte expanded form). The expanded 64 bytes are `seed || pubkey`. Document the convention used.
- Wait — clarify: is our `secret: [u8; 64]` the Ed25519 expanded key, or the 32-byte seed padded? Check existing code in `core/src/identity/mod.rs`. Use whatever the current convention is; do not change it in this task.
- The hardcoded `EXPECTED` string is ~700 chars. Use a raw string in Rust (`r#"..."#`) and a regular string in JS. Both languages must produce identical content.
- If the test fails due to a JSON-numeric-format difference (e.g., Rust outputs `66` and Node outputs `66.0` or vice versa), this is exactly the kind of drift the test is meant to catch — fix one side to match the other.
