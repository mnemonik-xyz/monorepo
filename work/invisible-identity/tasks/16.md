# Task 16: Security review of key handling

## Description

Read-only security audit covering the full diff introduced by Tasks 1-14. The reviewer agent does not write code; findings are appended to `decisions.md` and routed to fix-tasks if needed.

Scope: key material lifetime in memory, secret bytes in any log/error/stack trace, file permissions, ticket protocol correctness (replay, MITM, sealed-box misuse), JWT-deeplink exposure surface, supply-chain (new deps).

## What to do

The agent performs the following checks, each producing a finding line in the report:

### Key material handling

1. **Grep for any code path that prints raw secret bytes:**
   ```
   grep -rE "println!|eprintln!|tracing::|console\\.(log|error|info|debug|warn)" core/src/identity packages/cli/src/identity packages/cli/src/commands mcp/src/api.rs mcp/src/main.rs | grep -i secret
   ```
   Expected: empty. Any match is a finding.

2. **Inspect error formatters:**
   - `KeystoreError::Other(anyhow::Error)` — does the inner anyhow chain ever include a secret? Audit `OsKeyStore::get` and `FileKeyStore::get` error paths.
   - `IdentityRequiresKeystore` — confirm message only carries pubkey + keychain_ref, never secret bytes.

3. **Memory lifetime:**
   - `Identity` struct in Rust — does it hold `[u8; 64]` directly? If yes, is it zeroized on drop? Add `zeroize::Zeroize` if not present.
   - Node side — `KeystoreEntry.secret: number[]` — Node doesn't zeroize automatically, but minimize the lifetime by not stashing in module-level state.

4. **`Identity` clone semantics:**
   - If `Identity` derives `Clone`, every clone duplicates the secret in memory. Verify the codebase clones only when necessary (probably never — `Arc<Identity>` is the right pattern). Document any clone-heavy paths.

### File permissions

5. **Mode 0600 verification:**
   - `tests/fixtures/` should contain a test that asserts `stat ~/.mnemonic/identity.json` returns mode 0600 after `ensure()`.
   - On Windows, the ACL helper (if used by `work/mnemonic-cli/`) should be exercised — if it's a stub no-op, flag this.

6. **README.txt mode:**
   - Less critical (no secrets) but should be 0644.

### Ticket protocol

7. **Replay protection:**
   - `BootstrapTickets::redeemed` flag set BEFORE returning the unwrapped secret on `/redeem`.
   - Verify atomicity: no race window where two redemptions could both succeed.

8. **TTL enforcement:**
   - `expires_at` check happens BEFORE unwrap. Reject expired tickets without revealing whether the short_code was ever valid (timing-safe comparison).

9. **Sealed-box correctness:**
   - Rust `crypto_box::Box` and Node `@noble/curves` x25519 + `@noble/ciphers` xsalsa20poly1305 — do they use compatible nonce/MAC layouts? Confirm via the integration test (Task 13).
   - Server's static x25519 keypair — never persisted, regenerated on each boot. Confirm.

10. **Short code entropy:**
    - 8 chars from 32-char alphabet = 40 bits. 5-min TTL + single-use → attacker needs ~10^12 / 300s = 3 billion guesses/sec to brute-force, which is unrealistic. Document the choice.

11. **No secret in argv:**
    - `mnemonic identity pull-from-webapp <short_code>` — argv-positional is OK (the short_code, not the secret). The secret comes from server response.
    - Confirm there's no path where the raw secret is passed via argv.

### JWT-deeplink exposure

12. **JWT in URL query string:**
    - `/install` page uses POST + native deeplink, NOT a GET with JWT in URL.
    - Confirm `cursor://mcp/install?config=<base64>` has the JWT inside the base64-encoded config, not in a separate query param. Server-side logs that record URLs do NOT see the JWT in plaintext (only base64).

13. **Webapp localStorage XSS:**
    - JWT in localStorage is the existing risk surface. New code does not expand it.
    - Verify `?pull=<short_code>` handler does not enable script injection (treat short_code as opaque, no `dangerouslySetInnerHTML`).

### Supply-chain (new deps)

14. **`@napi-rs/keyring`, `qrcode-terminal`, `@noble/curves`, `keyring`, `crypto_box`:**
    - Run `npm audit` for Node packages.
    - Run `cargo audit` for Rust crates.
    - Check that none of the new deps have post-install hooks doing network calls or filesystem writes beyond their declared scope.

```
Title: <short>

Description: <what>
Recommendation: <how to fix>
```
