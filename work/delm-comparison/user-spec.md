# User Spec: Интеграция DeLM × Mnemonic (DeLM-on-Mnemonic)

## Что

Сделать так, чтобы общий контекст DeLM (shared context `C` — «доска» проверенных
gist-записей) сохранялся, подписывался и (опционально) якорился через Mnemonic, вместо
того чтобы жить только в оперативной памяти одного запуска.

Адаптер (Python-модуль в репозитории `delm`) реализует тот же интерфейс, что и
`SharedLessons` (`read()` / `admit()`), но пишет и читает записи через MCP-инструменты
Mnemonic (`mnemonic_sign_memory` / `mnemonic_recall`). Иерархия DeLM
**raw → summary → gist** раскладывается в связанные через lineage-граф артефакты:

- сырой trajectory/источник → артефакт `rag.context` (хранится целиком, без потерь);
- (опционально) reference-grounded summary → `rag.context` (родитель gist-а);
- компактный gist → `rag.result` (то, что видно всем агентам).

«Разворачивание» (unfold) детали — это обход lineage к **подписанному сырому артефакту**,
а не обратное преобразование компактора.

## Зачем

1. **DeLM не конкурент, а слой выше.** DeLM — это алгоритм координации мульти-агентов
   (test-time scaling), без блокчейна и без криптографии. Mnemonic — криптографический
   слой памяти. Они дополняют друг друга по двум разным смыслам слова «проверено»:
   DeLM проверяет *достоверность содержания*, Mnemonic — *криптографическую подлинность*.
2. **Закрываем то, что DeLM теряет:** его `C` живёт в RAM одного запуска, провенанс —
   просто строка `thread_id`, между сессиями ничего не переносится. Mnemonic даёт
   долговременное хранение, авторство (Ed25519), и проверяемость третьей стороной.
3. **Это прямо описано в самой статье** как будущая работа: «автоматизированные
   исследования», где агенты не должны повторно читать те же статьи и переоткрывать те
   же неудачи между запусками — то есть **межзапусковый** общий контекст. Это ровно
   Mnemonic, а не DeLM.
4. **Стратегически честно:** для «черновика внутри одного запуска» дешевле работает
   in-RAM доска DeLM, и навязывать туда криптографию не нужно. Ценность Mnemonic
   проявляется, когда находки должны пережить запуск, переехать в другой runtime или
   быть доказаны внешнему наблюдателю.

## Про компактор памяти DeLM (важно)

Компактор `memory_compactor.py` — это **детерминированное, одностороннее извлечение с
потерями** (regex по сигналам Python/pytest), а не обратимое сжатие. Восстановить
исходную траекторию из его вывода нельзя; обратной функции в репозитории нет.

- **Сохранность «логики» при восстановлении** обеспечивается не компактором, а
  **удержанием сырого артефакта** в lineage и разворачиванием к нему.
- **Заменить TurboQuant им нельзя:** TurboQuant сжимает вектор-эмбеддинг (ключ для
  recall), компактор сжимает текст-payload. Это разные оси, они дополняют, а не заменяют.
- **Отказаться от SQL за счёт него нельзя:** SQL — это индекс векторов и таблицы lineage,
  без которых нет семантического recall и обхода графа. Компактор отдаёт строку, он не
  хранилище.

Поэтому компактор берём как **детерминированный генератор gist-а** (за плагин-интерфейсом
экстракторов), а безпотерьность даёт lineage. Подробности — `decisions.md` D1.

## Критерии приёмки

1. DeLM может запуститься с бэкендом Mnemonic: каждый admit подписывается и доступен через
   recall; каждый gist связан lineage-ссылкой со своим сырым артефактом.
2. Unfold возвращает подписанный сырой контент через обход lineage (а не через инверсию
   компактора).
3. Один и тот же общий контекст переживает перезапуск процесса и читается во второй сессии
   (демонстрация межзапускового переиспользования — ключевое отличие от DeLM).
4. Никаких изменений в `core/`/`mcp/` для v1 (адаптер — клиентский Python поверх MCP).
5. Компактор работает детерминированно и за плагин-интерфейсом; при отсутствии сигналов
   payload сохраняется как сырой `rag.context` (фолбэк без потерь).
