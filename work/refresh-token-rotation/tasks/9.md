# Task 9: Pre-deploy QA

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:pre-deploy-qa` — [skills/pre-deploy-qa/SKILL.md](~/.claude/skills/pre-deploy-qa/SKILL.md)

## Description

Финальная приёмочная проверка фичи refresh-token-rotation на чистом локальном
чекауте перед dev-деплоем (Task 10) и prod-деплоем (Task 11). Цель — убедиться,
что после слияния всех изменений Wave 1–4 (Tasks 1–5) и аудитов Wave 5
(Tasks 6–8) сборка зелёная, все статические и динамические гейты проходят, а
все технические критерии приёмки из `tech-spec.md::Acceptance Criteria` и
пользовательские критерии из `user-spec.md::AC1–AC13` выполняются локально.
Это последний gate, который держит фичу до того, как код увидит реальное
окружение и реальных клиентов (Claude.ai + Cursor).

Задача non-code: ничего не пишем в `core/` или `mcp/`. Только запускаем,
наблюдаем, сводим результаты в отчёт.

## What to do

1. Чистый локальный чекаут на ветке фичи (`git status` чист, нет undeleted
   артефактов от предыдущих волн).
2. Прогнать четыре статических/динамических гейта последовательно и собрать
   их полный stdout/stderr (фрагменты, достаточные для восстановления
   контекста, в отчёт):
   - `cargo test --workspace --no-fail-fast` — все тесты воркспейса GREEN,
     включая `mcp/tests/oauth_refresh_e2e.rs` (15 интеграционных), unit-тесты
     `refresh::tests::*`, `oauth::tests::*`, и существующий `oauth/mod.rs`
     suite (auth_allowlist, anonymous_recall, oauth/mod.rs:2022-2099 area).
   - `cargo clippy --workspace --all-targets -- -D warnings` — без warning'ов.
   - `cargo fmt --all -- --check` — без расхождений.
   - `gitleaks detect --no-banner` — рабочее дерево + полная история.
3. Поднять локальный MCP-сервер с валидным `MCP_REFRESH_SALT` (например
   `openssl rand -base64 32`) и без `MCP_JWT_TTL_SECS` (default 3600); сделать
   `curl http://localhost:3000/.well-known/oauth-authorization-server` и
   убедиться, что `grant_types_supported` содержит и `"authorization_code"`,
   и `"refresh_token"` (tech-spec AC: discovery metadata).
4. Пройтись по каждому пункту секции `tech-spec.md::Acceptance Criteria`
   (после "Технические критерии приёмки") и сопоставить с фактическим
   состоянием в коде / прогоне тестов. Для каждого пункта в отчёте отметить
   PASS / FAIL / N/A с конкретной ссылкой на тест или фрагмент кода:
   - все 4 гейта (test/clippy/fmt/gitleaks) — из пунктов выше;
   - покрытие AC1–AC13 интеграционными тестами в `oauth_refresh_e2e.rs`;
   - discovery содержит `"refresh_token"` (AC7);
   - tracing-логи на refresh-rotation путях содержат `refresh_rotation`
     (INFO) и `family_revoke` (WARN), и НЕ содержат plaintext или
     `token_hash` (D14 — проверяется через
     `oauth::tests::logging_policy_no_plaintext_no_hash_across_branches`);
   - все `/oauth/token` ответы (success и error) выставляют
     `Cache-Control: no-store` + `Pragma: no-cache` (D15 — проверяется
     через `oauth::tests::token_response_emits_no_store_cache_headers`);
   - boot abort на пустом или коротком `MCP_REFRESH_SALT` после
     base64url-decode (D2 — проверяется через `salt_*_aborts_boot` тесты);
   - cap на длину `refresh_token` 4 KiB до хеширования (D16 — проверяется
     через `refresh_token_too_long_returns_invalid_request`);
   - `tower_governor` rate-limit активен на `/oauth/*` без новой обвязки
     (наследуется);
   - V1 limitation `client_id` НЕ валидируется на refresh-grant — задокумен­
     тировано;
   - регрессии отсутствуют в `mcp/src/oauth/mod.rs:2022-2099`,
     `mcp/tests/auth_allowlist.rs`, `mcp/tests/anonymous_recall.rs`.
5. Пройтись по пользовательским AC1–AC13 (`user-spec.md::AC1`–`AC13`) и
   сопоставить с конкретными тестами в `oauth_refresh_e2e.rs` (по тесту на
   каждый AC + extras AC11 legacy-lifecycle и AC12 10-parallel-rotations).
6. Свести результат в отчёт `work/refresh-token-rotation/logs/working/pre-deploy-qa-report.md`.
   Структура: общий вердикт (GO / NO-GO), таблица "AC → тест → PASS/FAIL",
   stdout-фрагменты четырёх гейтов, список замеченных отклонений и
   действий, если есть. NO-GO означает, что Task 10 НЕ стартует.
7. Если что-то FAIL — НЕ исправлять прямо здесь. Зафиксировать в отчёте
   и в `decisions.md`, дать команде сделать fix-PR; повторно запустить
   Task 9 на исправленном чекауте.

## Verification Steps

### Automated
- `cargo test --workspace --no-fail-fast` → all GREEN, в том числе:
  - `cargo test -p mnemonic-mcp --test oauth_refresh_e2e` — 15 тестов PASS,
    wall-clock <2s.
  - `cargo test -p mnemonic-mcp refresh::tests` — все unit-тесты Branch
    A/B/B'/C/D/E + LRU + миграция + evictor PASS.
  - `cargo test -p mnemonic-mcp oauth::tests` — все unit-тесты salt boot,
    grant_type, cache headers, logging policy, jwt_ttl PASS.
  - `cargo test -p mnemonic-mcp --test auth_allowlist` — без регрессий.
  - `cargo test -p mnemonic-mcp --test anonymous_recall` — без регрессий.
- `cargo clippy --workspace --all-targets -- -D warnings` → exit 0.
- `cargo fmt --all -- --check` → exit 0.
- `gitleaks detect --no-banner` → exit 0 на working tree.
- `gitleaks detect --no-banner --log-opts="--all"` (или эквивалент для
  полной истории) → exit 0.
- Локальный smoke: запустить
  `STORAGE_MODE=local PAYMENT_MODE=none MCP_REFRESH_SALT=$(openssl rand -base64 32) cargo run -p mnemonic-mcp --release -- --transport http --port 3000`
  в фоне, затем
  `curl -s http://localhost:3000/.well-known/oauth-authorization-server | jq '.grant_types_supported'`
  → массив содержит `"authorization_code"` И `"refresh_token"`. Остановить
  сервер.

## Details

**Files:**
- `work/refresh-token-rotation/logs/working/pre-deploy-qa-report.md` (new) —
  единственный артефакт этой задачи. Содержит общий вердикт, таблицу
  AC → тест → PASS/FAIL, stdout-фрагменты гейтов, перечень действий при
  NO-GO. Markdown (НЕ JSON — это краткий человекочитаемый отчёт).

**Dependencies:**
- Tasks 6, 7, 8 (Audit Wave) — должны быть DONE, отчёты в
  `logs/working/code-audit.md`, `security-audit.md`, `test-audit.md`
  прочитаны и учтены: если аудиты подняли блокирующие issues, их fix
  должен быть в чекауте до запуска Task 9.
- Все Tasks 1–5 (Waves 1–4) DONE — иначе тесты не соберутся.

**Edge cases:**
- Если на ветке остались артефакты от R1-деплой попыток (Task 10
  попадает раньше Task 9 в каком-то альтернативном порядке — НЕ наш
  случай, но защититься в чек-листе): `git status` должен быть чист.
- Если `cargo test` падает на flaky сетевом или time-зависимом тесте,
  прогнать ещё раз и зафиксировать стабильность в отчёте (D13
  гарантирует timing-isolation через `Duration` fields, поэтому
  flaky timing-tests быть не должно — если есть, это регрессия).
- Если gitleaks ругается на test-фикстуры с фиктивными секретами,
  убедиться что они уже в allowlist; если нет — добавить allowlist
  и зафиксировать в отчёте как deviation.
- Salt boot-validation тесты (`salt_missing_aborts_boot`,
  `salt_under_32_bytes_aborts_boot`) — критичны: если они FAIL, фича
  едет в прод с дырой; сразу NO-GO.

**Implementation hints:**
- Не пересобирать всё с нуля если есть кеш — `cargo test` сам решит,
  что инвалидно. Для clippy и fmt — отдельные команды, кеш Cargo
  переиспользует.
- Полную историю gitleaks гнать через
  `gitleaks detect --no-banner --log-opts="--all --full-history"` или
  по precedent из `patterns.md::Security gates` — взять команду оттуда
  как source of truth.
- `jq '.grant_types_supported'` ожидает JSON; если discovery вернёт
  HTML/text — это сама по себе FAIL по AC7.
- Отчёт писать сжато: общий вердикт сверху, таблица посередине,
  raw stdout — внизу под `<details>`-блоками если нужно.
