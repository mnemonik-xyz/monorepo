# Task 12: Post-deploy verification

## Required Skills

Before starting, load:

## Description

Live verification of the OAuth 2.1 refresh-token rotation feature on production
(`mcp.mnemonik.xyz`, version `v0.2.5`) after Task 11 prod deploy. This task is the
final gate: it confirms that the rotation surface, the D14 logging policy, and
the discovery metadata behave as specified under real MCP-host clients (Cursor and
Claude.ai) and that the operator-visible telemetry on the VPS matches the
contract (events emitted, sensitive fields absent).

Why this matters: pre-deploy QA (Task 9) and the dev R1 gate (Task 10) cover the
test harness and the dev environment. Task 12 is the only verification step that
runs against the real prod binary, with real client behaviour across actual JWT
expiries, and against the real `journalctl` log stream on the VPS — closing the
loop on AC7 (discovery), the user-spec lifetime ACs, and the D14 logging policy
that auditors flagged as the highest-impact non-test invariant of the feature.

The task produces a single report at
`work/refresh-token-rotation/logs/working/post-deploy-verification-report.md`
that records GO/NO-GO per check, the raw curl/log evidence, and the user's
manual observations from the two MCP-host sessions.

## What to do

1. Run the discovery smoke check against prod and confirm the response contains
   both supported grant types (AC7).
2. Ask the user to open a real Cursor session signed into `mcp.mnemonik.xyz` and
   leave it idle for at least 65 minutes (longer than the 1h JWT TTL), then call
   `mnemonic_whoami` once and confirm the response arrives without any
   re-authorization page or OAuth prompt.
3. Ask the user to open a real Claude.ai session signed into `mcp.mnemonik.xyz`,
   leave it idle for at least 65 minutes, then call `mnemonic_sign_memory` once
   and confirm the operation succeeds silently after the first JWT expiry.
4. SSH (or otherwise connect) to the prod VPS and tail the `mnemonic-mcp`
   service log via `journalctl`, filtering for the rotation events. Confirm
   the presence of `refresh_rotation` INFO events and (if any family-revoke
   occurred) `family_revoke` WARN events, each carrying the forensic fields
   D14 requires (`sub`, `family_id`, `remote_addr`, `request_id`), and the
   absence of any plaintext refresh token, `token_hash`, salt bytes, or full
   `access_token` string in the log lines.
5. Write the report at
   `work/refresh-token-rotation/logs/working/post-deploy-verification-report.md`
   capturing the raw curl JSON, the user's Cursor and Claude.ai observations,
   a representative sanitized log excerpt, and a final GO / NO-GO verdict per
   check.

## Verification Steps

### Smoke

Run the discovery probe against prod and assert both grant types are present:

```bash
curl -s https://mcp.mnemonik.xyz/.well-known/oauth-authorization-server | jq '.grant_types_supported'
```

Expected: a JSON array containing both `"authorization_code"` and `"refresh_token"`. Capture the raw output into the report.

Tail prod logs on the VPS for the rotation events emitted during the user
verification (run during steps 2–3 of `What to do`):

```bash
# On the prod VPS:
sudo journalctl -u mnemonic-mcp -f | grep -E 'refresh_rotation|family_revoke'
```

Expected: at least one `refresh_rotation` INFO line during the Cursor/Claude.ai
observation window with `sub`, `family_id`, `remote_addr`, `request_id` fields
present. NO plaintext, NO `token_hash`, NO salt, NO full `access_token`.

### User

Ask the user to perform the two real-client checks. Provide them with a clear
script:

1. Open Cursor with the MCP server pointed at `mcp.mnemonik.xyz`. Confirm
   `mnemonic_whoami` works initially. Leave the IDE open and idle (or do unrelated
   work) for at least 65 minutes. Then invoke `mnemonic_whoami` again.
   Expected: the call succeeds and Cursor never opens an OAuth re-authorization
   page. Capture the user's verbal confirmation + timestamp in the report.
2. Open Claude.ai with the same MCP server connected. Confirm
   `mnemonic_sign_memory` works initially. Leave the chat idle for at least 65
   minutes, then call `mnemonic_sign_memory` again.
   Expected: the call succeeds silently after the first JWT TTL has elapsed.
   Capture the user's verbal confirmation + timestamp in the report.

Both observations together confirm the user-spec R1 gate holds on prod with the
default `MCP_JWT_TTL_SECS=3600` and a real refresh-token rotation cycle.

## Details

**Files:**
- `work/refresh-token-rotation/logs/working/post-deploy-verification-report.md` (new) — the verification report. Sections to include:
  - **Environment**: prod host, version tag (`v0.2.5`), date/time of verification, operator identity.
  - **Discovery check**: raw `curl` output + `jq` filtered result + GO/NO-GO.
  - **Cursor session**: start time, expiry time, post-expiry tool call result, screenshots or user quote, GO/NO-GO.
  - **Claude.ai session**: same structure.
  - **Log tail**: sanitized excerpt of `refresh_rotation` and (if observed) `family_revoke` lines; explicit checklist confirming absence of plaintext / token_hash / salt / full access_token; GO/NO-GO.
  - **Summary**: overall GO/NO-GO verdict tying back to user-spec AC1, AC2, AC7 and tech-spec D14.

**Dependencies:**
- Task 11 (prod deploy) must be GREEN. Confirm the running prod version is `v0.2.5` before starting (e.g. via release tag in the deploy log or a version endpoint if exposed).
- Operator access to the prod VPS (`journalctl -u mnemonic-mcp`) — coordinate with the user if SSH credentials are needed.
- A real user willing to keep a Cursor session and a Claude.ai session idle for >65 minutes and report back.

**Edge cases:**
- No `refresh_rotation` events appear during the tail window: ask the user to perform an additional MCP tool call after the expected expiry so a rotation is forced. If still no event, that is a NO-GO — refresh-grant path is not being exercised in prod and we cannot confirm D14 policy.
- A `family_revoke` event appears unexpectedly during normal-use verification: capture it verbatim, mark NO-GO, and escalate — replay-detection firing on a legitimate session indicates a bug.
- Discovery returns only `authorization_code`: NO-GO; the deploy did not ship Task 3's discovery change. Roll back per `deployment.md`.
- User reports an OAuth re-authorization page in Cursor or Claude.ai after the 65-minute idle window: NO-GO; refresh-grant is failing or the client did not use it. File a follow-up consistent with the R1 NO-GO escalation path documented in tech-spec (Anthropic ticket + advance `work/stateless-auth-rearch/`).
- Log line contains anything in the forbidden set (plaintext, `token_hash`, salt, full `access_token`): NO-GO; this is a D14 violation and the highest-severity finding the task can produce. Immediate rollback per `deployment.md` and append an incident note to `decisions.md`.

**Implementation hints:**
- Run the discovery curl BEFORE asking the user to start their 65-minute idle windows — it is fast and fails fast if the deploy is wrong, saving the user's time.
- Coordinate the start times of the two user sessions so the log tail window covers both, reducing the number of separate log captures.
- When sanitizing log excerpts for the report, redact the per-request `sub` (Google subject) if it identifies the real user; keep `family_id`, `remote_addr`, `request_id` since they are the D14-required forensic fields and not directly user-identifying.
- The expected log line shape is INFO-level structured tracing; check `deployment.md` Monitoring & observability section for the project's expected log format if uncertain.
