## Description

Wave-2 wiring task: integrates the Wave-1 outputs (`mcp/src/oauth/refresh.rs` from Task 1 + `OnceLock`-backed `jwt_ttl_secs()` + `pub mod refresh;` from Task 2) into the HTTP handler surface.

Concretely:

1. Widen `OAuthState` with the five new fields (`refresh_store`, `refresh_salt`, `reuse_interval`, `evictor_tick`, `reuse_cache`) per Decision 6 / tech-spec §Shared resources, and thread the new constructor signature through all four `OAuthState::new` call sites (`main.rs::run_http`, `mcp/tests/_helpers/mod.rs`, `oauth/mod.rs::fresh_state` unit-test fixture, `mcp/src/mcp.rs` internal test fixture). The test-helper change in this task is signature-threading only — the new `with_oauth_token` builder method and fixture helpers (`bootstrap_oauth`, `rotate`, `insert_expired_refresh`, fast-`reuse_interval` setter) belong to Task 4.
2. Widen `TokenRequest` so every field is `Option<String>` (per tech-spec §Data Models and code-research §I.2). Add the explicit `grant_type` and `refresh_token` fields. `grant_type` defaults to `"authorization_code"` so legacy clients (existing webapp redeem, integration tests, `scripts/test-oauth-flow.sh`) that omit the field continue to hit the existing path.
3. Add the post-parse dispatch in `token_handler` (after the content-type dispatch at `oauth/mod.rs:990-1017`):
   - `"authorization_code"` (or default) → existing code+verifier path, with the new requirement that both fields be present-and-non-empty (return `invalid_request` otherwise — Decision 11).
   - `"refresh_token"` → require `refresh_token` non-empty AND `<= 4096` bytes (Decision 16, length-cap BEFORE hashing or any DB work), then call Task-1's `refresh::rotate(&state, plaintext)` and translate its result into a `(access_token, "Bearer", expires_in, refresh_token)` 4-field JSON response.
   - Any other `grant_type` → `400 unsupported_grant_type` (Decision 11 — closes the fallthrough where unknown grant types would otherwise silently re-enter the authorization_code path).
4. Emit `Cache-Control: no-store` + `Pragma: no-cache` on EVERY response from `token_handler` — success AND error alike (Decision 15 / RFC 6749 §5.1).
5. Append `"refresh_token"` to `grant_types_supported` in `/.well-known/oauth-authorization-server` (one-line change at `oauth/mod.rs:1178-1191` — code-research §I.7).
6. In `main.rs::run_http`, gate boot on `MCP_REFRESH_SALT`: read the env var, base64url-decode it, and abort boot if the decoded byte length is `< 32` (Decision 2 — guards against an operator setting a 32-character ASCII string with `~5` bytes of effective entropy that would pass a raw-byte length check).
7. In `main.rs::run_http`, spawn `refresh::start_evictor` alongside the existing `_confirmation_evictor` spawn point. Pass `evictor_tick` from `OAuthState`.
8. Document the two new env vars (`MCP_REFRESH_SALT` mandatory, `MCP_JWT_TTL_SECS` optional) in `.env.example` and the deployment doc — `MCP_REFRESH_SALT` MUST cite the `openssl rand -base64 32` recipe as the generator (Decision 2 — closes the entropy footgun). Task 2 already documented `MCP_JWT_TTL_SECS`; this task adds the `MCP_REFRESH_SALT` lines next to it.

After this task lands, the server boots cleanly with a valid salt, discovery advertises both grants, and the refresh path is live end-to-end through the HTTP surface. The integration-test infrastructure (`with_oauth_token`, AC1–AC13 e2e suite) is Task 4 and Task 5.

### Smoke

Server boots with a valid `MCP_REFRESH_SALT` and discovery advertises both grants:

```bash
# 1. Generate a valid salt + boot the server.
MCP_REFRESH_SALT="$(openssl rand -base64 32)" \
STORAGE_MODE=local PAYMENT_MODE=none \
  cargo run -p mnemonic-mcp --release -- --transport http --port 3000 &

# 2. Discovery advertises both grants.
curl -s localhost:3000/.well-known/oauth-authorization-server \
  | jq '.grant_types_supported'
# Expected: ["authorization_code", "refresh_token"]

# 3. Same response carries Cache-Control: no-store on /oauth/token (success and error).
curl -i -X POST localhost:3000/oauth/token \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'grant_type=client_credentials'
# Expected: HTTP/1.1 400 + Cache-Control: no-store + Pragma: no-cache + {"error":"unsupported_grant_type..."}

# 4. Boot fails fast with a short / missing salt.
unset MCP_REFRESH_SALT
cargo run -p mnemonic-mcp --release -- --transport http --port 3000
# Expected: process exits with a clear error mentioning MCP_REFRESH_SALT and the 32-byte minimum.

MCP_REFRESH_SALT="YQ==" \
  cargo run -p mnemonic-mcp --release -- --transport http --port 3000
# Expected: process exits with a clear error mentioning the 32-byte minimum AFTER base64url decode.
```

**Dependencies:**

- Task 2 (`pub mod refresh;` declared in `oauth/mod.rs`, `jwt_ttl_secs()` reading the `OnceLock<u64>`).

**Edge cases:**

- Concurrent rotations on sibling rows of the same `family_id` — already handled by Task 1's `BEGIN IMMEDIATE`; this task just plumbs the call through. Do NOT add a new mutex around `refresh::rotate` — the `Arc<Mutex<Connection>>` is sufficient.
- Legacy client posts no `grant_type` field → defaults to `"authorization_code"` (`#[serde(default)]`) so existing webapp / `scripts/test-oauth-flow.sh` / integration tests keep working.
- Legacy client posts `grant_type=authorization_code` with the new TokenRequest shape (all Optional) but omits `code` or `code_verifier` → `400 invalid_request` (was previously a serde-deserialize failure with the same status; behaviour is structurally equivalent, just routed through `oauth_error`).
- `MCP_REFRESH_SALT="hello-world-this-is-32-chars-long"` (32 ASCII chars, base64url-decoded gives `~24` bytes of garbage but the decode itself may succeed with arbitrary bytes) → boot aborts because the DECODED byte length is `< 32`. Test this explicitly in `salt_under_32_bytes_aborts_boot`.
- `MCP_REFRESH_SALT` value contains base64-standard chars (`+/=`) instead of base64url (`-_`) — accept both `base64::engine::general_purpose::URL_SAFE` and `URL_SAFE_NO_PAD`; if Decision 2's "base64url" is meant strictly, document the strict choice and reject — match Task 1 / `refresh.rs` choice. Prefer the strict url-safe variant since `.env.example` ships `openssl rand -base64 32` (standard, with padding) — handle that case explicitly. Re-read `refresh.rs` (Task 1) to align.
- `refresh_token` field exactly 4096 bytes → accepted (boundary is `> 4096` rejected).
- Response headers — be sure to set headers on the response carrying the JSON body, not only on a synthesised error response. Test `token_response_emits_no_store_cache_headers` must assert the headers on BOTH success and error paths.

**Implementation hints:**

- Wrap `token_handler`'s body in a small helper that returns a `Response`, and at the end of the handler post-set the two cache headers before returning. This guarantees every exit point gets the headers without scattering header inserts across N return sites.
- For `OAuthState::new`, follow `mcp/src/escrow.rs:113` for the `Arc<Mutex<Connection>>` field shape and `mcp/src/oauth/google.rs:340` for the multi-arg constructor convention.
- For the `MCP_REFRESH_SALT` base64url decode, use `base64::engine::general_purpose::URL_SAFE_NO_PAD` (with a fallback to `URL_SAFE` for padded input). Emit a clear `eprintln!` + return `Err(anyhow!(...))` on failure — `run_http` returns `Result<()>` so propagating the error aborts boot cleanly.
- `refresh::start_evictor` spawn point: alongside `_confirmation_evictor` in `main.rs::run_http`. Pattern from `confirmation_token.rs:259-267` — `tokio::spawn(async move { loop { sleep(tick).await; ... } })`, NOT `tokio::time::interval`.
- When threading the new `OAuthState::new` signature through tests, keep all the existing test-specific defaults (`TEST_JWT_SECRET`) and add a fixed test salt `[0xAB; 32]` + a fast `reuse_interval = Duration::from_millis(100)` + a permissive `evictor_tick = Duration::from_millis(50)`.
- The post-parse dispatch in `token_handler` lives AFTER the existing form/JSON parse at `oauth/mod.rs:990-1017` and BEFORE the existing `state.codes.lock().pop(&req.code)` at `oauth/mod.rs:1019-1022`. Keep the existing path intact for `grant_type=authorization_code`; redirect the new path early.
- The `unsupported_grant_type` branch is critical security-wise — without it, an unknown `grant_type` would silently re-enter the `authorization_code` path with empty `code` / `code_verifier` and surface a confusing error. Explicit `unsupported_grant_type` matches RFC 6749 §5.2 and Decision 11.
- For `salt_under_32_bytes_aborts_boot`, use a deterministic short payload like `"YQ=="` (decodes to `b"a"`, 1 byte) so the test is reproducible.
