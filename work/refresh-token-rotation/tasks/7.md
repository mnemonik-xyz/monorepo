# Task 7: Security Audit

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:security-auditor` — [agents/security-auditor.md](~/.claude/agents/security-auditor.md)

## Description

Full-feature security audit across every file touched by Tasks 1–5 of `refresh-token-rotation` (the new `refresh.rs` module, the widened `OAuthState` / `TokenRequest` / `token_handler`, the `JWT_TTL_SECS` env plumbing, the boot-time salt validation, the integration tests, and adjacent infra such as `main.rs`, `mcp.rs`, `escrow.rs`, `_helpers/mod.rs`, `test_support.rs`).

This is the security read-only pass of the Audit Wave — analysis-only, no code changes. Findings trigger a fixer + reviewer cycle on the upstream tasks if necessary.

The audit must walk OWASP Top 10 (A01–A10) against the new surface — refresh-token rotation, family-revoke, opaque-token hash-at-rest, the LRU pair cache, the boot-time secret material, the new env vars, the logging policy — and produce a per-focus-area verdict (closed / residual-risk-documented / finding) with file:line citations and threat-model reasoning.

In addition to the standard OWASP coverage, this task has a fixed list of decision-specific invariants from the tech-spec that MUST be checked individually (see What to do below).

## What to do

Audit the full set of files modified by Tasks 1–5 against OWASP Top 10 plus the decision-specific invariants below. For each item, verify the implementation actually closes the threat, or document the residual risk.

**Decision-specific invariants to verify (must all be checked, one verdict per item in the report):**

- **Salt is mandatory and ≥32 bytes after base64url decode (D2).** `MCP_REFRESH_SALT` is read at boot in `run_http`; boot aborts with a clear error if the env var is absent, or if the base64url-decoded length is under 32 bytes. The 32-character-ASCII footgun (~5 bytes of effective entropy passing a raw-byte length check) must be closed by decoding before measuring length. No fallback derived from `MCP_JWT_SECRET` exists anywhere in the codebase.

- **No plaintext refresh-token, no `token_hash`, no salt, no full `access_token` in `tracing` logs (D14).** Grep every `tracing::*!` macro call site in `oauth/refresh.rs` and the refresh branch of `token_handler`. For each of Branches A, B, B', C, D, E confirm the documented forensic-field set is logged (`family_id`, `sub`, `outcome`, `remote_addr`, `request_id` for A/B/C/D; outcome + addr + request_id + optional SHA256-stem for B'/E) and confirm none of the forbidden fields (plaintext, at-rest `token_hash`, salt bytes, full JWT access token) appear in any branch. Also verify Branches C, D, E use WARN/INFO levels as documented so volume alarms remain useful (CWE-778 mitigation).

- **Refresh-token field length cap enforced (D16, 4 KiB).** `token_handler` rejects `refresh_token` values longer than 4096 bytes with `400 invalid_request` BEFORE any blake3 hashing, before any `Connection` Mutex acquisition, before any SQL. Verify the check sits at the parse-time validation step and is not gated behind any other branch. Confirm no path allows a giant `refresh_token` to reach `refresh::rotate` and amplify shared-mutex contention (CWE-400).

- **`Cache-Control: no-store` + `Pragma: no-cache` headers on every `/oauth/token` response, success AND error (D15, RFC 6749 §5.1).** Trace every response builder path in `token_handler` (success path, `invalid_request`, `invalid_grant`, `unsupported_grant_type`, `500 internal_error`) and confirm both headers are emitted in each. Verify there is no early-return or error-shortcut that escapes the header-application layer.

- **Unknown `grant_type` returns `400 unsupported_grant_type` (D11, RFC 6749 §5.2).** Trace the post-parse `grant_type` dispatch in `token_handler`. Confirm any value not in `{"authorization_code", "refresh_token"}` returns `400 unsupported_grant_type` — closing the fallthrough vector where an unknown grant could silently re-enter the `authorization_code` path. Verify the absent-grant-type case (no `grant_type` field at all) maps to the legacy `authorization_code` path only if `code` + `code_verifier` are present, else `400 invalid_request`.

- **LRU `put` precedes `COMMIT` in Branch A (D5).** Read `refresh::rotate` Branch A code path. Confirm the publish ordering: (i) acquire `Arc<Mutex<Connection>>`, (ii) BEGIN IMMEDIATE, (iii) UPDATE/INSERT, (iv) `reuse_cache.put(old_hash, pair)`, (v) COMMIT, (vi) release Mutex. The cache `put` MUST be at step (iv) — between the writes and COMMIT — not after COMMIT. Verify whether the debug-build hook `debug_hook_cache_put_after_commit` exists (added by Task 1). If absent — flag as a CRITICAL audit finding (D5 ordering invariant is not test-pinned). If present — confirm its unit test asserts the race materializes when the hook is flipped. This closes the CWE-362 race where a Branch B retry could observe `revoked=1` from SQL before the cache entry is published.

- **`family_revoke` runs IN the same `BEGIN IMMEDIATE` transaction (D8).** In Branch C of `refresh::rotate`, the SELECT detecting the replay AND the UPDATE walking `family_id` to revoke every row in the family MUST run inside the same `BEGIN IMMEDIATE` transaction (no second transaction, no lock release between detect and revoke). Confirm by reading the code that no `COMMIT` / `tx.commit()` precedes the family-revoke `UPDATE`. This prevents a Branch C from racing with a concurrent Branch A on a sibling row. Also confirm the matching pair-cache entries for revoked family members are dropped (Branch C cleans cache, not just DB).

- **Existing `tower_governor` per-IP rate limiter on `/oauth/*` still active.** The refresh-grant inherits the existing limiter per `architecture.md:65`. Verify the route mounting in `main.rs` / `mcp.rs` did not accidentally strip the `tower_governor` layer from `/oauth/token`, and verify no new bypass route was introduced. The audit must not assume the limiter is in place — it must trace the actual layer-application code.

- **R7 no-global-logout trade-off documented but not silently introduced.** Decision 7 explicitly accepts the no-global-logout limitation. Confirm: (a) tech-spec and user-spec call out R7 / D7 explicitly; (b) implementation does not silently add a half-baked global-logout endpoint that doesn't actually revoke; (c) no code path falsely advertises a logout/revoke capability that the access-token JWT cannot honor. The point is to ensure the trade-off is accepted in the open, not hidden behind a fake-success surface.

**OWASP Top 10 walk (each must receive a verdict):**

- **A01 Broken Access Control** — refresh-grant does not let one `sub` rotate another `sub`'s token; `family_id` isolation across multi-device sessions holds (D3); the V1 limitation of not validating `client_id` against the refresh row is acceptable under public-clients model (`token_endpoint_auth_methods_supported: ["none"]`) and is documented.
- **A02 Cryptographic Failures** — refresh token plaintext is 32 random bytes from a CSPRNG (not `rand::thread_rng` if non-secure); blake3 hashing uses the mandatory salt; salt entropy is real (D2 base64url-decode check); JWT HS256 secret handling unchanged; no plaintext or hash at rest leaks via logs (D14) or response bodies.
- **A03 Injection** — every SQL in `refresh.rs` uses `rusqlite` parameter binding, no `format!` into SQL; no user input flows unsanitized into the `family_id` walk; no string interpolation in the `Cache-Control` header construction.
- **A04 Insecure Design** — rotation transaction design (D5, D8) covers the CWE-362 race and the sibling-family race; reuse-interval (D4) covers retry-vs-replay without opening a wider replay window; fail-closed Branch B' is intentional and documented.
- **A05 Security Misconfiguration** — boot aborts on absent/short salt (D2); `MCP_JWT_TTL_SECS` clamp `[60, 604800]` + WARN on parse failure (D12) prevents 1s footgun; no debug endpoints exposed; no permissive CORS added to `/oauth/token`.
- **A06 Vulnerable / Outdated Components** — no new dependencies in prod tree except `tracing-test` as `[dev-dependencies]` (per tech-spec Dependencies); audit confirms no new prod deps slipped in.
- **A07 Identification & Authentication Failures** — opaque refresh tokens (D1, D2); family-revoke on out-of-window replay (Branch C, D8); rotation is single-use within window (D4, D5); access-token format unchanged (D7); no fallback that lets a revoked refresh succeed.
- **A08 Software & Data Integrity Failures** — migration is idempotent (`CREATE TABLE IF NOT EXISTS`); rolling deploy safe; rollback is revert-the-tag with no data migration to undo; DB write failure during rotation returns 500 and retry-within-window is safe (Branch B cache hit).
- **A09 Security Logging & Monitoring Failures** — D14 logging policy provides credential-stuffing detection surface on Branch E (`remote_addr` + `request_id` logged); Branches C/D/E use WARN/INFO so log-volume alarms can distinguish abuse from operational expiry; the optional SHA256-stem on B'/E is a one-way digest distinct from the at-rest hash.
- **A10 Server-Side Request Forgery** — not applicable to this surface, but confirm no new external HTTP call was introduced in the refresh path.

**Specific code-level grep checks to perform (must all be in report):**

- `grep -rn "tracing::" mcp/src/oauth/refresh.rs mcp/src/oauth/mod.rs` — list every call site, classify each, confirm none log forbidden fields.
- `grep -rn "format!\|format_args!" mcp/src/oauth/refresh.rs` — confirm no string interpolation into SQL or log messages that includes credential material.
- `grep -rn "unwrap()\|expect(" mcp/src/oauth/refresh.rs` — outside `#[cfg(test)]`, no `unwrap()` in production paths (project-wide rule per `patterns.md`).
- `grep -rn "MCP_REFRESH_SALT\|MCP_JWT_TTL_SECS" mcp/src/ .env.example .claude/skills/project-knowledge/references/deployment.md` — both env vars are read in exactly one place, documented in `.env.example`, and called out in `deployment.md`.
- `grep -rn "tower_governor" mcp/src/` — confirm the limiter is still applied to `/oauth/*`.

Write the audit report to `work/refresh-token-rotation/logs/working/security-audit.md`. ## Details

**Files:**
- `work/refresh-token-rotation/logs/working/security-audit.md` — new audit report (this task's only output).

**Dependencies:**
- Task 5 (Integration test suite) must be complete so the full surface — including the integration-test boundary — is auditable.

**Edge cases to specifically probe:**
- `MCP_REFRESH_SALT` set to a 32-character ASCII string (`"a" * 32`) — must abort boot (raw-byte length passes 32, but base64url-decoded length is shorter and entropy is ~5 bytes).
- `MCP_REFRESH_SALT` set to a valid base64url string that decodes to exactly 32 bytes — must boot.
- `MCP_REFRESH_SALT` absent — must abort boot with a clear error message.
- `MCP_JWT_TTL_SECS=notanumber` — must WARN and fall back to 3600, not silently become 0 or panic.
- `MCP_JWT_TTL_SECS=1` (below clamp) — must clamp to 60 and WARN.
- `MCP_JWT_TTL_SECS=99999999` (above clamp) — must clamp to 604800 and WARN.
- `refresh_token` of 4097 bytes — must reject at parse with `400 invalid_request`, no DB / hashing reached.
- `grant_type=client_credentials` (unknown grant) — must return `400 unsupported_grant_type`, not silently fall through to `authorization_code`.
- Concurrent Branch A on sibling row of same `family_id` during a Branch C — must serialize via the writer lock; the report should confirm by reading the BEGIN IMMEDIATE scope.
- Cache miss inside reuse window (Branch B') — must return `400 invalid_grant` WITHOUT family-revoke; failing closed.

**Implementation hints:**
- Use `cargo doc --no-deps -p mnemonic-mcp --open` to navigate the module quickly, then drop back to direct file reads for the security-critical paths.
- Cross-reference the `oauth::tests::*` security tests (`salt_missing_aborts_boot`, `salt_under_32_bytes_aborts_boot`, `refresh_token_too_long_returns_invalid_request`, `unknown_grant_type_returns_unsupported_grant_type`, `token_response_emits_no_store_cache_headers`, `logging_policy_no_plaintext_no_hash_across_branches`) — each test SHOULD correspond to a closed verdict in the report, citing both the production code and the test.
- The pair-cache put-before-COMMIT ordering (D5) is expected to have a debug-build hook (`debug_hook_cache_put_after_commit`) per tech-spec D5. Verify presence; if missing, flag as audit finding.
- The shared-resource table in tech-spec § Architecture lists every singleton; cross-check that each has a single owner and the audit can identify the file:line of construction.
- Report format: lead with an executive summary (verdict + count of findings by severity), then per-focus-area sections, then OWASP walk, then grep results.

**Severity rubric (use consistently in report):**
- **critical** — exploitable now, no mitigating controls; ship-blocker.
- **high** — exploitable under realistic conditions; must fix before deploy.
- **medium** — exploitable under specific conditions or with limited blast radius; fix before V2.
- **low** — defence-in-depth gap, no current exploit path.
- **informational** — observation, no action required.
