# Task 5: Integration test suite — `oauth_refresh_e2e.rs`

## Required Skills

## Description

Implement the end-to-end integration test suite for the OAuth 2.1 refresh-token rotation feature. This is Wave 4 — the final wall of coverage that proves the production wire surface matches the 13 user-spec acceptance criteria plus two cross-cutting invariants (cross-table mutex no-starvation; DB write failure retry-safety).

Wave 1–3 produce the runtime: Task 1 ships `mcp/src/oauth/refresh.rs` (rotation transaction, LRU pair cache, evictor, migration); Task 2 wires `OnceLock<u64>` for JWT TTL and adds `pub mod refresh;`; Task 3 widens `OAuthState` / `TokenRequest` / `token_handler`, threads the new state, gates boot on `MCP_REFRESH_SALT`, spawns the evictor, and emits Cache-Control headers; Task 4 lands the `TestServerBuilder::with_oauth_token(true)` flag and the fixture helpers (`bootstrap_oauth`, `rotate` returning `(String, String)`, `insert_expired_refresh_for_test`, `with_reuse_interval`, `with_evictor_tick`).

This task consumes those helpers to author 15 `#[tokio::test]` functions in a single new file. Every test uses `TestServerBuilder::with_oauth_token(true)` plus `with_reuse_interval(Duration::from_millis(100))` so the whole suite runs in under 2 wall-clock seconds — no real `tokio::time::sleep(Duration::from_secs(5/6))` anywhere. Where a test must wait past the reuse window, it sleeps proportional to the configured 100ms interval (e.g. 150ms). The two cross-cutting tests fault-inject SQL failures via the same shared `Connection` to prove the mutex never starves and that retries inside the reuse window succeed with byte-identical pairs.

This is the gate on which Tasks 6–9 (audits and pre-deploy QA) verify acceptance criteria coverage; missing AC coverage here cascades into Task 8 (test audit) and Task 9 (pre-deploy QA) findings.

## What to do

- Create `mcp/tests/oauth_refresh_e2e.rs` with `mod _helpers;` and standard imports from the Task 4 helpers (`TestServer`, `bootstrap_oauth`, `rotate`, `insert_expired_refresh_for_test`).
- Implement 13 AC tests (AC1–AC13) and 2 cross-cutting tests, all annotated `#[tokio::test]` and all building the server via `TestServer::builder().with_oauth_token(true).with_reuse_interval(Duration::from_millis(100)).build()`.
- AC10 must assert **structural equality** between the form-encoded and JSON-encoded refresh-grant responses: same field set, same string lengths for `refresh_token`, identical `token_type`, identical `expires_in`. The `access_token` JWT itself differs across independent rotations (D5 makes Branch B idempotent on the SAME rotation, not across two distinct ones) — exclude it from the equality assertion but assert it is a well-formed three-segment JWT.
- AC11 must exercise the legacy-client multi-call lifecycle: the client never reads the `refresh_token` field, runs a fresh `authorization_code` exchange, calls a Bearer-gated tool, and re-runs `authorization_code` after access expiry — all without ever sending `grant_type=refresh_token`. Asserts no error from the server and that the response keeps the additive `refresh_token` field without breaking parsing.
- AC12 must spawn 10 `tokio::join!` rotations on the same `rt_X` inside the (100ms) reuse window, then assert all 10 responses are byte-identical on **both** `(access_token, refresh_token)` — the PAIR, not just the refresh string. This closes the round-2 test-reviewer minor where single-field assertion would silently pass a regression in which the cache stores only refresh and Branch B re-mints the access JWT.
- AC3 (replay outside window) and AC4 (family revoke) sleep for 150ms (>100ms reuse window) instead of 6s.
- `cross_table_mutex_no_starvation`: interleave 50 refresh rotations with 50 attestation writes against the shared `Connection`; assert both finish in a bounded time budget (e.g. <500ms) and neither side is starved by counting completions per side.
- `db_write_failure_during_rotation_returns_500_and_is_retry_safe`: fault-inject a single SQL write failure on the first Branch-A INSERT via a write-failing decorator/flag (helper provided by Task 4 or added inline by extending the Mutex<Connection> wrapper for the test); assert the response is 500 AND a retry within reuse window succeeds with a byte-identical `(access_token, refresh_token)` pair (Branch B cache hit).
- Verify the suite runs in under 2 seconds on a typical dev box (`time cargo test -p mnemonic-mcp --test oauth_refresh_e2e`).
- Do not modify any production code or other tests; the only file this task touches is `mcp/tests/oauth_refresh_e2e.rs`.

## Details

**Files:**

- `mcp/tests/oauth_refresh_e2e.rs` (NEW) — single file containing 15 `#[tokio::test]` functions. Top of file: `mod _helpers;` plus `use _helpers::{TestServer, bootstrap_oauth, rotate, insert_expired_refresh_for_test};` and stdlib imports (`std::time::Duration`, `tokio::join`, `serde_json::json`, `axum::http::StatusCode`). No `use` of any production module beyond `mnemonic_mcp::oauth` types for response deserialization where strictly needed. No test inserts secrets — `MCP_REFRESH_SALT` is provided by the `TestServerBuilder` default (a deterministic test salt ≥32 bytes — see Task 4 helper code).

**Dependencies:**
- Task 4 must be merged (helpers exist with the listed signatures and `with_reuse_interval` setter).
- Production crate `mnemonic-mcp` already pulls in `tokio`, `serde_json`, `axum`, `futures` (or this task adds nothing new — verify before writing tests; if `futures` missing for `join_all`, use `tokio::join!` for fixed-arity and a manual `Vec<JoinHandle<_>>` for the 10-rotation case).

**Edge cases:**
- AC12 with 10 parallel rotations: Branch A wins exactly once; remaining 9 hit Branch B with cache HIT and return the cached pair. Test must NOT distinguish which one was Branch A — only that all 10 outputs are equal.
- AC10 structural equality: do NOT compare `access_token` bytes (each independent rotation mints a fresh JWT with new `jti` + `iat`); compare `token_type`, `expires_in`, `refresh_token` length (43 bytes base64url), and overall JSON shape (key set).
- AC3/AC4 sleep: 150ms is enough (>100ms reuse window) without bloating suite time. Do NOT use 6s anywhere.
- AC4 family-revoke check: after triggering family revoke via post-window replay of `r1`, the LIVE descendant `r2` from the legitimate Branch A must also reject — assert 400 `invalid_grant` for `r2`.
- AC5 expired-refresh helper: use `insert_expired_refresh_for_test(&server) -> (plaintext, family_id)` from Task 4; assert `family_has_unrevoked_rows(&server, &family_id)` after the rejection (helper added in Task 4).
- AC9 regression anchor: build `TestServer::builder().build()` WITHOUT `with_oauth_token` for this test — exactly mirrors `anonymous_recall.rs` setup so the anonymous-recall path is untouched.
- AC11 legacy lifecycle: assertion is "no panic, no error envelope" across the multi-call session — not "did not contain refresh_token field" (the additive field is allowed).
- `cross_table_mutex_no_starvation`: count rotations vs attestation writes that complete in each 100ms window; assert no window is fully starved on either side. Use the `Arc<Mutex<Connection>>` exposed by `server.state.store` (existing access pattern from helpers).
- `db_write_failure_during_rotation_returns_500_and_is_retry_safe`: the fault-injection helper must be set up via `server.state.refresh_store_inject_failure_once()` (helper added inline in this task if Task 4 did not ship it — coordinate with the prior task). The second call must succeed with a byte-identical pair due to the Branch B reuse-interval cache hit.

**Implementation hints:**
- Build a small `assert_pair_eq(a, b)` helper at the top of the test file that compares two response bodies on `(access_token, refresh_token)` exactly, for AC12 and the retry-safety test.
- Build a small `assert_structural_eq(form_body, json_body)` helper for AC10 that compares everything EXCEPT the access_token JWT.
- For AC12, spawn 10 futures via `tokio::spawn` so they make progress concurrently, then `join_all`. Avoid `tokio::join!` for fixed-arity 10 — variadic, easier to read with `.await` on a `Vec<JoinHandle>`.
- Storage lock discipline (per `patterns.md` and CLAUDE.md): `rusqlite::Connection` is `!Send`. The shared `Mutex` is never held across `.await` in production; tests must follow the same — lock, read/write, drop guard inline. The Task 4 helper accessors enforce this.
- Do not paste production constants or magic numbers; use the same `Duration::from_millis(100)` value the builder is configured with so the suite stays internally consistent.
- Keep the file lean — under ~500 lines. Helper extraction inside the file is fine; sharing helpers with other tests is OUT OF SCOPE.
