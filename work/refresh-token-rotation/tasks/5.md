## Description

Implement the end-to-end integration test suite for the OAuth 2.1 refresh-token rotation feature. This is Wave 4 — the final wall of coverage that proves the production wire surface matches the 13 user-spec acceptance criteria plus one cross-cutting invariant (cross-table mutex no-starvation).

Wave 1–3 produce the runtime: Task 1 ships `mcp/src/oauth/refresh.rs` (rotation transaction, LRU pair cache, evictor, migration); Task 2 wires `OnceLock<u64>` for JWT TTL and adds `pub mod refresh;`; Task 3 widens `OAuthState` / `TokenRequest` / `token_handler`, threads the new state, gates boot on `MCP_REFRESH_SALT`, spawns the evictor, and emits Cache-Control headers; Task 4 lands the `TestServerBuilder::with_oauth_token(true)` flag and the fixture helpers (`bootstrap_oauth` returning `(code, verifier, redirect_uri)`, `rotate(server, refresh) -> (access_token, refresh_token)` tuple, `insert_expired_refresh_for_test(server) -> (plaintext, family_id)` tuple, `family_has_unrevoked_rows(server, family_id) -> bool`, `with_reuse_interval`, `with_evictor_tick`).

This task consumes those helpers to author 14 `#[tokio::test]` functions in a single new file. Every test uses `TestServerBuilder::with_oauth_token(true)` plus `with_reuse_interval(Duration::from_millis(100))` so the whole suite runs in under 2 wall-clock seconds — no real `tokio::time::sleep(Duration::from_secs(5/6))` anywhere. Where a test must wait past the reuse window, it sleeps proportional to the configured 100ms interval (e.g. 150ms). The single cross-cutting test interleaves refresh rotations with attestation writes on the shared `Connection` to prove the mutex never starves either side under contention.

**Scope-down note on R6 (DB-write-failure retry-safety):** the earlier draft of this task included a `db_write_failure_during_rotation_returns_500_and_is_retry_safe` integration test that fault-injected a SQL write failure via a hypothetical `McpState::refresh_store_inject_failure_once()` hook. That hook does not exist on `McpState`, and Task 5 is forbidden from modifying production code to add it. The realistic alternatives (mock `Connection` — `rusqlite` exposes no trait; cfg-test-gated `Arc<AtomicBool>` flag inside `ReuseCache` — out of scope for a tests-only task) all leak into Wave 1/3 production surface. **Decision: drop the R6 integration test from Task 5 entirely.** R6 risk is covered by Task 6 code-audit, which verifies that `refresh::rotate` propagates `rusqlite::Error` correctly (transaction rollback by SQLite semantics, response → 500 via `oauth_error`) and that a subsequent retry within the reuse window hits Branch B (cached pair) without re-entering the SQL path. Document this scope-down in the post-completion report so the audit chain catches any drift.

This is the gate on which Tasks 6–9 (audits and pre-deploy QA) verify acceptance criteria coverage; missing AC coverage here cascades into Task 8 (test audit) and Task 9 (pre-deploy QA) findings.

- Use the Task-4 helper signatures EXACTLY as Task 4 ships them — do not invent or rename:
  - `bootstrap_oauth(&server) -> (code, verifier, redirect_uri)` (triple of `String`).
  - `rotate(&server, refresh) -> (access_token, refresh_token)` (tuple of `(String, String)`).
  - `insert_expired_refresh_for_test(&server) -> (plaintext, family_id)` (tuple).
  - `family_has_unrevoked_rows(&server, &family_id) -> bool`.
  If any signature drifts at the point of test-writing (Task 4 has shipped a different shape), fix the call site in the test and note the drift in the post-completion report — do NOT modify Task 4's helper to match an outdated assumption here.
- AC10 must use **TWO independent `bootstrap_oauth` + `authorization_code` exchanges** — one for the form-encoded refresh-grant request, one for the JSON-encoded refresh-grant request. The form path consumes its refresh token; reusing the same `rt_X` for the JSON path would either hit Branch B (cached pair, not a parity test) or Branch C (family revoke, also not a parity test). Then assert **structural equality** between the two responses: same field set, identical `token_type`, identical `expires_in`, identical `refresh_token` length (43 base64url chars). The `access_token` JWT itself differs across independent rotations — exclude it from byte equality but assert it is a well-formed three-segment JWT in both responses.
- AC11 must exercise the legacy-client multi-call lifecycle: the client never reads the `refresh_token` field, runs a fresh `authorization_code` exchange, calls a Bearer-gated tool, and re-runs `authorization_code` after access expiry — all without ever sending `grant_type=refresh_token`. Asserts no error from the server and that the response keeps the additive `refresh_token` field without breaking parsing.
- AC12 must spawn 10 parallel rotations on the same `rt_X` inside the (100ms) reuse window. Use `tokio::spawn` + `futures::future::join_all` (or sequential `.await` of a `Vec<JoinHandle>`) since `tokio::join!` is fixed-arity and clunky at 10. Then assert all 10 responses are byte-identical on **BOTH `access_token` AND `refresh_token`** — the PAIR, not just one field. The helper returns the tuple `(access, refresh)` precisely so that this assertion can be made on the pair. Single-field assertion would silently pass a regression in which the cache stores only refresh and Branch B re-mints the access JWT.
- AC3 (replay outside window) and AC4 (family revoke) sleep for ~150ms (`Duration::from_millis(150)`) which is just above the 100ms `reuse_interval`. **Do NOT use the 6-second sleep sketched in `code-research.md` §I.9** — that draft predates D13 and the `with_reuse_interval(100ms)` builder hook, and would inflate the suite wall-clock past the 2s budget. The whole point of D13 + Task 4's `with_reuse_interval` setter is to keep these waits in the 150ms range.
- AC5 uses the Task-4 helper `insert_expired_refresh_for_test(&server) -> (plaintext, family_id)`. After the server rejects the expired plaintext (400 `invalid_grant`), assert `family_has_unrevoked_rows(&server, &family_id) == true` — i.e. the family is NOT revoked (Branch D, expired ≠ replay attack).
- `cross_table_mutex_no_starvation`: interleave 50 refresh rotations with 50 attestation writes against the shared `Connection`; assert both finish in a bounded time budget (e.g. <500ms) and neither side is starved by counting completions per side.
- Verify the suite runs in under 2 seconds on a typical dev box (`time cargo test -p mnemonic-mcp --test oauth_refresh_e2e`).
- **Cargo test target discovery:** Cargo auto-discovers any `.rs` file under `mcp/tests/` as an integration-test binary. The new file `mcp/tests/oauth_refresh_e2e.rs` does NOT require any `[[test]]` entry in `mcp/Cargo.toml`. Do not add one; verify `cargo test -p mnemonic-mcp --test oauth_refresh_e2e` runs the new target without any Cargo.toml edit. If for any reason it doesn't (e.g. a non-default `autotests = false` flag in the manifest), that's an upstream regression — flag it in the post-completion report and add the minimal `[[test]] name = "oauth_refresh_e2e" path = "tests/oauth_refresh_e2e.rs"` entry, but do not assume this is needed.

**Edge cases:**
- AC12 with 10 parallel rotations: Branch A wins exactly once; remaining 9 hit Branch B with cache HIT and return the cached pair. Test must NOT distinguish which one was Branch A — only that all 10 outputs are equal on the pair `(access_token, refresh_token)`. Asserting on the refresh string alone would silently pass a regression where the cache stores only refresh and Branch B re-mints the access JWT.
- AC10 two independent bootstraps: the form-encoded path consumes `rt_X` (its first refresh). Reusing `rt_X` for the JSON-encoded path would either hit Branch B (same cached pair, parity test becomes tautological) or, if the test sleeps past the reuse window, hit Branch C (family revoke, also not parity). Therefore AC10 calls `bootstrap_oauth` twice for two independent `rt_X` / `rt_Y`. Compare `token_type`, `expires_in`, `refresh_token` length (43 bytes base64url), and overall JSON shape (key set) — NOT `access_token` bytes (each rotation mints a fresh JWT with new `jti` + `iat`).
- AC3/AC4 sleep: ~150ms is enough (just above the 100ms `reuse_interval`) without bloating suite time. **Do NOT use 6 seconds anywhere — the 6s value in `code-research.md` §I.9 predates D13 / `with_reuse_interval(100ms)` and would break the <2s wall-clock budget.**
- AC4 family-revoke check: after triggering family revoke via post-window replay of `r1`, the LIVE descendant `r2` from the legitimate Branch A must also reject — assert 400 `invalid_grant` for `r2`.
- AC5 expired-refresh helper: use `insert_expired_refresh_for_test(&server) -> (plaintext, family_id)` from Task 4; after rejection, assert `family_has_unrevoked_rows(&server, &family_id) == true` (Branch D, expired ≠ replay attack).
- AC9 regression anchor: build `TestServer::builder().build()` WITHOUT `with_oauth_token` for this test — exactly mirrors `anonymous_recall.rs` setup so the anonymous-recall path is untouched.
- AC11 legacy lifecycle: assertion is "no panic, no error envelope" across the multi-call session — not "did not contain refresh_token field" (the additive field is allowed).
- `cross_table_mutex_no_starvation`: count rotations vs attestation writes that complete in each 100ms window; assert no window is fully starved on either side. Use the `Arc<Mutex<Connection>>` exposed by `server.state.store` (existing access pattern from helpers).

**Implementation hints:**
- Build a small `assert_pair_eq(a, b)` helper at the top of the test file that compares two response bodies on `(access_token, refresh_token)` exactly, for AC12. The helper consumes the tuples returned by `rotate`.
