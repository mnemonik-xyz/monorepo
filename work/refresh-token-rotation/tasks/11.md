# Task 11: Prod deploy (gated by Task 10)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:deploy-pipeline` — [skills/deploy-pipeline/SKILL.md](~/.claude/skills/deploy-pipeline/SKILL.md)

## Description

Promote the refresh-token-rotation feature to production on `mcp.mnemonik.xyz` after the Task 10 R1 empirical gate signs off with GO. This task tags a release, lets the existing `release.yml` workflow build and ship the artifacts, then performs the VPS deploy per the documented process.

**Only execute if Task 10 reports GO.** A NO-GO outcome from Task 10 means Claude.ai did not survive a forced JWT expiry under refresh-token rotation; in that case this task must STOP without touching prod. The Task 10 report MUST be read first and its verdict confirmed before any tag is pushed.

Two operational constraints matter here:

1. Prod must run with the **1h JWT TTL preserved** — `MCP_JWT_TTL_SECS` is a Task 10 dev knob only. On prod it must be unset (default 3600) or explicitly `3600`. Any other value is a misconfiguration and must be corrected before the deploy is considered done.
2. Prod must run with a **fresh, prod-only `MCP_REFRESH_SALT`**. Reusing the dev salt generated for Task 10 would couple prod tokens to a secret that already lived on the dev box and in Task 10 logs/notes. Generate a new salt for prod (`openssl rand -base64 32`, ≥32 bytes after decode) and store it in the prod secret store before the release tag is pushed.

The `refresh_tokens` table migration runs at server startup via the idempotent `CREATE TABLE IF NOT EXISTS` in `refresh::migrate_refresh_tokens`. Verifying it appears on prod SQLite after first boot is the migration-applied check.

## What to do

1. **Verify Task 10 GO verdict.** Read the Task 10 report at `work/refresh-token-rotation/logs/working/task-10/` (or the location named in the Task 10 task file). Confirm the verdict is GO. If NO-GO — STOP. Do not tag, do not deploy. Note the STOP in the prod-deploy report and exit.
2. **Pre-flight prod env audit.** Confirm with the operator (or by reading the prod env file on the VPS via the documented access path) that:
   - `MCP_JWT_TTL_SECS` is unset OR explicitly equals `3600` on the prod environment.
   - `MCP_REFRESH_SALT` is set on prod to a freshly generated value (NOT the dev-Task-10 salt). If it is not set yet, generate one with `openssl rand -base64 32`, validate that it decodes to ≥32 bytes, and install it in the prod secret store before tagging.
3. **Tag the release.** Cut tag `v0.2.5` on the merged feature commit on `main` (per `deployment.md::VPS Deploy Process` tag convention). Push the tag. The `release.yml` workflow cross-compiles the mcp binary, builds the Docker image, and attaches artifacts to the GitHub Release.
4. **Wait for release.yml to complete green.** If it fails, STOP and write the failure mode into the prod-deploy report. Do not deploy a partially-built artifact.
5. **Deploy to `mcp.mnemonik.xyz`.** Follow `deployment.md::VPS Deploy Process` step-by-step. Pull the released image/binary on the VPS, swap it in, restart the service.
6. **Confirm prod boot.** Tail prod logs and confirm clean startup — specifically that `MCP_REFRESH_SALT` validation passes (no boot-abort), `OnceLock<u64>` for `MCP_JWT_TTL_SECS` seeds to 3600, and `refresh::start_evictor` spawns.
7. **Verify the migration applied.** On the prod SQLite file, confirm the `refresh_tokens` table exists (e.g. `sqlite3 <prod.db> ".schema refresh_tokens"` returns the columns defined in tech-spec Data Models). Idempotent `CREATE TABLE IF NOT EXISTS` means re-running boot is safe.
8. **Write the deploy report.** Capture: Task 10 verdict, tag pushed, release.yml run URL + status, deploy timestamp, prod env confirmation (`MCP_JWT_TTL_SECS` state, `MCP_REFRESH_SALT` set + fresh), migration verification output, any incidents. Save to `work/refresh-token-rotation/logs/working/prod-deploy-report.md`.
9. **Hand off to Task 12.** Task 12 (post-deploy verification) executes the live AVP against the running prod deployment.

## Details

**Files:**
- Prod deploy artifacts on the VPS (binary or Docker image swapped via `deployment.md::VPS Deploy Process`).
- `work/refresh-token-rotation/logs/working/prod-deploy-report.md` (new) — deploy execution report. Fields per step 8.

**Dependencies:**
- Task 10 GO verdict (hard prerequisite — NO-GO ⇒ STOP).
- `release.yml` workflow (existing, triggered by `v*` tag push per `CLAUDE.md`).
- `deployment.md::VPS Deploy Process` — read this first; the deploy mechanics are not duplicated here.

**Edge cases:**
- Task 10 verdict is NO-GO → STOP. Do not tag. Write the STOP into the deploy report and exit.
- `MCP_JWT_TTL_SECS` is set to something other than `3600` on prod → STOP, unset (or correct to `3600`) before tagging. A leftover dev value would silently re-create the Task 10 short-TTL window in prod.
- `MCP_REFRESH_SALT` not set on prod → server aborts boot (D2 boot validation). Generate and install before tagging.
- `MCP_REFRESH_SALT` set to the same value as Task 10's dev salt → STOP, regenerate. Reusing dev secrets in prod violates secret hygiene.
- `release.yml` workflow fails after tag push → STOP, investigate, do not deploy. Do not retag — cut a follow-up patch tag if needed.
- `refresh_tokens` table missing on prod after first boot → migration did not run; check `refresh::migrate_refresh_tokens` was wired in `main.rs::run_http` (Task 3 deliverable) and that the boot logs do not show a swallowed error.

**Implementation hints:**
- Generate the prod salt with `openssl rand -base64 32` per `.env.example` recipe (Decision 2 in tech-spec).
- The deploy mechanics — image pull, service restart, health probe — live in `deployment.md::VPS Deploy Process`; follow that doc verbatim rather than re-deriving steps here.
- This task does not run the live AVP (curl checks, real Cursor/Claude.ai sessions, prod log tailing for `refresh_rotation` / `family_revoke` events). That is Task 12.
- No rollback rehearsal is required for this task — rollback per tech-spec is "revert the tag with no data migration to undo" (Solution section). Document the rollback procedure in the deploy report only if an incident occurs during this task.
