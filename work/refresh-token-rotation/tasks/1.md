# Task 1: Refresh-token storage module + migration + evictor

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Реализовать новый модуль `mcp/src/oauth/refresh.rs` — SQLite-backed
storage для refresh-токенов с миграцией, атомарной ротацией под `BEGIN
IMMEDIATE` (все ветки A, B, B', C, D, E), in-memory LRU pair-cache для
reuse-interval идемпотентности, и фоновым evictor'ом просроченных строк.

Это первая задача Wave 1 фичи `refresh-token-rotation`. Модуль подключается
к `mcp/src/oauth/mod.rs` одной строкой `pub mod refresh;` (см. Files-to-modify
ниже). Без этой строки Rust **не компилирует** файл — auto-discovery не
работает: Cargo требует явной `mod`-декларации в родительском модуле, иначе
ни сам файл, ни его `#[cfg(test)] mod tests` не попадают в тестовый
бинарник, и smoke (`cargo test refresh::tests`) ничего не найдёт.

Контекст и зачем это нужно: hosted HTTP MCP-host сессии (Claude.ai, Cursor,
VS Code) сейчас умирают после истечения 1-часового JWT — клиент должен
заново проходить полный OAuth flow. Стандартная OAuth 2.1 refresh-token
rotation (1h access + 1y rolling refresh, Stripe MCP precedent) решает это
прозрачно для пользователя. Этот таск кладёт фундамент: storage + rotation
core, на который Task 2 повесит JWT TTL knob, а Task 3 — широкие изменения
в `OAuthState`/`TokenRequest`/`token_handler` и discovery.

## What to do

0. Добавить одну строку `pub mod refresh;` в `mcp/src/oauth/mod.rs`
   рядом с другими `pub mod ...;` декларациями (там сейчас `google`,
   `solana`). Эта строка обязательна — без неё Rust не компилирует
   `refresh.rs` и тесты не запускаются. Это единственное изменение
   `oauth/mod.rs` в Wave 1; конфликтов с Task 2/3 нет (они трогают
   другие файлы или другие участки `mod.rs`).

1. Создать новый файл `mcp/src/oauth/refresh.rs` со следующим публичным
   surface:
   - Тип `RefreshToken` — newly-minted token с полями `plaintext`
     (URL-safe-base64), `token_hash` (hex `blake3(salt || raw_bytes)`),
     `family_id` (UUID), `expires_at` (unix seconds).
   - Тип `RefreshTokenRecord` — представление строки таблицы для
     family-revoke + reuse-detection (token_hash, sub, google_sub,
     issued_at, expires_at, revoked, rotated_at, rotated_to, family_id).
   - Тип `ReuseCache` — обёртка над `lru::LruCache<String, (String,
     String, Instant)>` с **manual TTL** и cap; ключ —
     `old_token_hash`, value — `(access_jwt_string,
     new_refresh_plaintext, deadline)`. `lru = "=0.12.5"` НЕ имеет
     native TTL — `LruCache::put` принимает только `(K, V)`; TTL
     реализуется вручную: храним `deadline = Instant::now() + ttl`
     внутри value, в `get` проверяем `if now > deadline -> remove +
     return None`. Конструктор `with_cap_and_ttl(cap: NonZeroUsize, ttl:
     Duration)` (NonZeroUsize т.к. `LruCache::new` ожидает её per lru
     0.12 API), методы `put`, `get`, `remove_by_family` (для D14
     pair-cache cleanup в Branch C).
   - `pub fn migrate_refresh_tokens(conn: &Connection) -> Result<()>` —
     идемпотентная миграция через `execute_batch(MIGRATION_SQL)`, mirrors
     `escrow::migrate_key_escrow_blobs` verbatim. `MIGRATION_SQL` —
     публичная `const &str` (как в `escrow.rs`). Per tech-spec D6 эта
     миграция вызывается на **второй** `Connection`, открытой
     `OAuthState` на том же SQLite-файле (НЕ shared с `McpState.store`).
   - `pub fn mint_for_authorization_code(conn: &Connection, salt, sub,
     google_sub) -> Result<RefreshToken>` — генерирует 32 random bytes,
     base64url encode для wire, `blake3(salt || raw_bytes)` для at-rest,
     генерирует свежий `family_id = Uuid::new_v4()`, INSERT с
     `expires_at = now + 1 год`.
   - `pub fn rotate(conn: &Connection, salt, cache, plaintext) ->
     RotateResult` — ядро ротации в одной `BEGIN IMMEDIATE` транзакции.
     Все ветки A/B/B'/C/D/E внутри одной транзакции (D8). Принимает
     `&Connection` напрямую (per tech-spec D6 — это connection,
     принадлежащая `OAuthState`, не shared с `McpState.store`). См. TDD
     Anchor + Details.
   - `pub fn family_revoke(conn: &Connection, family_id) -> Result<()>`
     — UPDATE `revoked=1, rotated_at=now` для всей семьи (Branch C use).
   - `pub fn evict_expired(conn: &Connection) -> Result<usize>` —
     `DELETE FROM refresh_tokens WHERE expires_at + grace < now`,
     возвращает кол-во удалённых строк.
   - `pub fn start_evictor(conn: Arc<Mutex<Connection>>, tick: Duration)
     -> JoinHandle<()>` — `tokio::spawn` с `loop { sleep(tick).await;
     evict_expired(...) }` per pattern `confirmation_token.rs:259-267`
     (НЕ `tokio::time::interval`). `conn` здесь — `OAuthState`'s second
     connection (D6).
   - `pub fn hash_refresh_token(salt: &[u8], plaintext: &str) -> String`
     — `hex(blake3(salt || plaintext_bytes))`, mirrors
     `payment::hash_api_key` (`payment.rs:737-744`).

2. Реализовать `rotate` с тремя слоями защиты:
   - Pre-flight (вне транзакции): отказать на пустой plaintext;
     length-cap проверка опционально — D16 length-cap живёт в
     `token_handler` (Task 3), но защититься от пустой строки здесь
     дёшево.
   - В `BEGIN IMMEDIATE` транзакции последовательно: SELECT по
     `token_hash = hash_refresh_token(salt, plaintext)`, classify ветку,
     выполнить мутации, COMMIT.
   - В Branch A: после `UPDATE old SET revoked=1, rotated_at=now,
     rotated_to=new_hash` и `INSERT new` — **сделать `cache.put(old_hash,
     (access_jwt, new_plaintext))` ДО `COMMIT`** (D5 ordering invariant,
     это закрывает CWE-362).

3. Имплементировать `ReuseCache` с конфигурируемым cap (default 256, D5)
   и TTL = `reuse_interval` (D13). Использовать `lru` крейт (уже в
   `mcp/Cargo.toml:51`). Бэкенд — `Mutex<LruCache<...>>` либо `parking_lot`
   (выбор по существующему prior art в `mcp/`). Метод
   `remove_by_family(family_id, conn)` сканирует cache и удаляет записи,
   чьи `old_hash` принадлежат семье (нужно для Branch C — иначе остаются
   "вакуумные" `(jwt, refresh)` пары после family-revoke).

4. Реализовать все ветки rotate согласно tech-spec §"How it works" step 4:
   - **Branch A** — `revoked=0, expires_at > now`: ротация. INSERT new,
     UPDATE old; `cache.put` ДО `COMMIT`; вернуть `(new_token, sub,
     google_sub)`.
   - **Branch B** — `revoked=1, rotated_at + reuse_interval > now`,
     cache HIT по `old_token_hash`: вернуть кешированную пару
     `(access_jwt, refresh_plaintext)` byte-for-byte идентично Branch A.
     БЕЗ DB writes.
   - **Branch B'** — same window, cache MISS: вернуть `invalid_grant`
     БЕЗ family-revoke (defensive fail-closed; D5). WARN log с `family_id
     + sub`.
   - **Branch C** — `revoked=1`, outside window: replay. **В ТОЙ ЖЕ
     транзакции** вызвать `family_revoke(conn, family_id)`, очистить
     pair-cache от записей этой семьи (`cache.remove_by_family`),
     COMMIT, вернуть `invalid_grant`. WARN log.
   - **Branch D** — `revoked=0, expires_at <= now`: expired. Вернуть
     `invalid_grant` БЕЗ family-revoke. INFO log.
   - **Branch E** — SELECT not found: вернуть `invalid_grant`. INFO log
     с `remote_addr + request_id + length-prefix` (D14 logging policy
     для unknown tokens).

5. Логирование строго по D14:
   - НИКОГДА не логировать: `token_hash`, full plaintext, JWT
     `access_token`, salt bytes.
   - Branches A, B, C, D логируют `outcome + family_id + sub +
     remote_addr + request_id`.
   - Branches B', E логируют `outcome + remote_addr + request_id +
     first 8 chars of SHA256(plaintext) stem` (one-way digest, отличный
     от at-rest blake3-keyed hash — нельзя cross-correlate).
   - Branches C — WARN; B' — WARN; D, E — INFO; A, B — INFO/DEBUG.

6. Написать unit-тесты в `#[cfg(test)] mod tests` под уже перечисленными
   именами (TDD Anchor). Тесты используют in-memory SQLite + быстрый
   `reuse_interval` (100ms) и `evictor_tick` (50ms) — никаких реальных
   `sleep(5s)`.

7. Документировать в module-doc:
   - Mutex discipline (no `.await` inside `lock()`).
   - `MIGRATION_SQL` invariant — DDL стабильна; меняем только через новый
     migration helper.
   - Salt invariant — `MCP_REFRESH_SALT` immutable-after-first-boot
     (rotation invalidates all live tokens) — это операционная заметка
     для Task 3 deployment doc, но в коде тут rationale присутствует.

**Out of scope для Task 1**: тест

**Task 3** (`oauth::tests::*`, не `refresh::tests::*`) — он проверяет
сквозную logging policy на уровне `token_handler`, где собирается
request_id + remote_addr. Не добавляй его в `refresh::tests` здесь.

- `refresh::tests::rotate_branch_a_writes_row_and_caches_pair_before_commit`
  — Branch A ordering: cache содержит запись после `rotate`, даже если
  caller "падает" сразу после. Использует
  `debug_hook_cache_put_after_commit` (cfg-gated) чтобы перевернуть
  порядок put/COMMIT в debug-сборке и убедиться, что race материализуется
  — pinning D5 invariant.
- `refresh::tests::reuse_within_window_returns_byte_identical_pair`
  — Branch B: повторный вызов внутри 100ms (`reuse_interval = 100ms` в
  тесте) возвращает идентичный `(access_jwt, refresh_plaintext)`.
- `refresh::tests::reuse_cache_miss_inside_window_returns_invalid_grant_without_family_revoke`
  — Branch B' fail-closed: руками удалить запись из cache внутри окна,
  сделать вторую попытку — `invalid_grant`, family ВСЕ ЕЩЁ имеет
  `revoked=0` строки (не revoke-нута).
- `refresh::tests::replay_outside_window_revokes_full_family_in_one_tx`
  — Branch C атомарность: семья с тремя сиблингами; replay одного
  outside window; assert ВСЕ три помечены `revoked=1` после одного
  COMMIT. Параллельная ротация на сиблинге блокирована (тест запускает
  `tokio::spawn` второго rotate во время первого; второй должен
  дождаться lock и получить `invalid_grant` по уже-revoked строке).
- `refresh::tests::expired_refresh_rejected_without_family_revoke`
  — Branch D: вставить строку с `expires_at = now - 1`, rotate,
  `invalid_grant`, family не revoke-нута.
- `refresh::tests::unknown_token_returns_invalid_grant`
  — Branch E: rotate несуществующего plaintext, `invalid_grant`, лог
  Branch E без `token_hash`.
- `refresh::tests::cross_family_isolation`
  — Две family на один `sub`. Family-revoke на одной не трогает строки
  другой.
- `refresh::tests::migration_is_idempotent`
  — Вызвать `migrate_refresh_tokens` дважды на одном Connection; второй
  вызов — no-op, схема та же.
- `refresh::tests::evictor_evicts_expired_rows`
  — Засеять смесь expired + live строк, запустить `start_evictor` с
  `tick = 50ms`, через 100ms проверить: expired удалены, live на месте.
- `refresh::tests::lru_cap_evicts_oldest`
  — Инициировать `ReuseCache::with_cap(256)`, вставить 300 записей,
  assert: 256 cap соблюдается, oldest 44 эвакуированы.
- `refresh::tests::lru_ttl_expires_within_window`
  — Создать cache с TTL 50ms, вставить, sleep 75ms, GET → miss.
- `refresh::tests::family_revoke_drops_matching_cache_entries`
  — Branch C cleanup: засеять cache 3 записями для одной family,
  вызвать `family_revoke` + `cache.remove_by_family`; assert: все 3
  cache-записи ушли, записи других семей остались.

### Edge cases

- Plaintext пустой → `Err(invalid_grant)` ДО хеширования / SQL.
- `rotated_to` колонка пустая в Branch B (нештатно): защититься
  `.ok_or_else(|| invalid_grant)`; не паниковать.
- `rotated_at` не выставлен в строке с `revoked=1` (drift / тест
  data): трактовать как outside window → Branch C.
- Concurrent rotation на сиблингах одной family: D8 invariant
  гарантирует сериализацию через writer lock; тест
  `replay_outside_window_revokes_full_family_in_one_tx` проверяет.
- Cache poisoning: `Mutex` в `ReuseCache` poisoned → `continue` /
  обращаться к DB как cache miss (Branch B'); тест не обязателен,
  но defensive `match guard` нужен.
- LRU `put` infallible (lru crate API) — единственный side effect:
  evict oldest при cap. Это OK для D5.
- `MIGRATION_SQL` — все `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX
  IF NOT EXISTS`; одна `execute_batch` — atomic rollback на failure.
- `evict_expired` использует параметризованный `now` — НЕ inline
  `strftime`; тест должен иметь возможность контролировать "now"
  (передать `now_override: Option<u64>` параметром либо аналог).

  (a) `cache.put` ДО `COMMIT` в Branch A (D5 invariant — критический
      ordering для закрытия CWE-362, см. **tech-spec §"Decisions" D5**
      и **§"Architecture" Branch A**),
  (b) manual TTL wrapper для `lru::LruCache` (lru 0.12 не имеет
      native TTL — см. ReuseCache описание выше),
  (c) `cache.remove_by_family` cleanup внутри Branch C перед COMMIT.
  Эти три behavior-detail возьми из tech-spec, не из §I.5 sketch.
- **D5 ordering invariant (Branch A)**: внутри одной транзакции
  последовательность строго: `BEGIN IMMEDIATE` → SELECT → UPDATE old →
  INSERT new → `cache.put(old_hash, (jwt, new_plaintext))` → `COMMIT`.
  Если `put` делать ПОСЛЕ `COMMIT`, открывается окно: client получает
  network error → retry → запись уже в DB как revoked, в cache её нет
  → Branch B' fail-closed → клиент потерял сессию. См. tech-spec D5 +
  Architecture Branch A pseudocode.
- **ROLLBACK на каждой ошибке внутри транзакции**: SELECT failed,
  UPDATE failed, INSERT failed, `cache.put` panic (poisoned mutex) —
  любая ветка ошибки до COMMIT должна вызвать `conn.execute("ROLLBACK",
  [])` и вернуть `Err(...)`. Не полагайся на drop — `rusqlite` НЕ
  делает auto-rollback на drop `Connection`; pending транзакция
  останется висеть до следующего statement. Pattern: `let result = (||
  -> Result<_> { ... })(); if result.is_err() { conn.execute("ROLLBACK",
  []).ok(); } else { conn.execute("COMMIT", [])?; } result`.
- Для `BEGIN IMMEDIATE` используй `conn.execute("BEGIN IMMEDIATE",
  [])` затем явный `COMMIT` / `ROLLBACK` (canonical в `payment.rs`).
- `now_secs()` — есть в `oauth/mod.rs`; либо локально:
  `SystemTime::now().duration_since(UNIX_EPOCH).unwrap_or_default()
  .as_secs()`. Project precedent — последний вариант (`escrow.rs`,
  `confirmation_token.rs:119-123`).
- Salt — НЕ хардкодить; принимай `&[u8]` (Task 3 прокинет
  `OAuthState.refresh_salt`). В тестах используй фикс. массив 32 байт.
- `pub mod refresh;` в `oauth/mod.rs` — **ОБЯЗАТЕЛЕН**, добавляется
  именно в этом таске (см. шаг 0 в What-to-do). Без него тесты не
  собираются и smoke red.
- LRU evictor cleanup pair-cache в Branch C: нужно хранить indices
  `family_id -> [old_hash]` либо проходить cache linearly. 256
  максимум — linear scan дёшев. Recommendation: linear scan.
- `ReuseCache` manual TTL: lru 0.12.5 API — `LruCache::put(K, V) ->
  Option<V>` (без TTL). Реализуй TTL вручную: храни `deadline:
  Instant` внутри value-tuple; в `get` проверяй
  `if Instant::now() > entry.deadline { self.inner.pop(key); return
  None; }`. Тест `lru_ttl_expires_within_window` пинит этот контракт.
