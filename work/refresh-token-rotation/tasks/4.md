# Task 4: TestServerBuilder::with_oauth_token + integration test helpers

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:code-writing` — [skills/code-writing/SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Wave-3 единственная задача, целиком отвечающая за расширение тестовой инфраструктуры под рефреш-токен фичу. После Wave 2 у нас:

- В `mcp/src/oauth/mod.rs` появилась ветка `grant_type=refresh_token` в `token_handler` (Task 3).
- `OAuthState` несёт `refresh_store`, `refresh_salt`, `reuse_interval`, `evictor_tick`, `reuse_cache`. Конструктор `OAuthState::new` стал шире (Task 3 уже протолкнул новые аргументы через все 4 продакшен call-site'а и через `mcp/tests/_helpers/mod.rs:111` "thread-through only" — то есть аргументы пробрасываются, но `/oauth/token` в тестовом роутере ещё НЕ смонтирован).

Сейчас же нужно дать интеграционным тестам Wave 4 (`oauth_refresh_e2e.rs`, Task 5) ровно те примитивы, без которых они не напишутся:

1. Включаемый mount `/oauth/token` на тот же tower-stack, что и `/mcp`, через флаг билдера `with_oauth_token(bool)` — без флага роут не появляется (это нужно AC9 `test_anonymous_recall_unchanged`, который проверяет, что наша фича не задевает рекалл-путь и идёт через старый builder без `/oauth/token`).
2. Test-overridable таймеры по Decision 13 — `with_reuse_interval(Duration)` и `with_evictor_tick(Duration)`. Без них AC3/AC4/AC12 заставят тесты делать `sleep(5s)` против реальных constants из прода → флейк и медленный suite. Декларативно: интеграционные тесты Task 5 должны проходить под 2 секунды wall-clock — это AC из tech-spec.
3. Тестовые fixture-функции для всего цикла OAuth:
   - `bootstrap_oauth(&server) -> (code, verifier, redirect_uri)` — отдаёт сырой `authorization_code` + PKCE `code_verifier` + связанный `redirect_uri`, на основе которых Task 5 уже сама постит на `/oauth/token` и получает первый `(access, refresh)` pair. Возвращаем именно сырьё (не уже-вызванный POST), чтобы AC1 (`test_authcode_grant_returns_refresh`) и AC10 (form/JSON parity) могли сами управлять content-type'ом и форматом первого `/oauth/token` запроса.
   - `rotate(server, refresh) -> (String, String)` — крутит refresh, **возвращает обе строки** `(new_access_token, new_refresh_token)`. Раньше в драфте было `String` (только refresh) — round-2 test-reviewer закрыли это minor'ом: AC12 "10 parallel rotations" должен утверждать байт-идентичность ОБЕИХ полей одновременно, иначе регрессия "Branch B перевыдаёт access JWT вместо отдачи кешированной пары" пройдёт молча.
   - `insert_expired_refresh_for_test(state, sub) -> plaintext` — напрямую вставляет в `refresh_tokens` строку с `expires_at` в прошлом и **возвращает plaintext**, который Task 5 пошлёт в Branch D (`test_expired_refresh_rejected_no_family_revoke`, AC5). Без прямого insert'а Task 5 пришлось бы либо ждать 1 год, либо лезть в DB через ad-hoc SQL в самом тесте.

Задача атомарная — после её завершения `mcp/src/test_support.rs` и `mcp/tests/_helpers/mod.rs` других правок по этой фиче НЕ получают (это явное обязательство в tech-spec, чтобы Task 5 не натыкался на конфликты с этой задачей).

Скоуп изменений ограничен ровно двумя файлами: `mcp/tests/_helpers/mod.rs` и `mcp/src/test_support.rs`. Ничего в проде не трогаем.

## What to do

1. Расширить `TestServerBuilder` в `mcp/tests/_helpers/mod.rs`:
   - Добавить три новых поля: `oauth_token: bool`, `reuse_interval: Option<Duration>`, `evictor_tick: Option<Duration>`.
   - `Default::default()` — `oauth_token=false`, оба `Option`'а `None` (fallback на `OAuthState`-дефолты из Task 3).
   - Добавить builder-сеттеры `with_oauth_token(bool)`, `with_reuse_interval(Duration)`, `with_evictor_tick(Duration)` — сигнатуры строго через `mut self` + return `Self` (стиль уже существующих `storage_mode`, `payment_mode`, `sign_memory_cost_micro_usdc`).
2. В `TestServerBuilder::build()`:
   - На месте создания `OAuthState` пробросить переданные `reuse_interval` / `evictor_tick` (если `None` — оставить дефолты `OAuthState`).
   - После того как базовый роутер (`/mcp`, `/api/pending/{...}`, `/api/sign-callback` + bearer middleware + `with_state(state.clone())`) собран, если `self.oauth_token == true` — смержить отдельный `Router` с `/oauth/token` (`post(oauth::token_handler)`) и `with_state(oauth_state.clone())`. Шаблон взять из code-research §I.8.
   - НЕ изменять поведение существующих тестов, которые не вызывают `.with_oauth_token(true)` — `/oauth/token` для них не появляется.
3. Добавить публичные fixture-функции в `mcp/tests/_helpers/mod.rs` (не в `test_support.rs` — они оперируют `TestServer`, а не сырым `McpState`):
   - `pub async fn bootstrap_oauth(server: &TestServer) -> (String, String, String)` — генерирует PKCE `code_verifier` (32 байта рандома → base64url) + `code_challenge` (SHA256 + base64url), вызывает существующий продакшен путь `/oauth/authorize` через `server.app.clone().oneshot(...)` чтобы получить `authorization_code`, и возвращает `(code, verifier, redirect_uri)`. Тест Task 5 сам отправит эти три значения на `/oauth/token`. Использовать существующий test PKCE pattern из `mcp/src/oauth/mod.rs` тестов (`oauth/mod.rs:2022-2099`) как образец того, как генерируется challenge.
   - `pub async fn rotate(server: &TestServer, refresh: &str) -> (String, String)` — постит `grant_type=refresh_token` + `refresh_token=<refresh>` на `/oauth/token`, парсит ответ и возвращает `(access_token, refresh_token)` строки. Если ответ != 200 — паника с body для удобства отладки (тесты Task 5 сами проверяют негативные пути напрямую через статус-коды, эту helper-функцию они используют только на счастливом пути).
   - `pub async fn insert_expired_refresh_for_test(server: &TestServer, sub: &str) -> String` — берёт `server.oauth_state.refresh_store` (lock на `Mutex<Connection>`), INSERT'ит строку в `refresh_tokens`: свежий `family_id = Uuid::new_v4()`, `expires_at = now - 60` (минута назад), `revoked = 0`, `rotated_at = NULL`, `token_hash = blake3(server.oauth_state.refresh_salt + plaintext)`. Возвращает plaintext (43 байта base64url из 32 случайных байт), который Task 5 пошлёт в `/oauth/token` как Branch D. **Mutex `Connection` — освобождать ДО любого `.await`** (CLAUDE.md жёсткое правило).
4. Добавить smoke-тест в этом же файле в самом конце `mcp/tests/_helpers/mod.rs` (или отдельным интеграционным `mcp/tests/_helpers_test_server_mounts_oauth_token.rs` — выбрать формат, который Cargo сам подхватит как `--test` цель):
   - `#[tokio::test] async fn _helpers_test_server_mounts_oauth_token` — собирает `TestServer::builder().with_oauth_token(true).build()`, делает `app.clone().oneshot(POST /oauth/token)` с заведомо-инвалидным body, проверяет: статус НЕ 404 (то есть роут смонтирован). 400/422 — норма, нам важно отличить "роут есть" от "роута нет".
   - Симметричный negative-case: `TestServer::builder().build()` (без `with_oauth_token`) → тот же POST → ожидаем 404. Закрывает обратное направление: без флага роута быть не должно.
5. Если в `mcp/src/test_support.rs` потребуется минимальная helper-функция для генерации валидного `refresh_salt` (`[0xAB; 32]` per code-research §I.8) или мини-обёртка над `mint_jwt` — добавить туда. Иначе `test_support.rs` остаётся как есть (этот файл уже большой; не добавлять туда то, что относится к `TestServer` а не к `McpState`).

## TDD Anchor

Тесты, которые нужно написать ДО реализации. Пишем → запускаем → убеждаемся что падают → пишем код → убеждаемся что проходят.

- `mcp/tests/_helpers/mod.rs::_helpers_test_server_mounts_oauth_token` (или отдельный test target) — `with_oauth_token(true)` → POST `/oauth/token` НЕ возвращает 404; без флага → возвращает 404. Это и есть Verify-smoke этой задачи.
- `mcp/tests/_helpers/mod.rs::_helpers_bootstrap_oauth_returns_usable_code` — `bootstrap_oauth(&server)` отдаёт триплет, по которому первый POST `/oauth/token` с `grant_type=authorization_code` возвращает 200 + ненулевой `access_token` + ненулевой `refresh_token`.
- `mcp/tests/_helpers/mod.rs::_helpers_rotate_returns_pair_both_strings_non_empty` — после `bootstrap_oauth` + первый POST + `rotate(&server, &refresh1)`: возвращённая пара `(access2, refresh2)` — две непустые base64url-/JWT-формы строки, причём `refresh2 != refresh1`. Это контракт API, на который полагается AC12.
- `mcp/tests/_helpers/mod.rs::_helpers_insert_expired_refresh_returns_plaintext_in_db` — после `insert_expired_refresh_for_test(&server, "test-sub")` plaintext хешируется в `blake3(salt+plaintext)` и ровно эта строка находится в SQL'е таблицы `refresh_tokens` с `expires_at < now`.

(Все четыре теста живут в `mcp/tests/_helpers/mod.rs` либо рядом, чтобы прогон `cargo test -p mnemonic-mcp` поднимал их без отдельных Cargo target'ов.)

## Details

**Files:**
- `mcp/tests/_helpers/mod.rs` — расширить `TestServerBuilder` (поля + сеттеры), переписать `build()` для conditional mount `/oauth/token` через `Router::merge`, добавить три fixture-функции (`bootstrap_oauth`, `rotate`, `insert_expired_refresh_for_test`) и smoke-тест. Текущий файл — ~370 строк; ожидаемый прирост — ~120-180 строк.
- `mcp/src/test_support.rs` — минимальные правки: возможно добавить публичный const `TEST_REFRESH_SALT: [u8; 32] = [0xAB; 32]` для удобной переиспользования между `mod.rs` и потенциальными unit-тестами Task 5. Если решено, что соль остаётся локальной приватной const'ой в `_helpers/mod.rs` — `test_support.rs` НЕ трогаем вообще.

**Dependencies:**
- Wave 2 (Task 3) должен быть закончен — `OAuthState` уже несёт `refresh_store`/`refresh_salt`/`reuse_interval`/`evictor_tick`/`reuse_cache`, и call-site в `mcp/tests/_helpers/mod.rs:111` уже пробрасывает их как "thread-through only".
- Task 1 (`mcp/src/oauth/refresh.rs`) должен быть в дереве — `insert_expired_refresh_for_test` использует `refresh::hash_token` и таблицу `refresh_tokens` (миграция уже была применена в Task 1).

**Edge cases:**
- `with_oauth_token(false)` (или не вызвано) → POST `/oauth/token` должен возвращать 404. Это критично для AC9 `test_anonymous_recall_unchanged` в Task 5 — там анонимный путь идёт через builder без OAuth-роута, и тест проверяет, что фича не задела рекалл.
- `bootstrap_oauth` — code должен быть единоразовым: повторный POST `/oauth/token` с тем же `code` должен вернуть ошибку (продакшен поведение). Helper это поведение НЕ перепроверяет — Task 5 проверит сам.
- `insert_expired_refresh_for_test` — если у `sub` уже есть запись в `refresh_tokens`, новая строка должна быть с другим `token_hash` (PK = `token_hash`). Поскольку plaintext генерится свежим `OsRng`, коллизия практически невозможна, но в имени `family_id` важно использовать **новый** `Uuid::new_v4()` чтобы тест AC5 проверял изоляцию семьи (single-row family, family_revoke не задевает других).
- `rotate` — на счастливом пути возвращает пару. На несчастливом (status != 200) — паника с body. Task 5 для негативных кейсов **не** использует `rotate` — там тесты сами шлют POST и проверяют статус-коды напрямую.
- Любой раздел кода, удерживающий `MutexGuard<Connection>`, должен освободить guard до `.await` (CLAUDE.md). Внутри `insert_expired_refresh_for_test`: lock → INSERT → drop guard → return. Никаких `.await` под guard'ом.

**Implementation hints:**
- Для PKCE-генерации в `bootstrap_oauth` использовать `rand::rngs::OsRng` (уже в workspace) + `base64::engine::general_purpose::URL_SAFE_NO_PAD` + `sha2::Sha256`. Если эти пакеты ещё не на сцене у `mcp/Cargo.toml`'s `[dev-dependencies]` — заиспользовать тот же подход, что и существующие OAuth-тесты в `oauth/mod.rs:2022-2099` (там этот паттерн уже выписан, можно копировать стиль 1-в-1).
- Для `/oauth/authorize` call внутри `bootstrap_oauth` — `bootstrap_oauth` собирает request-builder + `server.app.clone().oneshot()`. Не делать прямые SQL-вставки в `issued_codes` — это хрупко и обходит продакшен валидации.
- `rotate` принимает `&str`, чтобы тесты могли передавать как `&String`, так и string slice без `.to_string()`.
- Возвращать `(String, String)` (owned), потому что строки уезжают за пределы лайфтайма ответа.
- `insert_expired_refresh_for_test` — использовать `now - 60` (минута в прошлом) а не `now - 1`, чтобы спасти от потенциального clock skew между измерениями `now()` внутри теста и продакшен-кода Branch D.
- Smoke-тест: можно либо `#[tokio::test]` прямо в `mcp/tests/_helpers/mod.rs` (Cargo автоматически включает в test-binary), либо отдельный `mcp/tests/_helpers_test_server_mounts_oauth_token.rs`. Первый вариант проще — никаких новых файлов, тест живёт рядом с кодом, который проверяет.
- Если решишь добавить отдельный test target, имя файла → `mcp/tests/helpers_smoke.rs` (с прицепленным `mod _helpers`) — `_helpers` лучше держать как private module чтобы не плодить публичные тестовые targets.
