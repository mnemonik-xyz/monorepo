# Task 8: Test Audit

## Required Skills

Перед выполнением задачи загрузи:

## Description

Full-feature test-quality audit across all tests added or modified by Tasks 1-5
of the `refresh-token-rotation` feature. The audit is read-only — no production
code changes. It produces a single Markdown report at
`work/refresh-token-rotation/logs/working/test-audit.md` that the Final Wave
(Task 9 pre-deploy QA) treats as a quality gate input.

The audit answers five questions:

1. **AC coverage.** Does each user-spec AC1-AC13 have at least one
   integration test in `mcp/tests/oauth_refresh_e2e.rs`? Map AC → test
   function names.
2. **Decision coverage.** Do the decisions whose correctness is
   test-observable — D5 (LRU pair-cache idempotency / put-before-COMMIT
   ordering), D8 (single `BEGIN IMMEDIATE` transaction covers detection
   AND family-revoke), D9 (hourly background evictor only, sleeps
   `evictor_tick`) — and risk R6 (DB write failure during rotation is
   retry-safe) each have at least one dedicated test? Map decision/risk
   → test function names.
3. **No real-time waits.** No test in the suite calls
   `tokio::time::sleep` or `std::thread::sleep` with a duration ≥1s.
   Tests for AC3 / AC4 / AC12 and the evictor must rely on D13's
   `reuse_interval = Duration::from_millis(100)` and
   `evictor_tick = Duration::from_millis(50)` overrides — never a real
   5s reuse window.
4. **No litmus-failing tests.** Every test asserts behaviour of
   project code, not of derive macros / library APIs / language
   features. Specifically check the dropped pair from the early draft
   (`token_request_deserializes_both_grants`, `mint_and_hash_roundtrip`)
   did not silently re-appear; flag any new test that only tests
   `serde_derive`, `blake3`, `Uuid`, `LruCache`, or `rusqlite` directly.
5. **No regression.** No tests in the existing scope were deleted or
   weakened. Specifically verify the following remain present and
   unchanged in semantics:
   - tests covering `oauth/mod.rs` lines 2022-2099 (existing OAuth
     handler tests in this hot region);
   - `mcp/tests/auth_allowlist.rs` (every test function name and
     assertion intent preserved);
   - `mcp/tests/anonymous_recall.rs` (every test function name and
     assertion intent preserved).

The audit is read-only — produces a Markdown report only; no commits
to source code.

## What to do

1. Re-read the tech-spec Testing Strategy section (unit + integration)
   and the user-spec AC1-AC13 list to anchor the audit checklist.
2. Enumerate every test added or modified by Tasks 1-5:
   - `mcp/src/oauth/refresh.rs` (Task 1) — `#[cfg(test)] mod tests`
     and any `#[cfg(test)]` helpers.
   - `mcp/src/oauth/mod.rs` (Task 2 + Task 3) — `#[cfg(test)] mod tests`
     additions, including the JWT TTL clamp tests, salt boot tests,
     header tests, logging policy test, reuse-cap-from-state test, and
     the `unknown_grant_type` / `refresh_token_too_long` tests.
   - `mcp/src/test_support.rs` and `mcp/tests/_helpers/mod.rs` (Task 4)
     — smoke `_helpers_test_server_mounts_oauth_token` if present.
   - `mcp/tests/oauth_refresh_e2e.rs` (Task 5) — 13 AC tests +
     `cross_table_mutex_no_starvation` +
     `db_write_failure_during_rotation_returns_500_and_is_retry_safe`.
3. For each of the five audit questions above, walk the enumerated
   tests and record findings. Use direct file:line references and
   exact function names; do not paraphrase test bodies.
4. For AC coverage, build a table: `AC# | acceptance criterion summary
   | test function | file:line`. Flag any AC with zero coverage as
   BLOCKER.
5. For decision / risk coverage, build a table: `D# or R# | what
   correctness property the test must witness | test function |
   file:line`. Flag any uncovered item as BLOCKER for D5/D8/D9/R6.
6. For real-time waits, grep the entire `mcp/` tree for `sleep(` and
   manually inspect every hit; record any duration ≥1s as a finding.
7. For litmus tests, inspect every new test body. If the only
   non-trivial assertion is on third-party-library behaviour (serde
   `Deserialize`, blake3 hashing, `Uuid::new_v4`, `LruCache` ordering,
   `rusqlite` round-trip), flag as a litmus finding. Subsumption by
   AC-bound integration tests is acceptable — note it in the finding.
8. For regression, diff (mentally or via `git diff main -- <file>`)
   the three named scopes against `main` at the wave-5 checkpoint;
   confirm function-name set unchanged and assertion intent
   preserved.
9. Write the report. Use the structure under Details → Report
   structure below.
10. Stop. Do not modify production code or tests as part of this
    task — findings flow back to whichever wave is responsible for
    the fix.

**Report structure** (use these exact H2 headings so downstream
tooling can parse it):

```
# Test Audit — refresh-token-rotation

## Scope
Tasks 1-5; files audited; commit SHA of the wave-5 checkpoint.

## AC Coverage
Table: AC# | summary | test function | file:line | status (COVERED / MISSING).

## Decision & Risk Coverage
Table: D#/R# | property under test | test function | file:line |
status (COVERED / MISSING).

## Real-time Waits
List of every `sleep(...)` call in audited tests with duration. Pass
if all <1s.

## Litmus Tests
List of any test whose only meaningful assertion is on third-party
behaviour. Empty list = PASS.

## Regression Check
For each of the three regression scopes: list of test function names
present in `main` vs. wave-5 checkpoint; any delta is a finding.

## Findings
Numbered list. Each finding: severity (BLOCKER / MINOR / INFO),
description, file:line, suggested fix owner (which task to re-open).

## Verdict
One of: PASS | PASS WITH MINOR | BLOCKER.
One-paragraph summary for the Final Wave reviewer.
```

**Dependencies:** Task 5 must be `done` before this task starts —
the audit cannot run until the integration tests are written. Tasks
6 (Code Audit) and 7 (Security Audit) run in parallel with this task
in Wave 5; no inter-auditor coordination required.

**Edge cases:**
- A test exists for an AC but its assertion is wrong (e.g. asserts
  presence of a field without asserting its value). Flag as MINOR
  with the specific assertion that needs strengthening — do not
  count as MISSING.
- A decision is tested transitively by an AC integration test (e.g.
  D5 idempotency is exercised by the AC12 ten-parallel-rotations
  test). Count as COVERED but note the transitive coverage; recommend
  a dedicated unit test if the transitive coverage hides the
  decision's specific invariant (e.g. put-before-COMMIT ordering).
- A regression scope file moved in the wave (renamed, content
  preserved). Treat the move as INFO, not a regression, but record
  the new path so reviewers can re-run their own diffs.
- An audited test exists but is `#[ignore]`d. Treat as MISSING for
  the corresponding AC / decision / risk.

**Implementation hints:**
- Use `git diff main...HEAD -- mcp/tests/auth_allowlist.rs
  mcp/tests/anonymous_recall.rs mcp/src/oauth/mod.rs` to drive the
  regression check; trust the diff, do not eyeball.
- The Wave-1 + Wave-2 unit tests listed in tech-spec Testing
  Strategy → Unit tests are the authoritative D5 / D8 / D9 / R6
  coverage source. Cross-reference the test names you find in
  source against that list.
- The two cross-cutting integration tests
  (`cross_table_mutex_no_starvation`,
  `db_write_failure_during_rotation_returns_500_and_is_retry_safe`)
  satisfy D8 race-resilience and R6 retry-safety respectively;
  confirm both are present.
- AC10 has a structural-equality nuance — independent rotations
  return distinct access JWTs by design (D5 idempotency is
  per-rotation, not across rotations). If the AC10 test asserts
  byte-equality across two independent rotations, that's a test
  bug, not a coverage issue — flag MINOR.
- AC12 must assert byte-identical equality on BOTH `access_token`
  AND `refresh_token` across all 10 parallel responses. A
  single-field assertion is a MINOR finding (would silently pass a
  regression where Branch B re-mints only the JWT).
- The `logging_policy_no_plaintext_no_hash_across_branches` unit
  test transitively covers D14 — note in the report but D14 is not
  part of the required D5/D8/D9/R6 coverage table.
- Litmus filter is strict: a test that round-trips a `TokenRequest`
  through serde with both content-types is a LITMUS finding if it
  only asserts deserialization succeeded; it is NOT a finding if it
  asserts the post-parse dispatch behaviour (`grant_type` selects
  the correct branch). Inspect the assertion, not the setup.
