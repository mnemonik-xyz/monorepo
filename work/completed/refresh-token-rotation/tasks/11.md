# Task 11: Prod deploy (gated by Task 10)

## Required Skills

Перед выполнением задачи загрузи:
- `/skill:deploy-pipeline` — [skills/deploy-pipeline/SKILL.md](~/.claude/skills/deploy-pipeline/SKILL.md)

## Description

Promote the refresh-token-rotation feature to production on `mcp.mnemonik.xyz` after the Task 10 R1 empirical gate signs off with GO. This task tags a release, lets the existing `release.yml` workflow build and ship the artifacts, then performs the VPS deploy per the documented process.

**Only execute if Task 10 reports GO.** A NO-GO outcome from Task 10 means Claude.ai did not survive a forced JWT expiry under refresh-token rotation; in that case this task must STOP without touching prod. The Task 10 report MUST be read first and its verdict confirmed before any tag is pushed.

Two operational constraints matter here:

1. Prod must run with the **1h JWT TTL preserved** — `MCP_JWT_TTL_SECS` is a Task 10 dev knob only. On prod it must be unset (default 3600) or explicitly `3600`. Any other value is a misconfiguration and must be corrected before the deploy is considered done.
2. Prod must run with a **fresh, prod-only `MCP_REFRESH_SALT`**. Reusing the dev salt generated for Task 10 would couple prod tokens to a secret that already lived on the dev box and in Task 10 logs/notes. Generate a new salt for prod (`openssl rand -base64 32`, ≥32 bytes after decode) and store it in the prod secret store before the release tag is pushed.

The `refresh_tokens` table migration runs at server startup via the idempotent `CREATE TABLE IF NOT EXISTS` in `refresh::migrate_refresh_tokens`. Verifying it appears on prod SQLite after first boot is the migration-applied check.

## What to do

1. **Verify Task 10 GO verdict.** Read the Task 10 report at `work/refresh-token-rotation/logs/working/r1-empirical-gate-report.md` (the file path written by Task 10). Confirm the verdict is GO. If NO-GO — STOP. Do not tag, do not deploy. Note the STOP in the prod-deploy report and exit.
2. **Pre-flight prod env audit.** Confirm with the operator (or by reading the prod env file on the VPS via the documented access path) that:
   - `MCP_JWT_TTL_SECS` is unset OR explicitly equals `3600` on the prod environment.
   - `MCP_REFRESH_SALT` is set on prod to a freshly generated value (NOT the dev-Task-10 salt). If it is not set yet, generate one with `openssl rand -base64 32`, validate that it decodes to ≥32 bytes, and install it in the prod secret store before tagging.
3. **Merge the feature branch to `main`.** Tags are cut from `main` (per `architecture.md`); the feature branch MUST be merged BEFORE running the release tag, otherwise `git pull origin main` on the VPS will not see the new commit and the deploy will ship the wrong artifact. If the branch is not merged yet, STOP and merge first.
4. **Bump versions.** Update `mcp/Cargo.toml` package version from `0.2.4` to `0.2.5` (and matching `Cargo.lock`); commit on `main`. Without this bump, the `release.yml` cross-compile produces tarballs named `mnemonic-mcp-0.2.4-*.tar.gz` under a `v0.2.5` GitHub Release — confusing for users.

5. **Tag the release.** Cut tag `v0.2.5` on the bumped commit on `main` (per `deployment.md::Pre-Deploy Checklist` tag convention — `v{MAJOR}.{MINOR}.{PATCH}` semver). Push the tag. The `release.yml` workflow cross-compiles the Rust binary for the host targets (x86_64-linux + aarch64-darwin) and attaches the artifacts to the GitHub Release. **No Docker image is built** — `release.yml` has zero Docker steps; the Docker image mentioned in `deployment.md`'s component table is a separate aspiration not wired into `release.yml`. The prod deploy is binary-on-VPS only.
5. **Wait for release.yml to complete green.** If it fails, STOP and write the failure mode into the prod-deploy report. Do not deploy a partially-built artifact.
6. **Deploy to `mcp.mnemonik.xyz`.** Follow `deployment.md::VPS Deploy Process` step-by-step. Pull the released binary on the VPS (`git pull origin main` + `cargo build --release` or the documented artifact-pull path), swap it in, restart the `mnemonic-mcp` systemd service.
7. **Confirm prod boot.** Tail prod logs (`journalctl -u mnemonic-mcp --since "5 minutes ago"`) and confirm clean startup — specifically that `MCP_REFRESH_SALT` validation passes (no boot-abort), `OnceLock<u64>` for `MCP_JWT_TTL_SECS` seeds to 3600, and `refresh::start_evictor` spawns.
8. **Verify the migration applied.** On the prod SQLite file, confirm the `refresh_tokens` table exists: `sqlite3 /home/claude/data/attestations.db ".schema refresh_tokens"` returns the columns defined in tech-spec Data Models. Idempotent `CREATE TABLE IF NOT EXISTS` means re-running boot is safe.
9. **Write the deploy report.** Capture: Task 10 verdict, merge-to-main confirmation (commit SHA), tag pushed, release.yml run URL + status, deploy timestamp, prod env confirmation (`MCP_JWT_TTL_SECS` state, `MCP_REFRESH_SALT` set + fresh), migration verification output, any incidents. Save to `work/refresh-token-rotation/logs/working/prod-deploy-report.md`.
10. **Hand off to Task 12.** Task 12 (post-deploy verification) executes the live AVP against the running prod deployment.

## Details

**Files:**

- `work/refresh-token-rotation/logs/working/prod-deploy-report.md` (new) — deploy execution report. Fields per step 9.

**Dependencies:**
- Task 10 GO verdict (hard prerequisite — NO-GO ⇒ STOP).
- `release.yml` workflow (existing, triggered by `v*` tag push per `CLAUDE.md`).
- `deployment.md::VPS Deploy Process` — read this first; the deploy mechanics are not duplicated here.

**Edge cases:**
- Task 10 verdict is NO-GO → STOP. Do not tag. Write the STOP into the deploy report and exit.
- Feature branch not yet merged to `main` → STOP, merge first. `git pull origin main` on the VPS would otherwise miss the feature commit and ship the previous release.
- `MCP_JWT_TTL_SECS` is set to something other than `3600` on prod → STOP, unset (or correct to `3600`) before tagging. A leftover dev value would silently re-create the Task 10 short-TTL window in prod.
- `MCP_REFRESH_SALT` not set on prod → server aborts boot (D2 boot validation). Generate and install before tagging.
- `MCP_REFRESH_SALT` set to the same value as Task 10's dev salt → STOP, regenerate. Reusing dev secrets in prod violates secret hygiene.
- `release.yml` workflow fails after tag push → STOP, investigate, do not deploy. Do not retag — cut a follow-up patch tag if needed.
- `refresh_tokens` table missing on prod after first boot → migration did not run; check `refresh::migrate_refresh_tokens` was wired in `main.rs::run_http` (Task 3 deliverable) and that the boot logs do not show a swallowed error.

**Implementation hints:**
- Generate the prod salt with `openssl rand -base64 32` per `.env.example` recipe (Decision 2 in tech-spec).
- The deploy mechanics — binary pull, systemd service restart, health probe — live in `deployment.md::VPS Deploy Process`; follow that doc verbatim rather than re-deriving steps here. The systemd unit is `mnemonic-mcp` (use `journalctl -u mnemonic-mcp` for log tailing).
- The prod SQLite file is at `/home/claude/data/attestations.db` (per `deployment.md`). Use the full path with `sqlite3` — the binary requires the DB path as the first arg before any dot-commands.
- `release.yml` produces a Rust binary attached to the GitHub Release, not a Docker image. Do not look for a Docker pull step in the deploy procedure.
- This task does not run the live AVP (curl checks, real Cursor/Claude.ai sessions, prod log tailing for `refresh_rotation` / `family_revoke` events). That is Task 12.
- No rollback rehearsal is required for this task — rollback per tech-spec is "revert the tag with no data migration to undo" (Solution section). Document the rollback procedure in the deploy report only if an incident occurs during this task.
