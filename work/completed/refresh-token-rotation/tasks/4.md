## Description

Wave-3 единственная задача, целиком отвечающая за расширение тестовой инфраструктуры под рефреш-токен фичу.

**Pre-condition gate (CRITICAL — run BEFORE writing any code):**

```bash
cargo build -p mnemonic-mcp
```

Если эта команда падает с ошибкой "`mcp/src/oauth/refresh.rs` not found" или "`OAuthState` missing field `refresh_store`/`refresh_salt`/`reuse_interval`/`evictor_tick`/`reuse_cache`" — это значит Wave 1 (Task 1) или Wave 2 (Task 3) ещё не выполнены или сломаны. **STOP и поднять у юзера**, не пытаться писать код задачи 4 — все хелперы этой задачи опираются на `refresh::hash_refresh_token`, `refresh::ReuseCache`, поля `OAuthState`, которых без Tasks 1–3 в дереве просто нет.

После Wave 2 у нас:

- В `mcp/src/oauth/mod.rs` появилась ветка `grant_type=refresh_token` в `token_handler` (Task 3).
- `OAuthState` несёт `refresh_store: Arc<Mutex<rusqlite::Connection>>`, `refresh_salt: Vec<u8>`, `reuse_interval: Duration`, `evictor_tick: Duration`, `reuse_cache: Arc<refresh::ReuseCache>`. По Decision 6 (commit `d4db8bd`) `OAuthState::new` открывает **второй** `rusqlite::Connection` на том же SQLite-файле, что и `McpState.store` — это значит, что в `TestServerBuilder::build()` нужно создать отдельную Connection (для тестов — `:memory:` или временный файл; код-research §I.8 показывает паттерн) и передать её как `Arc::new(Mutex::new(conn))` в `OAuthState::new`.
- Конструктор `OAuthState::new` стал шире (Task 3 уже протолкнул новые аргументы через все 4 продакшен call-site'а и через `mcp/tests/_helpers/mod.rs:111` "thread-through only" — то есть аргументы пробрасываются, но `/oauth/token` и `/oauth/authorize` в тестовом роутере ещё НЕ смонтированы).

Сейчас же нужно дать интеграционным тестам Wave 4 (`oauth_refresh_e2e.rs`, Task 5) ровно те примитивы, без которых они не напишутся:

1. Включаемый mount **обоих** OAuth-роутов — `/oauth/token` И `/oauth/authorize` (GET + POST) — на тот же tower-stack, что и `/mcp`, через флаг билдера `with_oauth_token(bool)` — без флага роуты не появляются (это нужно AC9 `test_anonymous_recall_unchanged`, который проверяет, что наша фича не задевает рекалл-путь и идёт через старый builder без OAuth-роутов). **Mount именно обоих**, потому что `bootstrap_oauth` (см. ниже) гоняет реальный продакшен-флоу через `/oauth/authorize` чтобы получить `authorization_code` — production parity, минимум test-only кода.
2. Test-overridable таймеры по Decision 13 — `with_reuse_interval(Duration)` и `with_evictor_tick(Duration)`. Без них AC3/AC4/AC12 заставят тесты делать `sleep(5s)` против реальных constants из прода → флейк и медленный suite. Декларативно: интеграционные тесты Task 5 должны проходить под 2 секунды wall-clock — это AC из tech-spec.
3. Тестовые fixture-функции для всего цикла OAuth:
   - `bootstrap_oauth(&server) -> (code, verifier, redirect_uri)` — отдаёт сырой `authorization_code` + PKCE `code_verifier` + связанный `redirect_uri`, на основе которых Task 5 уже сама постит на `/oauth/token` и получает первый `(access, refresh)` pair. Возвращаем именно сырьё (не уже-вызванный POST), чтобы AC1 (`test_authcode_grant_returns_refresh`) и AC10 (form/JSON parity) могли сами управлять content-type'ом и форматом первого `/oauth/token` запроса. **Реализация:** прогонять реальный продакшен-флоу через `server.app.clone().oneshot(GET /oauth/authorize-init)` + `POST /oauth/authorize`, не миновать `OAuthState` через прямой insert в `issued_codes` (хрупко, обходит продакшен валидации). Этот путь требует, чтобы `with_oauth_token(true)` смонтировало `/oauth/authorize` (см. пункт 1) — production parity.
   - `rotate(server, refresh) -> (String, String)` — крутит refresh, **возвращает обе строки** `(new_access_token, new_refresh_token)`. Раньше в драфте было `String` (только refresh) — round-2 test-reviewer закрыли это minor'ом: AC12 "10 parallel rotations" должен утверждать байт-идентичность ОБЕИХ полей одновременно, иначе регрессия "Branch B перевыдаёт access JWT вместо отдачи кешированной пары" пройдёт молча.
   - `insert_expired_refresh_for_test(&server) -> (String, String)` — напрямую вставляет в `refresh_tokens` строку с `expires_at` в прошлом и **возвращает кортеж `(plaintext, family_id)`**. Plaintext Task 5 пошлёт в Branch D (`test_expired_refresh_rejected_no_family_revoke`, AC5); `family_id` Task 5 использует, чтобы утверждать `family_has_unrevoked_rows(&server, &family_id) == true` после получения 400 (то есть expired-refresh НЕ должен задеть остальные строки семьи). Без прямого insert'а Task 5 пришлось бы либо ждать 1 год, либо лезть в DB через ad-hoc SQL в самом тесте. **Внутренне** функция вычисляет hash через `refresh::hash_refresh_token(server.oauth_state.refresh_salt.as_slice(), &plaintext)` — это **публичный** символ модуля Task 1 (см. code-research.md §I.5 line 89: `pub fn hash_refresh_token(salt: &[u8], plaintext: &str) -> String`). Если cross-check показывает, что Task 1 переименовал функцию (например, в `hash_token`) — использовать имя из Task 1 фактически (этот task НЕ должен ходить в Task 1 чтобы переименовывать — берём имя как есть в дереве).
   - `family_has_unrevoked_rows(&server, family_id: &str) -> bool` — query helper для AC5: возвращает `true`, если в `refresh_tokens` есть хотя бы одна строка с указанным `family_id` где `revoked = 0`. Task 5 (`test_expired_refresh_rejected_no_family_revoke`) использует этот хелпер после `POST /oauth/token` с expired refresh, чтобы убедиться, что Branch D **не** запустил family-revoke. Реализация — SELECT с lock на `Mutex<Connection>`, lock освобождать ДО `.await` (как и в `insert_expired_refresh_for_test`).

Задача атомарная — после её завершения `mcp/src/test_support.rs` и `mcp/tests/_helpers/mod.rs` других правок по этой фиче НЕ получают (это явное обязательство в tech-spec, чтобы Task 5 не натыкался на конфликты с этой задачей).

Скоуп изменений ограничен ровно двумя файлами: `mcp/tests/_helpers/mod.rs` и `mcp/src/test_support.rs`. Ничего в проде не трогаем.

Передать в `OAuthState::new` как `Arc::new(Mutex::new(conn))`. Сразу же вызвать `mnemonic_mcp::oauth::refresh::migrate_refresh_tokens(&conn)` чтобы таблица существовала.

   - После того как базовый роутер (`/mcp`, `/api/pending/{...}`, `/api/sign-callback` + bearer middleware + `with_state(state.clone())`) собран, если `self.oauth_token == true` — смержить отдельный `Router` с **двумя** OAuth-роутами и `with_state(oauth_state.clone())`:
     - `POST /oauth/token` → `oauth::token_handler`
     - `GET /oauth/authorize` → `oauth::authorize_init_handler` (bootstrap, отдаёт challenge JSON)
     - `POST /oauth/authorize` → `oauth::authorize_handler` (принимает COSE_Sign1, выдаёт `authorization_code`)
     Это нужно потому, что `bootstrap_oauth` гоняет реальный продакшен-флоу через `/oauth/authorize` (production parity, см. Finding 4 в decisions). Шаблон mount'а взять из code-research §I.8 и из продакшен-роутера в `main.rs` где эти три роута уже смонтированы side-by-side.
   - НЕ изменять поведение существующих тестов, которые не вызывают `.with_oauth_token(true)` — ни `/oauth/token`, ни `/oauth/authorize` для них не появляются.
3. Добавить публичные fixture-функции в `mcp/tests/_helpers/mod.rs` (не в `test_support.rs` — они оперируют `TestServer`, а не сырым `McpState`):
   - `pub async fn bootstrap_oauth(server: &TestServer) -> (String, String, String)` — генерирует PKCE `code_verifier` (32 байта рандома → base64url) + `code_challenge` (SHA256 + base64url), генерит свежий Ed25519 keypair, делает `GET /oauth/authorize?...` чтобы получить challenge bytes, подписывает их COSE_Sign1 с этим keypair, делает `POST /oauth/authorize` с подписью и в ответ получает `authorization_code`. Возвращает `(code, verifier, redirect_uri)`. Тест Task 5 сам отправит эти три значения на `/oauth/token`. Использовать существующий test PKCE + COSE pattern из `mcp/src/oauth/mod.rs` тестов (`oauth/mod.rs:2022-2099`) как образец того, как генерируется challenge и формируется подпись. Прямо в production-флоу — никаких прямых SQL-insert'ов в `issued_codes`.
   - `pub async fn rotate(server: &TestServer, refresh: &str) -> (String, String)` — постит `grant_type=refresh_token` + `refresh_token=<refresh>` на `/oauth/token`, парсит ответ и возвращает `(access_token, refresh_token)` строки. Если ответ != 200 — паника с body для удобства отладки (тесты Task 5 сами проверяют негативные пути напрямую через статус-коды, эту helper-функцию они используют только на счастливом пути).
   - `pub async fn insert_expired_refresh_for_test(server: &TestServer) -> (String, String)` — берёт `server.oauth_state.refresh_store` (lock на `Mutex<Connection>`), INSERT'ит строку в `refresh_tokens`: свежий `family_id = Uuid::new_v4().to_string()`, фиксированный `sub = "expired-refresh-test"`, `expires_at = now - 60` (минута назад), `revoked = 0`, `rotated_at = NULL`, `token_hash = mnemonic_mcp::oauth::refresh::hash_refresh_token(server.oauth_state.refresh_salt.as_slice(), &plaintext)`. **Возвращает кортеж `(plaintext, family_id)`** — оба значения нужны Task 5 (plaintext для POST на `/oauth/token`, family_id для последующего `family_has_unrevoked_rows`). **Если фактическое имя функции в Task 1 отличается от `hash_refresh_token`** (например, `hash_token`) — использовать имя из дерева; не править Task 1, не угадывать. **Mutex `Connection` — освобождать ДО любого `.await`** (CLAUDE.md жёсткое правило).

AND revoked = 0`, возвращает `true` если есть хотя бы одна строка. Lock на `Mutex<Connection>` освобождать ДО `.await` (но эта функция целиком sync внутри — нет `.await` после lock'а).
4. Добавить smoke-тест в этом же файле в самом конце `mcp/tests/_helpers/mod.rs` (или отдельным интеграционным `mcp/tests/_helpers_test_server_mounts_oauth_token.rs` — выбрать формат, который Cargo сам подхватит как `--test` цель):

## TDD Anchor

Тесты, которые нужно написать ДО реализации. Пишем → запускаем → убеждаемся что падают → пишем код → убеждаемся что проходят.

- `mcp/tests/_helpers/mod.rs::_helpers_test_server_mounts_oauth_token` (или отдельный test target) — `with_oauth_token(true)` → POST `/oauth/token` НЕ возвращает 404 И GET `/oauth/authorize` НЕ возвращает 404; без флага → оба возвращают 404. Это и есть Verify-smoke этой задачи.
- `mcp/tests/_helpers/mod.rs::_helpers_bootstrap_oauth_returns_usable_code` — `bootstrap_oauth(&server)` отдаёт триплет, по которому первый POST `/oauth/token` с `grant_type=authorization_code` возвращает 200 + ненулевой `access_token` + ненулевой `refresh_token`.
- `mcp/tests/_helpers/mod.rs::_helpers_rotate_returns_pair_both_strings_non_empty` — после `bootstrap_oauth` + первый POST + `rotate(&server, &refresh1)`: возвращённая пара `(access2, refresh2)` — две непустые base64url-/JWT-формы строки, причём `refresh2 != refresh1`. Это контракт API, на который полагается AC12.
- `mcp/tests/_helpers/mod.rs::_helpers_insert_expired_refresh_returns_plaintext_and_family_id` — после `let (plaintext, family_id) = insert_expired_refresh_for_test(&server).await;`:
  - `plaintext` непустой, длина соответствует 32 байтам base64url (43 символа).
  - `family_id` — валидный UUID-форма (хекс с дефисами).
  - В таблице `refresh_tokens` существует ровно одна строка с этим `family_id`, `expires_at < now()`, `revoked = 0`, и `token_hash` равен `mnemonic_mcp::oauth::refresh::hash_refresh_token(salt, &plaintext)`.
- `mcp/tests/_helpers/mod.rs::_helpers_family_has_unrevoked_rows` — после `insert_expired_refresh_for_test` → `family_has_unrevoked_rows(&server, &family_id) == true`. После UPDATE строки на `revoked = 1` через прямой SQL (внутри теста) → `family_has_unrevoked_rows(...) == false`. После UPDATE обратно на `revoked = 0` → снова `true`.

(Все пять тестов живут в `mcp/tests/_helpers/mod.rs` либо рядом, чтобы прогон `cargo test -p mnemonic-mcp` поднимал их без отдельных Cargo target'ов.)

## Details

**Files:**
- `mcp/tests/_helpers/mod.rs` — расширить `TestServerBuilder` (поля + сеттеры + создание второй Connection per D6), переписать `build()` для conditional mount **обоих** OAuth-роутов (`/oauth/token`, `/oauth/authorize` GET+POST) через `Router::merge`, добавить четыре fixture-функции (`bootstrap_oauth`, `rotate`, `insert_expired_refresh_for_test -> (String, String)`, `family_has_unrevoked_rows`) и smoke-тесты. Текущий файл — ~370 строк; ожидаемый прирост — ~180-260 строк.
- `mcp/src/test_support.rs` — минимальные правки: возможно добавить публичный const `TEST_REFRESH_SALT: [u8; 32] = [0xAB; 32]` для удобной переиспользования между `mod.rs` и потенциальными unit-тестами Task 5. Если решено, что соль остаётся локальной приватной const'ой в `_helpers/mod.rs` — `test_support.rs` НЕ трогаем вообще.

**Dependencies:**
- Pre-condition: `cargo build -p mnemonic-mcp` зелёный (Tasks 1–3 в дереве). Если падает — STOP, поднять у юзера, не править файлы.
- Wave 2 (Task 3) должен быть закончен — `OAuthState` уже несёт `refresh_store: Arc<Mutex<rusqlite::Connection>>`, `refresh_salt: Vec<u8>`, `reuse_interval: Duration`, `evictor_tick: Duration`, `reuse_cache: Arc<refresh::ReuseCache>`. Call-site в `mcp/tests/_helpers/mod.rs:111` уже пробрасывает их как "thread-through only".
- Task 1 (`mcp/src/oauth/refresh.rs`) должен быть в дереве — `insert_expired_refresh_for_test` использует `refresh::hash_refresh_token(salt, plaintext)` (фактическое имя сверить cross-check'ом с `mcp/src/oauth/refresh.rs`) и таблицу `refresh_tokens` (миграция применяется в `TestServerBuilder::build()` через `migrate_refresh_tokens(&conn)` сразу после открытия второй Connection — D6).

**Edge cases:**
- `with_oauth_token(false)` (или не вызвано) → POST `/oauth/token` И GET/POST `/oauth/authorize` должны возвращать 404. Это критично для AC9 `test_anonymous_recall_unchanged` в Task 5 — там анонимный путь идёт через builder без OAuth-роутов, и тест проверяет, что фича не задела рекалл.
- `bootstrap_oauth` — code должен быть единоразовым: повторный POST `/oauth/token` с тем же `code` должен вернуть ошибку (продакшен поведение). Helper это поведение НЕ перепроверяет — Task 5 проверит сам.
- `insert_expired_refresh_for_test` — каждый вызов генерит свежий `Uuid::new_v4()` для `family_id` (изоляция семьи: family_revoke не задевает других). Плэйнтекст — свежий `OsRng`, PK-коллизия по `token_hash` практически невозможна. Возвращаемая пара `(plaintext, family_id)` — owned `String`s.
- `family_has_unrevoked_rows` — на пустой семье (нет строк с `family_id`) возвращает `false`. На семье где есть строки но все `revoked = 1` — тоже `false`. Только если есть хотя бы одна `revoked = 0` — `true`.
- `rotate` — на счастливом пути возвращает пару. На несчастливом (status != 200) — паника с body. Task 5 для негативных кейсов **не** использует `rotate` — там тесты сами шлют POST и проверяют статус-коды напрямую.
- Любой раздел кода, удерживающий `MutexGuard<Connection>`, должен освободить guard до `.await` (CLAUDE.md). Внутри `insert_expired_refresh_for_test` и `family_has_unrevoked_rows`: lock → SQL → drop guard → return. Никаких `.await` под guard'ом.

**Implementation hints:**
- Для PKCE-генерации в `bootstrap_oauth` использовать `rand::rngs::OsRng` (уже в workspace) + `base64::engine::general_purpose::URL_SAFE_NO_PAD` + `sha2::Sha256`. Для подписи COSE_Sign1 над challenge bytes — `ed25519-dalek` (уже в workspace для основной фичи). Если этих пакетов ещё нет в `mcp/Cargo.toml`'s `[dev-dependencies]` — заиспользовать тот же подход, что и существующие OAuth-тесты в `oauth/mod.rs:2022-2099` (там этот паттерн уже выписан, можно копировать стиль 1-в-1).
- Для `/oauth/authorize` call внутри `bootstrap_oauth` — `bootstrap_oauth` собирает GET request-builder для challenge fetch, парсит JSON challenge, подписывает COSE_Sign1, собирает POST request-builder, посылает обоих через `server.app.clone().oneshot()`. Не делать прямые SQL-вставки в `issued_codes` — это хрупко и обходит продакшен валидации.
- `rotate` принимает `&str`, чтобы тесты могли передавать как `&String`, так и string slice без `.to_string()`.
- Возвращать `(String, String)` (owned), потому что строки уезжают за пределы лайфтайма ответа.
- `insert_expired_refresh_for_test` — использовать `now - 60` (минута в прошлом) а не `now - 1`, чтобы спасти от потенциального clock skew между измерениями `now()` внутри теста и продакшен-кода Branch D. Возвращать `(plaintext, family_id)` — оба `String` owned.
- `family_has_unrevoked_rows` — простой `SELECT COUNT(*) FROM refresh_tokens WHERE family_id = ?1 AND revoked = 0`. Можно через `conn.query_row` + проверка `count > 0`.
- D6 (commit `d4db8bd`) — `OAuthState::new` ожидает свой собственный `Arc<Mutex<rusqlite::Connection>>` на тот же SQLite-файл, что и `McpState.store`. В тестах: либо `Connection::open_in_memory()` (но это будет в **разной** памяти от `McpState.store`, поэтому WAL-shared-file не воспроизводится — для интеграционных тестов hash-at-rest это окей, рефреш-таблица живёт отдельно), либо общий `tempfile::NamedTempFile` для обоих. Выбрать тот вариант, который пропускают тесты Task 5 (Task 5 НЕ полагается на cross-table consistency между attestations и refresh_tokens — они изолированы).
- Smoke-тест: можно либо `#[tokio::test]` прямо в `mcp/tests/_helpers/mod.rs` (Cargo автоматически включает в test-binary), либо отдельный `mcp/tests/_helpers_test_server_mounts_oauth_token.rs`. Первый вариант проще — никаких новых файлов, тест живёт рядом с кодом, который проверяет.
- Если решишь добавить отдельный test target, имя файла → `mcp/tests/helpers_smoke.rs` (с прицепленным `mod _helpers`) — `_helpers` лучше держать как private module чтобы не плодить публичные тестовые targets.
- **Cross-check `hash_refresh_token` имени в Task 1:** перед написанием `insert_expired_refresh_for_test` открыть `mcp/src/oauth/refresh.rs` и найти фактическое имя hash-функции (`hash_refresh_token` per code-research §I.5 line 89). Если оно другое — использовать как есть в дереве, не править Task 1.
