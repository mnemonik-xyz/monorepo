# Task 7: Core — POST_V1 schema + public-artifacts and timeline queries

## Required Skills

- `/skill:code-writing` — [SKILL.md](~/.claude/skills/code-writing/SKILL.md)

## Description

Backend foundation in `core/` (zero refs to `mcp/`; no payment methods; parameterized
SQL only; TurboQuant bit width unchanged). A blog post is a signed PUBLIC attestation
— reuse the existing CBOR/COSE_Sign1/blake3 pipeline; do not build a parallel store.

## What to do

- Define a POST representation: a dedicated `POST_V1` schema or a tagged attestation
  (`tag: post`) carrying title, slug, body_markdown, author/agent, published_at.
  Record the choice in decisions.md.
- Add storage queries in `core/src/storage/sqlite.rs`:
  - public-artifacts list — `visibility = public` ONLY (reuse `SEARCH_SQL_CROSS_OWNER_VIS`, `core/src/storage/sqlite.rs:116`); never owner-private.
  - attestation timeline aggregation — counts bucketed by day, on-node vs on-chain by `write_mode`.
  - optional `blog_posts` projection table (slug PK index/ordering), idempotent `CREATE TABLE IF NOT EXISTS`.
- Expose via storage traits as needed; keep `rusqlite::Connection` `!Send` discipline.

## TDD Anchor

- public-artifacts query returns only `visibility=public` rows (seed private + public; private never returned).
- timeline aggregation buckets/counts correct across ranges + write_mode split.
- POST round-trips through canonical CBOR + COSE_Sign1 + blake3.
- migration idempotent (run twice).

## Acceptance Criteria

- [ ] POST representation chosen + documented; round-trips and verifies
- [ ] public-artifacts query is public-only
- [ ] timeline aggregation correct
- [ ] migration idempotent
