# Task 10: Code Audit (Audit Wave)

## Required Skills

Before starting, load: `/skill:code-reviewing` — [SKILL.md](/Users/syi/src/sessions/2/.claude/skills/code-reviewing/SKILL.md)

## Description

Holistic code-quality audit of all feature code produced by tasks 1-9. This is **analysis only — no code changes**. The reviewer reads every source file written or modified during the feature, evaluates it against project conventions and the architectural rules in `CLAUDE.md`, and writes a finding-by-finding report appended to `work/mnemonic-integrations/decisions.md`.

The audit runs in parallel with Tasks 11 (Security Audit) and 12 (Test Audit) — coordinate scope so this task focuses on code quality and architecture (not security or test pyramid). Findings are advisory; deferred fixes are logged in `decisions.md` and triaged before pre-deploy QA.

## What to do

1. Read all files listed in **Context Files** below. Build a mental model of what each task produced.
2. Walk each focus area and produce findings. Each finding has: `severity` (critical / major / minor), `area`, `file:line`, `issue`, `recommendation`.
3. Verify the architectural rules section (see Acceptance Criteria) and mark each rule pass / fail with evidence.
4. Append a `## Code Audit (Task 10)` section to `work/mnemonic-integrations/decisions.md`. Group findings by focus area, list rule-verification results last.
5. If a finding is critical and blocks deploy, flag it explicitly so the pre-deploy QA gate (Task 12 / 14) picks it up.

### Focus areas

- **Streamable HTTP transport (Task 1)** — chunked NDJSON correctness, `Content-Type: application/x-ndjson`, no leftover SSE code paths or `text/event-stream` headers, backpressure handling, graceful shutdown.
- **WASM bindgen wrappers (Task 2)** — feature-gating consistency (`#[cfg(feature = "wasm")]` vs `#[cfg(target_arch = "wasm32")]`), no leakage of `wasm_bindgen` types into the native build, idiomatic Rust↔JS bridging (`JsValue` only at the boundary), error conversion patterns.
- **Webapp WASM build pipeline (Task 3)** — `webapp/scripts/build-wasm.sh` readability, no hard-coded absolute paths, proper `.gitignore` for generated `pkg/` output, exit-code propagation.
- **OAuth + auth middleware (Task 4)** — Axum router structure, middleware ordering (CORS → auth → handler), error-handling consistency (`anyhow::Result` mapped to `IntoResponse`), no `unwrap()` in request handlers.
- **Browser-mediated signing infra (Task 5)** — `pending.rs` LRU cap correctness (eviction order, capacity boundary, no unbounded growth), sign-callback validation completeness (signature verify before accept, replay protection, TTL).
- **Smithery + DNS (Task 6)** — `smithery.yaml` schema correctness, all required fields populated, install URL matches deployment target.
- **Webapp pages (Task 7)** — React idioms (hooks rules, key props), component composition (no monolithic pages), CSP correctness (no `unsafe-inline` unless justified).
- **Integration tests (Task 8)** — test quality (one assertion concept per test), no flaky patterns (no `sleep()`-based waits, no timing assumptions), realistic fixtures.
- **Smoke checklist (Task 9)** — clarity and unambiguity, every step has expected result + rollback note.

## Details

**Approach:**
- Read each file end-to-end before noting findings — partial reads produce false positives.
- For architectural-rule checks, use Grep over the workspace (`Grep "HashEmbedder"`, `Grep "axum" core/src/`, etc.) to produce evidence. Quote the result in the report.
- When a finding requires a code change, do **not** make the change — record severity and recommendation only. Fixes are scheduled separately.

**Severity guidelines:**
- **Critical** — blocks deploy: violates an architectural rule, introduces a panic path in a request handler, leaks credentials, or breaks a public contract.
- **Major** — should fix before merge: missing error handling, incorrect lifecycle, performance regression on hot path, missing test for new code path.
- **Minor** — nice to fix: style, naming, dead code, comment quality, doc gaps.

**Edge cases:**
- If a focus-area file does not exist (e.g. webapp not yet wired), record that as a major finding pointing back to the originating task.
- If two areas overlap (e.g. OAuth handler in `mcp.rs`), file the finding under the more specific area (OAuth) and cross-reference.
