# Sealed-режим: зашифрованные приватные воспоминания и приватный шеринг

Статус: черновик для владельца, 2026-09-27. Ничего из описанного ещё не
реализовано (всё — «запланировано»). Технические детали — в `tech-spec.md`,
открытые решения — в `decisions.md`.

## Зачем

Решение владельца от 2026-09-27: **«приватное» означает «зашифрованное»**.
Это относится и к воспоминаниям, которые хранит сервер (`local`), и к
воспоминаниям, закреплённым в блокчейне (Arweave + Solana).

Сейчас это не так:

1. **Закреплённые «приватные» воспоминания сейчас лежат на Arweave открытым
   текстом.** Метка `private` — это только фильтр в базе сервера
   (`mcp/src/api.rs:766-784`, загрузка — `mcp/src/api.rs:569-600`). Любой может
   прочитать эти байты на Arweave. Удалить их нельзя.
2. Воспоминания `local` на хостинге хранятся на сервере открытым текстом
   вместе с эмбеддингом. Оператор сервера может их прочитать.
3. Код шифрования (`core/src/encrypt.rs`) есть, но нигде не используется и не
   умеет «выдать доступ потом».

## Что получит пользователь

| Режим | Где хранится | Кто может прочитать |
|---|---|---|
| `local` (по умолчанию) | На сервере, **только шифротекст** | Только автор |
| `sealed` (закреплённое приватное) | Шифротекст на Arweave + отпечаток в Solana | Автор и агенты, которым он выдал доступ |
| `public` | Открытый текст на Arweave + отпечаток в Solana | Все |

- **Шифрование по умолчанию.** Любое воспоминание, которое не помечено
  `public`, шифруется. Для каждого воспоминания создаётся свой случайный ключ.
- **Доступ «потом».** Автор сохраняет воспоминание сейчас, а читателя может
  выбрать позже. Для этого он выдаёт «грант» — маленькую подписанную запись с
  ключом, зашифрованным для конкретного агента. Само воспоминание не
  перезагружается.
- **Ссылка-ключ.** Можно поделиться ссылкой `mnemonik.xyz/m/<отпечаток>#k=…`.
  Ключ находится после `#`, браузер не отправляет эту часть на сервер. Кто
  получил ссылку — тот может читать, навсегда.
- **Проверка без чтения.** Любой может проверить, кто и когда закрепил
  воспоминание, не видя текста. Отпечаток в Solana считается от шифротекста,
  поэтому короткий секрет (например, пароль) нельзя угадать перебором.
- **Шеринг между агентами по A2A** (issue #242): зашифрованное воспоминание
  передаётся внутри A2A-сообщения вместе с грантом для получателя.

## Как это работает (просто)

1. Клиент (или сервер на хостинге) генерирует ключ `K` и шифрует воспоминание.
2. `K` шифруется для открытого ключа автора. Этот ключ получается из той же
   подписи Ed25519, что уже есть у агента. Новых секретов хранить не нужно.
3. Автор подписывает зашифрованное воспоминание. Подпись и отпечаток
   доказывают авторство и дату.
4. Чтобы дать доступ агенту, автор шифрует `K` для ключа этого агента
   (обмен ключами Диффи–Хеллмана X25519, стандарт HPKE, RFC 9180).

## Честные ограничения

- **Отозвать доступ нельзя.** Если читатель уже получил и сохранил ключ, он
  сохранит доступ. Можно только перестать раздавать грант и выпустить новую
  версию с новым ключом.
- **Хостинг-коннектор видит текст в момент записи.** Когда агент (например,
  чат-клиент с удалённым MCP) передаёт текст серверу, сервер видит его, пока
  обрабатывает вызов. Потом сервер хранит только шифротекст. Полная защита
  «от начала до конца» — через локальный MCP, SDK, CLI или расширение: они
  шифруют текст до отправки.
- **Семантический поиск по зашифрованным воспоминаниям.** Сервер не может
  искать по смыслу в том, что не может прочитать. Эмбеддинг почти так же
  раскрывает текст, как сам текст, поэтому сервер не хранит его в открытом
  виде. Поиск идёт на стороне клиента. Для хостинг-коннекторов предлагается
  опциональная «сессия поиска»: владелец на время открывает ключ, и сервер
  ищет в памяти. Во время сессии сервер может читать — это будет сказано
  прямо.
- **Связка ключей ОС.** Сейчас ключ читается только для подписи. Теперь он
  понадобится и чтобы открыть зашифрованное воспоминание. Мы кэшируем ключ в
  памяти процесса, чтобы запрос связки ключей был не чаще одного раза за сессию.
  Запись `local` по-прежнему не требует доступа к связке ключей.
- Автор, дата и примерный размер закреплённого воспоминания остаются публичными.

## Что нужно решить владельцу

Полный список с вариантами и рекомендациями — `decisions.md`. Главное:

1. **D-1.** Принять формулировку «хостинг видит текст в момент записи» (рекомендуем) или запретить sealed-запись через хостинг-коннектор.
2. **D-2.** Ключ шифрования выводить из ключа подписи (рекомендуем сейчас) или завести отдельный.
3. **D-3.** Поиск по sealed на хостинге: только на клиенте + опциональная сессия поиска (рекомендуем).
4. **D-7.** Старые открытые `local`-записи на сервере: зашифровать на месте (рекомендуем).
5. **D-8.** Сразу переименовать старые «приватные» закреплённые записи в публичные и предупредить пользователей (рекомендуем).

## Критерии готовности

- Ни одна запись без `public` не хранится открытым текстом на сервере или на Arweave.
- Третья сторона проверяет авторство и дату sealed-воспоминания без ключа.
- Автор выдаёт доступ агенту позже, без повторной загрузки.
- Получатель открывает воспоминание у себя; сервер не видит ни текста, ни ключа `K`.
- Байты совпадают между Rust и SDK (WASM) на эталонных векторах.
- Документация (whitepaper, yellowpaper, `docs/tools.md`, README) честно описывает ограничения.
