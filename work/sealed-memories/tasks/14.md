# Task 14: A2A sealed payloads (issue #242)

## Description

Carry sealed memories in A2A messages and artifacts (tech-spec §9). This is
task 9 of #233. Start only after the a2a-bridge tasks 1, 4, 5 and 7 land.

## What to do

1. Data part media type `application/vnd.mnemonic.sealed+cbor` with
   `{sealed, grants[]}` (tech-spec §9.1).
2. Recipient key from a verified AgentCard `x-mnemonic.ed25519_pubkey_base58`
   (mapped to X25519) or a signed `x-mnemonic.enc_key` when present.
3. `mnemonic_attest_a2a` / `mnemonic_recall_a2a`: `sealed` input/output;
   decryption only on the client.
4. Stream chunks with `seal_chunk` / `open_chunk` (task 3), hashes in the #61 chain.
5. Conformance vectors: seal and open by recipient, non-recipient error,
   tampered ciphertext or wrap fails, Rust vs WASM byte parity.
6. Threat notes into a2a-bridge task 8.

## Acceptance

- Conformance vectors pass in Rust and in the SDK.

## Implementation evidence (2026-10-01)

Client-signed ingestion, sealed schema/dispatch, atomic ciphertext/grant storage,
author/recipient recall and SDK/CLI local open are implemented in the
`feat/sealed-a2a-client-signing` branch. Native vectors and real-WASM tests cover
author/recipient/outsider, tampering, signed cards and byte parity. A real HTTP
test exercises messages/artifacts with and without the completed sealed chunk
chain. [Contract, tests and threat notes](../../../docs/sealed-a2a.md).

Keep this task open: the completed chunk manifest is not yet connected to the
per-SSE #61 chain. Merge and passing conformance alone do not satisfy item 4.
