3. **Author the Browser-WASM verification UI sub-section** (~25-30 lines) under "Follow-up roadmap items":
   - **Problem:** Today's verification path requires a runtime that can run the Rust `verify` tool (MCP server, native binary). Browser users cannot independently verify a recalled attestation without contacting a backend, which weakens the "anyone can verify" property. The webapp ships a WASM build of `mnemonic-core` but the verification flow has no UI surface yet.
   - **Proposed Approach:** Surface the existing `verify` and `whoami` exports from the WASM build in the webapp; add a verification panel that takes an attestation_id (or full bundle), fetches the Arweave payload, runs blake3 + COSE_Sign1 verification entirely in-browser, and renders Solana anchor + signature OK/tampered badges. Reuse the design tokens from `ux-guidelines.md`.
   - **Dependencies:** `mnemonic-core` WASM target (completed feature); webapp Vite build already imports the WASM package.
   - **Open Questions:** (a) Does verifying a >10MB Arweave payload in-browser create UX issues? (b) Should the panel optionally accept a Solana RPC URL or rely on a public default? (c) How to surface signature `tampered` vs `not_found` distinctively without alarming users? (d) Should this panel also render the full COSE_Sign1 protected header for transparency? (e) Mobile browsers — feasible or desktop-first?
   - **Source-doc refs:** [docs/usecases/agent-continuity-layer.md](../../docs/usecases/agent-continuity-layer.md); [docs/research/apply-to-agent-memory-architecture.md](../../docs/research/apply-to-agent-memory-architecture.md); [docs/WHITEPAPER.md](../../docs/WHITEPAPER.md) §4 layered pipeline.
