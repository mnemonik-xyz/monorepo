# Task 6: Conformance golden vectors + threat model

## Description

Publish byte-parity fixtures for a full trajectory and document the trust
boundary. Lets any third-party implementation prove identical canonicalization,
hashing, and root computation.

## What to do

1. Golden vectors (committed under `core/tests/fixtures/trajectory/`): a 3-step
   trajectory with one verdict per step. For each step emit
   `{step_json, canonical_cbor_hex, cose_hex, content_hash}`; for the trajectory
   emit `{bundle_manifest_root_hex, inclusion_proof_per_step}` (the manifest root
   == the order-preserving `trajectory_root`). A test re-derives all bytes and
   asserts equality.
2. `references/threat-model.md` (this feature's section) covering: step reordering,
   content tampering, verdict forgery, judge-substitution (judge==producer),
   step omission / dense-range break, batch-root mismatch, replay across
   trajectories, broken checkpoint root-of-roots, **bundler trust** (Irys/Bundlr
   reordering or dropping data items — defeated because the anchored manifest root
   is over `seq`-ordered hashes and verify re-derives it), and **recall
   availability** (a withholding gateway can hide steps but cannot forge a passing
   `chain_valid` — omission breaks the dense range). For each: attack → defeating
   check, and which are integrity (defeated) vs availability (detected only).
3. Add a short subsection to `references/crypto-design.md` (or link) describing the
   STEP/VERDICT/TRAJECTORY envelope and the ordered vs set Merkle distinction.

## TDD anchors

- `tests::golden_trajectory_bytes_stable` — re-derive == fixtures, exact hex.
- `tests::golden_inclusion_proofs_verify` — every fixture proof verifies.

## Done when
