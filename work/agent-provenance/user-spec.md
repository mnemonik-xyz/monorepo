# User Spec: Agent Provenance — доказуемое соответствие действий агента полученному заданию

## Что делаем

Добавляем в Mnemonic **третью, недостающую ногу** доказуемости агентов:
криптографически верифицируемое **соответствие действий агента исходному
заданию (intent / mandate)**, которое он получил.

Сегодня (после `work/verifiable-trajectories/`) Mnemonic умеет доказывать два из
трёх утверждений «хорошего» агента:

1. **Целостность последовательности** — шаги шли в этом порядке, ничего не
   подменено (`STEP_V1`, hash-linked цепочка). ✓ есть.
2. **Привязка вердикта** — каждый шаг оценён независимым судьёй (`VERDICT_V1`). ✓ есть.
3. **Соответствие заданию** — агент сделал именно то, что просили, в рамках
   выданных полномочий и ограничений. ✗ **этого нет — это и есть фича.**

Конкретно поставляем:

1. **`MANDATE_V1`** — подписанное **принципалом** (тем, кто ставит задачу:
   человек, оркестратор, родительский агент) задание: текст интента +
   машинно-проверяемые ограничения (constraints) + выданные полномочия
   (capabilities: разрешённые инструменты, лимит трат) + `subject` (pubkey
   агента-исполнителя). Хеш мандата — это **корень соответствия**: вся цепочка
   шагов укореняется в нём.
2. **`EVIDENCE_V1`** — привязка внешних данных, на которые опирался шаг
   (request/response hash, источник, опционально zkTLS/notary/TEE-пруф по хешу).
   Это децентрализованный аналог Delta-шного zkTLS Evidence Layer: Mnemonic не
   *производит* TLS-пруф, а **фиксирует и упорядочивает** его.
3. **`COMPLIANCE_V1`** — вердикт соответствия, подписанный **независимым
   проверяющим** (`checker != subject`): по каждому ограничению мандата —
   satisfied/нет, с привязкой к доказательству. Может **связывать по хешу
   внешний zk-пруф (в т.ч. пруф самой Delta)**.
4. **Чистый policy-evaluator** — крошечный детерминированный вычислитель
   предикатов (числа/строки/множества/regex), который **любой** проверяющий
   может перезапустить над зафиксированными данными и получить тот же вердикт.
   Это и делает соответствие децентрализованным — не нужно доверять пруверу.
5. **Чистый correspondence-verifier** — проверяет: подпись мандата, укоренение
   шага 0 в мандате, что все шаги от авторизованного `subject`, что действия в
   рамках capabilities, что ограничения выполнены (машинные — пересчётом,
   субъективные — через подписанный `COMPLIANCE_V1`).
6. **Переосмысленный `safe_to_settle`** — теперь это «агент сделал то, что
   просили», а не просто «шаги были аккуратными». Децентрализованный аналог
   Delta-шного «Verifier одобрил proposal», но считается любым участником офлайн
   из перманета, без хостед-сервиса.
7. **MCP-инструменты**: `mnemonic_sign_mandate`, `mnemonic_attest_evidence`,
   `mnemonic_attest_compliance`, расширение `attest_step` и `verify_trajectory`.

Всё — за существующим cargo-feature `trajectory-experimental`, до объявления GA.

## Зачем

Появился внешний ориентир — **Delta Network**: они доказывают, что *действие*
агента соответствует подписанному пользователем intent'у (типизированная
политика), используя **централизованный закрытый SP1 zkVM + zkTLS** и проверяя
*до того, как уйдут деньги*. Их тезис: «Delta доказывает, что агенты *делают*;
Mnemonic доказывает, что агенты *знают*».

Владелец хочет двинуть Mnemonic в ту же содержательную область — доказуемое
соответствие действий заданию — но **по-своему**, по трём осям:

- **Децентрализованно.** Не хостед-прувер, которому надо доверять, а
  **детерминированная политика, перезапускаемая кем угодно** над хеш-
  зафиксированными данными. zk привязывается по хешу только там, где данные
  должны остаться приватными. Это ровно зафиксированная философия Mnemonic
  («производим commitment/lineage, внешние пруфы связываем, не производим»).
- **Эффективно.** Никакого zkVM в `core/`. Один маленький подписанный мандат,
  предикаты считаются за микросекунды, один order-preserving Merkle-корень, одна
  anchor-запись на чекпойнт. Стоимость zk-доказательства всегда чужая.
- **Provenance, а не только гейт.** Delta блокирует *до* действия. Mnemonic
  производит неизменяемую, заякоренную, независимо проверяемую *запись* того, что
  действие соответствовало заданию — и при этом тоже даёт гейт (`safe_to_settle`)
  для тех, кому нужно enforcement до действия. И то, и другое.

Композиция, не конкуренция: `COMPLIANCE_V1` может **связать пруф Delta по хешу**.
Mnemonic упорядочивает, якорит и делает recall-абельным то, что доказала Delta
(или TEE, или детерминированный чекер).

## Как это работает (happy path)

1. Принципал подписывает `MANDATE_V1` (`mnemonic_sign_mandate`): «купи синие
   кроссовки, размер 10, до $150», + constraints (`price ≤ 150`, `size == "10"`,
   `color == "blue"`), + capabilities (инструменты, лимит траты), + pubkey
   агента-исполнителя. Получает `mandate_hash`.
2. Агент на каждом шаге зовёт `mnemonic_attest_step` с `mandate_hash`. Шаг 0
   укореняется в мандате (`prev_hash := mandate_hash`). Где надо — прикладывает
   `EVIDENCE_V1` (данные товара с хешем ответа мерчанта, опц. zkTLS).
3. Независимый чекер оценивает соответствие и подписывает `COMPLIANCE_V1`:
   по каждому ограничению satisfied/нет, привязка к `mandate_hash` и корню
   траектории. Машинные ограничения он (и любой верификатор) считает пересчётом.
4. `mnemonic_verify_trajectory` возвращает correspondence-отчёт и
   `safe_to_settle`. Любой третий участник офлайн проверяет: подпись мандата,
   укоренение, авторизацию `subject`, рамки capabilities, выполнение ограничений
   (машинные — сам пересчитывает, субъективные — по подписи чекера) — без доступа
   к весам модели и без обращения к какому-либо серверу.

## Вне V1 (явно)

- Генерация zkVM/zkML/zkTLS-пруфов внутри Mnemonic — только связывание по хешу
  (композиция с Delta / TEE).
- On-chain verifier-контракт (ERC-8274) — наследуется из ERC-8004 / anchor-
  pluggable бэклога.
- Многоуровневые цепочки делегирования (`subject` — одиночный pubkey в V1).
- Богатый DSL ограничений сверх ограниченного набора предикатов — набор намеренно
  мал, чтобы оставаться тотальным и перезапускаемым.
