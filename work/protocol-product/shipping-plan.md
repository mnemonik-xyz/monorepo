# Product development and shipping plan

Status: proposed execution sequence. Gates require evidence, not a calendar date.

## Product and buyer

Mnemonik provides signed-memory delivery and independently verifiable recovery.
The first buyer hypothesis is a team running long-lived agents across replaceable runtimes.
The payer is that team. Agents call the SDK or Model Context Protocol service.
Sell managed delivery, integration, monitoring and continuity support.
Keep formats, verification and independent exit available without operator login.
There is no native token in the active product roadmap.

The research handoff demonstration makes authorship and recovery visible.
Its market fit remains a hypothesis.
Software-agent migration and incident handoff are follow-up experiments.
Permanent storage may exclude sensitive enterprise workloads.

Start customer interviews alongside implementation.
Do not delay learning until the full roadmap is built.
Repository extraction planning in task 11 is parallel work.
It is not a prerequisite for delivering recovery.

## Package and pricing experiment

Start with free local tools and managed delivery.
Test a team continuity package with usage, monitoring and support.
Show external costs and service fees separately.
Measure storage, gateway, compute, payment and support cost.
Track free-quota subsidy separately from paying demand.

Use the proposed ten interviews and three design partners as research budgets.
Three paying pilots and two repeat recovery drills are proposed demand evidence.
These counts are not settled commercial or legal gates.
Record refusal reasons and revise the offer when evidence contradicts it.
No outreach is performed by this documentation change.

## Release requirements

Publish a matrix of supported clients, artifact kinds, operators, backends and discovery sources.
Declare partial support, retention rules and known provider dependencies.
Release package versions with protocol compatibility and reproducible build references.
Provide key backup, checkpoint backup and restoration instructions.
Provide a separate staging deployment with synthetic artifacts.
Choose an external test environment only after confirming adapter support.

A release candidate needs install, save, restore, switch and continuation drills.
Include billing retries and settled-payment failure remedy.
Monitor delivery verification latency, failure rate, discovery lag and remedy backlog.
Set availability targets from measurements; do not invent a service agreement.

A rollback must preserve delivered artifacts and financial replay records.
Keep compatible readers for existing signed bytes.
Stop accepting writes that cannot satisfy the declared contract.
Do not silently fall back to hosted local memory storage.

## Meaning of release claims

| Claim | Required evidence |
|---|---|
| Client-private path | Operator receives no plaintext or keys |
| SQL-independent recovery | Operator disabled; receipts deleted; fresh client succeeds |
| Operator portability | Another compatible operator verifies external parent and continues |
| Backend portability | Exact-byte migration and recovery with source backend disabled |
| Production discovery | Dated live-provider evidence, including lag and failure behavior |
| Paid product validation | Customer repeats recovery and pays for the supported service |

Local fixtures prove code behavior.
Live-provider tests prove observed behavior under measured conditions.
Neither proves permanent availability or undisclosed-history completeness.

## Counsel and ownership

Engineering owns format integrity, data-flow facts and tested technical boundaries.
The owner chooses product scope, budget, signers and fundraising direction.
Counsel reviews entity, retention, permanent storage, deletion, cross-border processing,
service liability, refunds and fundraising instruments.
Do not publish legal compliance or token classification as an engineering conclusion.
