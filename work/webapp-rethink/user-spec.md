# User Spec: webapp-rethink (Evidence Ledger + Artifacts/Analytics/Blog + SEO)

## Что делаем

Переосмысление публичной части webapp (`webapp/`) в эстетике "Evidence Ledger" —
форензический архив машинной памяти. Сохраняем брендовую палитру (тёмный фон,
mint = "verified / on-node", Solana-purple = "anchored on-chain"), но усиливаем
типографику, добавляем мотив "квитанции/печати" для подписанных артефактов.

Добавляем четыре публичные страницы и SEO-инфраструктуру:

1. **Ledger** (`/ledger`) — список recalled-артефактов, сохранённых на ноде:
   текст памяти, blake3-хэш, теги, ссылки на Solana/Arweave, режим записи
   (`local` / `participate`), время.
2. **Analytics** (`/analytics`) — аттестации во времени (временной ряд on-node
   vs on-chain), сводные счётчики, переключатель диапазона.
3. **Blog** (`/blog`, `/blog/:slug`) — публикации протокола, с API для публикации
   AI-агентом.
4. **Landing** (`/`) — переосмысление в новой эстетике, без слома существующих
   OAuth/подписных страниц (`/sign`, `/oauth/consent`, `/install`).
5. **SEO** — поисковая дружелюбность всего сайта.

## Зачем

Сейчас публичная витрина — это landing + чат. Нет способа увидеть, что протокол
живой: какие памяти реально сохранены и верифицированы, как растёт сеть во
времени. Нет канала контента (блог), и SPA плохо индексируется. Эта фича:

1. **Доказательство работы.** Ledger и Analytics показывают реальные подписанные
   артефакты и динамику аттестаций — "доказательство существования" как
   публичный, проверяемый факт, а не маркетинговое заявление.
2. **Контент-канал для агентов.** Блог с API позволяет AI-агенту публиковать
   материалы (research notes, changelog, разборы) программно — демонстрация
   agent-native distribution.
3. **Органический трафик.** SEO-инфраструктура делает страницы индексируемыми и
   корректно превьюируемыми в поиске и соцсетях.

## Как должно работать

### Сценарий 1 — Просмотр сохранённых артефактов (Ledger)

Пользователь открывает `/ledger`. Видит ленту "квитанций": каждая — recalled
память с текстом, mono-хэшем blake3 (с кнопкой copy), тегами, бейджем режима
(`on-node` mint / `on-chain` purple) и ссылками на Solana/Arweave-эксплореры
(если анкор есть). Сверху — поле "recall by meaning" (поиск по смыслу/тегам) и
фильтры по режиму записи. Артефакты с on-chain-анкором несут печать "SEALED".

### Сценарий 2 — Динамика сети (Analytics)

Пользователь открывает `/analytics`. Видит кастомный SVG-график аттестаций во
времени с разбивкой on-node vs on-chain, переключателем диапазона (30d / 90d /
12m) и сводными счётчиками (всего на ноде, всего on-chain, уникальных
владельцев). График анимируется при загрузке (рисование линии).

### Сценарий 3 — Чтение блога

Пользователь открывает `/blog`. Видит список постов (заголовок, аннотация,
автор/агент, дата, теги). Клик открывает `/blog/:slug` с отрендеренным
Markdown. Заголовки страниц, описания, canonical и OG-теги корректны для каждого
поста (SEO).

### Сценарий 4 — Публикация поста AI-агентом

AI-агент вызывает API публикации (`POST /blog`, аутентифицированный), передаёт
title, body (Markdown), tags, имя агента. Сервер сохраняет пост, он становится
доступен на `/blog`. Пост помечается как опубликованный агентом.

### Сценарий 5 — Деградация без живых данных

Если бэкенд-эндпоинты (`/artifacts`, `/analytics/attestations`, `/blog`) ещё не
развёрнуты или недоступны, страницы показывают аккуратные loading / empty /
error состояния и репрезентативные sample-данные с явной пометкой "sample / not
live", чтобы UI не вводил в заблуждение.

### Сценарий 6 — Индексация поисковиком

Краулер запрашивает `/robots.txt` и `/sitemap.xml`, видит все публичные
маршруты. На каждой странице присутствуют уникальный `<title>`, meta description,
canonical, OG/Twitter-теги и JSON-LD. Существующая CSP не нарушается (без внешних
шрифтов/скриптов).

## Критерии приёмки

- [ ] `/ledger` рендерит список артефактов; каждая карточка показывает текст,
      blake3-хэш (copy работает), теги, бейдж режима, ссылки на эксплореры
- [ ] `local:`-tx не превращаются в ссылки (рендерятся как plain text)
- [ ] Поиск/фильтр на `/ledger` фильтрует список (по тексту и тегам)
- [ ] `/analytics` рендерит временной ряд on-node/on-chain с переключателем
      диапазона и сводными счётчиками; график доступен с reduced-motion
- [ ] `/blog` рендерит список постов; `/blog/:slug` рендерит Markdown поста
- [ ] `POST /blog` (аутентифицированный) принимает {title, body_markdown, tags[],
      agent} и публикует пост; неаутентифицированный запрос отклоняется
- [ ] Опубликованный агентом пост появляется в `GET /blog` и на `/blog/:slug`
- [ ] При недоступности бэкенда страницы показывают sample-данные с пометкой и не
      падают
- [ ] Landing переосмыслен в новой эстетике; `/sign`, `/oauth/consent`,
      `/install`, `/chat` функционально не сломаны (существующие тесты зелёные)
- [ ] `/robots.txt` и `/sitemap.xml` отдаются и перечисляют публичные маршруты
- [ ] Каждая публичная страница имеет уникальные title/description/canonical/OG +
      JSON-LD (React 19 head hoisting), CSP не нарушена
- [ ] Новые ссылки (Ledger, Analytics, Blog) добавлены в header и footer
- [ ] `cargo test --workspace`, `npm test`, `cargo clippy -D warnings`, `cargo fmt`
      зелёные; новые E2E (если добавлены) проходят

## Ограничения

- **OAuth/подписные страницы не трогаем по функциям.** `/sign`, `/oauth/consent`,
  `/install`, `/chat` сохраняют поведение и тесты; допустим только аккуратный
  визуальный апдейт shared header/footer.
- **Без внешних шрифтов/скриптов.** CSP (`font-src 'self'`, `script-src 'self'`)
  остаётся в силе — типографика на системных характерных шрифтах (Charter/Iowan
  serif + mono), без Google Fonts.
- **Без SSR.** SEO достигается через React 19 head hoisting + статические
  robots/sitemap + JSON-LD, без перехода на Next/SSR. Prerender — вне scope (может
  быть отдельной фичей).
- **Ledger/Analytics — публичные данные только.** Показываем строки с
  `visibility = public`; приватные памяти владельцев не утекают.
- **Блог-постинг — только аутентифицированный.** Анонимная публикация запрещена.
- **Графика без сторонних библиотек.** График — кастомный SVG, без recharts/d3.

## Риски

- **Риск 1: SEO без SSR ограничен.** Клиентский рендер хуже индексируется. 
  Митигация: React 19 head-теги + sitemap + JSON-LD + семантический HTML;
  prerender вынесен в отдельную фичу.
- **Риск 2: Утечка приватных артефактов в Ledger.** Митигация: backend-эндпоинт
  `/artifacts` возвращает строго `visibility = public`; фронт никогда не
  запрашивает приватные данные.
- **Риск 3: Спам/злоупотребление blog API.** Митигация: аутентификация + (опц.)
  rate limit; модерация/ревизия — отдельный вопрос, зафиксировать в decisions.
- **Риск 4: Рассинхрон CSP meta vs nginx header при SEO-правках.** Митигация: не
  добавляем внешние источники; если добавим — синхронно правим nginx-заголовок
  (см. комментарий в index.html).

## Технические решения

См. tech-spec.md. Кратко:

- **Frontend:** React 19 + React Router 6 + Tailwind 4. Дизайн-токены и
  утилиты "Evidence Ledger" уже заложены (`src/index.css`, `tailwind.config.js`),
  типизированные клиенты с graceful-fallback заложены (`src/lib/ledger.ts`,
  explorer-хелперы в `src/lib/links.ts`). Это НЕ переделывать.
- **Backend (отдельная волна, по спек-процессу):** новые axum-роуты в `mcp/`:
  `GET /artifacts`, `GET /analytics/attestations`, `GET /blog`, `GET /blog/:slug`,
  `POST /blog` (auth). Новая таблица `blog_posts` (миграция в
  `core/src/storage/sqlite.rs`). Соблюдение архитектурных правил из CLAUDE.md.
- **SEO:** `<Seo>`-компонент на React 19 head hoisting; `public/robots.txt`,
  `public/sitemap.xml`; JSON-LD (Organization + Article).

## Тестирование

**Unit (frontend, vitest):** ledger-клиент (live → graceful fallback на sample),
explorer-хелперы (`local:` → null), `<Seo>` рендерит теги, рендер карточки
артефакта, фильтрация, рендер графика (snapshot структуры SVG).

**Unit/integration (backend, при реализации волны):** `/artifacts` отдаёт только
public-строки; `/blog` CRUD; `POST /blog` отклоняет неаутентифицированный запрос;
миграция `blog_posts` идемпотентна.

**E2E (Playwright):** открыть `/ledger` → увидеть карточки; `/analytics` → увидеть
график; `/blog` → открыть пост; навигация header/footer; (backend) публикация
поста через API → появление на `/blog`.

## Как проверить

### Агент проверяет

| Шаг | Инструмент | Ожидаемый результат |
|-----|-----------|-------------------|
| 1. Build | `bash: cd webapp && npm run build` | Сборка без ошибок |
| 2. Unit | `bash: cd webapp && npm test` | Все тесты зелёные |
| 3. Lint | `bash: cargo clippy --workspace --all-targets -- -D warnings` | Без warnings |
| 4. Robots | `bash: curl -s http://localhost:3000/robots.txt` | Содержит Sitemap + Allow |
| 5. Sitemap | `bash: curl -s http://localhost:3000/sitemap.xml` | Перечисляет /ledger /analytics /blog |
| 6. Artifacts (после backend-волны) | `bash: curl -s http://localhost:3000/artifacts` | JSON со списком public-артефактов |
| 7. Blog publish (после backend-волны) | `bash: curl -X POST .../blog -H 'authorization: ...' -d '{...}'` | 200 + пост в GET /blog |

### Пользователь проверяет

- Открыть `/ledger` — убедиться, что карточки артефактов читаемы, copy хэша
  работает, ссылки на эксплореры ведут куда нужно.
- Открыть `/analytics` — убедиться, что график понятен, переключатель диапазона
  работает.
- Открыть `/blog` и пост — убедиться, что Markdown рендерится, заголовок/описание
  корректны в превью ссылки (OG).
- Проверить landing — новая эстетика, навигация в Ledger/Analytics/Blog работает.
