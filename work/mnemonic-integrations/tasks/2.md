# Task 2: WASM bindgen wrappers in core (incl. attestation signing)

## Required Skills

Before starting, load: `/skill:code-writing` — [SKILL.md](/Users/syi/.claude/skills/code-writing/SKILL.md)

## Description

Add a new module `core/src/wasm/mod.rs` exposing five `#[wasm_bindgen]` functions that the webapp calls from the browser to manage Ed25519 keypairs and produce COSE_Sign1 attestations entirely client-side. The wrappers compose existing primitives in `core/src/identity/mod.rs`, `core/src/codec/canonical.rs`, `core/src/codec/hash.rs`, and `core/src/codec/sign.rs` — no business-logic changes anywhere else in `core/`.

The five exports are:

1. `generate_keypair() -> JsValue` — creates a fresh `solana_sdk::signature::Keypair` and returns its 64-byte secret as a JSON object `{ "secret": [u8; 64], "pubkey_base58": String }`.
2. `sign_challenge(keypair_json: JsValue, challenge: &[u8]) -> Vec<u8>` — restores keypair from JSON, calls `identity::sign_bytes`, returns the 64-byte Ed25519 signature.
3. `sign_attestation_bundle(content: &str, embedding_bytes: &[u8], content_hash: &[u8], owner_pubkey: &str, keypair_json: JsValue) -> Vec<u8>` — builds the canonical-CBOR attestation bundle (same field layout used by the native flow), blake3-hashes per the existing pipeline, and signs via `codec::sign::sign_payload`, returning the COSE_Sign1 bytes that a native verifier can validate.
4. `export_keypair_json(keypair_json: JsValue) -> String` — serializes a keypair JSON object to a downloadable string for backup.
5. `import_keypair_json(json_str: &str) -> Result<JsValue, JsValue>` — parses a JSON backup, validates the secret length and that the embedded pubkey matches, returns the keypair JSON or a descriptive error (never panics).

The entire module is gated by `#[cfg(target_arch = "wasm32")]` AND a new `wasm` feature flag in `core/Cargo.toml`. Native builds (workspace `cargo build`) must not pull in `wasm-bindgen` and must not include the module. `wasm-bindgen-test`-driven tests run only on `wasm32-unknown-unknown` via `wasm-pack test --headless --chrome`.

This task is a foundation for Task 4b (browser-mediated signing) and Task 6 (sign-approval page) — both depend on `sign_attestation_bundle` being callable from the browser.

## What to do

1. **Add WASM dependencies** to `core/Cargo.toml` under a new wasm32-target-gated dependency block per Decision 3 of tech-spec. Pin versions exactly as listed in tech-spec Architecture section:
   - Under `[target.'cfg(target_arch = "wasm32")'.dependencies]`: `wasm-bindgen = "=0.2.95"`, `wasm-bindgen-futures = "0.4"`, `js-sys = "0.3"`, `serde-wasm-bindgen = "0.6"`, `getrandom = { version = "0.2", features = ["js"] }` (the `js` feature is required so `getrandom` resolves to the Web Crypto API in browsers).
   - Under `[target.'cfg(target_arch = "wasm32")'.dev-dependencies]`: `wasm-bindgen-test = "=0.3.45"`.
   - Under `[features]`: add `wasm = []`. The feature is a marker — actual WASM dependencies key off `cfg(target_arch = "wasm32")`. The feature exists so `cargo build -p mnemonic-core --features wasm --target wasm32-unknown-unknown` is the canonical invocation and so the wasm module body conditionally compiles via `#[cfg(all(target_arch = "wasm32", feature = "wasm"))]`.

2. **Wire the module into `core/src/lib.rs`** with:
   ```rust
   #[cfg(all(target_arch = "wasm32", feature = "wasm"))]
   pub mod wasm;
   ```
   Place near the bottom of `lib.rs` to keep native-build module ordering untouched.

3. **Implement `core/src/wasm/mod.rs`** with the five functions above. The same `#[cfg(...)]` guard wraps the file body. Use `serde-wasm-bindgen` (not `serde_json::to_value` → `JsValue::from_serde`) for JS interop — the latter is deprecated. Reuse `identity::sign_bytes`, `codec::canonical::to_canonical_cbor`, `codec::hash::blake3` (or whichever helper exists), and `codec::sign::sign_payload`. Errors from `import_keypair_json` must be returned as `Err(JsValue::from_str(msg))`, never `panic!` or `unwrap`.

4. **Mirror the canonical-CBOR field layout** used by the native MCP flow when building the bundle inside `sign_attestation_bundle`. Inspect `mcp/src/tools.rs::sign_memory` (or its successor after Task 4b) to confirm exact field names/order — bundle keys typically include content, embedding, content_hash, owner_pubkey, timestamp. Use `to_canonical_cbor` so byte-output is deterministic and matches the native verifier's expected input.

5. **Write 6 `wasm-bindgen-test` unit tests** at the bottom of `core/src/wasm/mod.rs`, gated by `#[cfg(test)]` plus the same wasm32+feature cfg, per the Testing Strategy in tech-spec:
   - keypair gen produces a valid 64-byte Ed25519 secret with matching base58 pubkey
   - `sign_challenge` round-trip: sign a 32-byte challenge, verify the signature with `identity::verify_signature`
   - JSON export → import round-trip preserves both secret and pubkey
   - two `generate_keypair()` calls produce distinct keys (no fixed seed leak)
   - `import_keypair_json("not-json")` returns `Err`, not panic
   - after a simulated page reload (just call `generate_keypair()` twice in the same test), entropy is non-zero and the two keys differ — proves `getrandom` `js` feature is wired and Web Crypto provides entropy

6. **Verify natively first:** `cargo build --workspace` (no `--features wasm`) must succeed and must not download `wasm-bindgen` — the wasm feature is off by default. Confirm with `cargo tree -p mnemonic-core | grep -E "wasm-bindgen|js-sys"` returning empty.

7. **Verify on wasm32 target:** `cargo build -p mnemonic-core --features wasm --target wasm32-unknown-unknown` must succeed.

8. **Run wasm-bindgen tests:** `wasm-pack test --headless --chrome core --features wasm` exits 0 with all 6 tests passing.

## TDD Anchor

Write the 6 wasm-bindgen tests BEFORE the implementation bodies — drive each public function from the test that exercises it.

- `core/src/wasm/mod.rs::tests::keypair_gen_produces_valid_ed25519` — calls `generate_keypair()`, asserts secret is 64 bytes and base58 pubkey decodes to 32 bytes
- `core/src/wasm/mod.rs::tests::sign_challenge_roundtrip_with_native_verifier` — generates keypair, signs a 32-byte challenge, calls `identity::verify_signature(pubkey, challenge, sig)` and asserts true
- `core/src/wasm/mod.rs::tests::export_import_preserves_keypair` — generate → export to JSON string → import → assert secret and pubkey unchanged
- `core/src/wasm/mod.rs::tests::repeated_generate_produces_distinct_keys` — call `generate_keypair()` twice, assert pubkeys differ
- `core/src/wasm/mod.rs::tests::malformed_import_returns_err_not_panic` — call `import_keypair_json("not-json")` and `import_keypair_json("{}")`, assert both return `Err` with non-empty message
- `core/src/wasm/mod.rs::tests::getrandom_provides_nonzero_entropy_after_reload` — generate two keypairs back-to-back, assert neither secret is all-zero and the two differ (proves Web Crypto path active)

A 7th implicit anchor that tech-spec acceptance criterion captures (round-trip COSE through native verifier) is exercised as part of the Task 7 integration test `roundtrip_cose_via_http_proxy.rs`; this task only needs the unit-level signing roundtrip in test #2 above.

**Dependencies:**
- This task has no task dependencies — wave 1, runs in parallel with Tasks 1 (HTTP transport) and 3 (webapp build pipeline).
- Output is consumed by Task 3 (webapp imports the generated WASM), Task 4b (server-side `sign_attestation_bundle` call validation), and Task 6 (sign-approval page).

**Edge cases:**
- `getrandom` without the `js` feature compiles on wasm32 but panics at runtime (`unable to fill randomness`). The `js` feature is mandatory.
- `solana_sdk::signature::Keypair` may pull non-WASM-compatible transitive deps. If wasm32 build fails on a `solana-sdk` feature, narrow to `solana-sdk = { version = "2.2", default-features = false }` or use `ed25519-dalek` directly for the wasm path. Document any deviation in `decisions.md`.
- `wasm-bindgen` version is pinned `=0.2.95` because mismatched runtime/cli versions break loading. Do not bump.
- Do not add `console_error_panic_hook` in production paths — the task is panic-free by contract. It may be wired in tests only if helpful for diagnostics.
- `wasm-pack` must be installed (`cargo install wasm-pack`) before running smoke. CI install is added by Task 7.

**Implementation hints:**
- Keep `core/src/wasm/mod.rs` under ~250 lines including tests. Helpers like a private `keypair_from_json(JsValue) -> Result<Keypair, JsValue>` reduce boilerplate.
- Prefer `serde-wasm-bindgen` over `JsValue::from_serde` (deprecated since wasm-bindgen 0.2.84).
- For the bundle CBOR construction, copy the field-build sequence from native `sign_memory` exactly — any drift breaks the cross-verifier round-trip in Task 7's `roundtrip_cose_via_http_proxy.rs`.
- Run the native build first; it's fast and surfaces feature-flag mistakes immediately.
