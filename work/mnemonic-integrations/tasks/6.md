# Task 6: Smithery listing + DNS subdomain + nginx

## Required Skills

Before starting, load: `/skill:infrastructure-setup` — [SKILL.md](/Users/syi/.claude/skills/infrastructure-setup/SKILL.md)

## Description

Three coordinated sub-tasks that together expose the MCP server publicly under `mcp.mnemonik.xyz` and make it discoverable in the Smithery registry. This is the single discovery surface for Phase 1 (Decision 5 of tech-spec, line 118-120).

1. **Smithery manifest:** Create `smithery.yaml` at the repo root declaring the `mcp.mnemonik.xyz` HTTP endpoint, the OAuth 2.1 + PKCE flow (authorization-code), and the five MCP tools published by the server. Format follows code-research.md §7 (currently no smithery.yaml exists in repo).
2. **DNS + nginx + SSL:** Add an A-record for `mcp.mnemonik.xyz` pointing at the existing VPS (`150.251.147.215`). Add a new `server` block to `/etc/nginx/sites-available/mnemonic` (currently single-host on `mnemonik.xyz` per `deployment.md` lines 222-244) that proxies `/` and `/mcp` and `/health` and `/oauth/*` to `localhost:3000`. Issue an SSL cert via `certbot --nginx -d mcp.mnemonik.xyz` reusing the existing certbot install.
3. **Smithery submission:** Once the endpoint is reachable over HTTPS and `tools/list` works, submit the listing through the Smithery web UI so it appears at `smithery.ai/mcp/mnemonic` with an install-deeplink.

This task does not touch Rust code. The MCP server already binds to `localhost:3000` from Task 1; this task only routes traffic and registers the endpoint externally.

## What to do

   - Description framed as "verifiable knowledge memory" (per Risks table line 280) — lead with utility, treat blockchain anchoring as plumbing.

3. **Coordinate DNS:** Add an A-record `mcp.mnemonik.xyz → 150.251.147.215` at the registrar managing `mnemonik.xyz`. Wait for propagation (verify with `dig +short mcp.mnemonik.xyz` from at least two networks).

4. **Update nginx config on VPS** (`/etc/nginx/sites-available/mnemonic`): add a second `server` block for `server_name mcp.mnemonik.xyz;` that proxies `/`, `/mcp`, `/health`, `/oauth/`, and `/api/` to `http://127.0.0.1:3000` with `proxy_set_header Host $host` and `X-Real-IP $remote_addr`. 5. **Issue SSL cert:** `sudo certbot --nginx -d mcp.mnemonik.xyz --non-interactive --agree-tos --email bogdan.sivochkin@gmail.com`. Certbot rewrites the new server block to listen on 443 and adds the redirect from 80.

7. **Submit to Smithery:** Use the smithery.ai web UI (no public submission API as of code-research.md §7). Paste the repo URL and ensure the listing shows the install-deeplink for Cursor.

## Details

**`smithery.yaml` (new, repo root):** Copy the template from `code-research.md` §7 (lines 418-449), then change every `mcp.mnemonic.dev` to `mcp.mnemonik.xyz`. Keep author email `dev@mnemonik.xyz`. **Nginx server block (on VPS, documented in deployment.md):** A new server-block alongside the existing `mnemonik.xyz` one. Routes:
- `/` → `http://127.0.0.1:3000` (so the root MCP probe Smithery does works)
- `/mcp` → `http://127.0.0.1:3000` (JSON-RPC + streamable HTTP)
- `/oauth/` → `http://127.0.0.1:3000` (authorize, token, callback — landed by Task 4a)
- `/api/` → `http://127.0.0.1:3000` (sign-callback, pending bundle fetch — landed by Task 4b)
- `/health` → `http://127.0.0.1:3000`
- Standard `proxy_set_header Host $host;` and `X-Real-IP $remote_addr;` — match the existing block on lines 230-233.
- `proxy_read_timeout 120s` for `/mcp` to allow streamable-HTTP long polls.
- After certbot rewrite: listens on 443 with TLS, redirects 80 → 443.

**Dependencies:**
- Listed as `depends_on: []` because the smithery.yaml file and DNS update don't require any code from earlier waves. However, the **Smithery submission step** is only useful once Wave 1 + Task 4a are deployed — so practically, run step 7 (submit to Smithery) after Wave 1 ships and the endpoint actually answers `tools/list`. The smoke check `curl https://mcp.mnemonik.xyz/health` will return 502 until the MCP binary is running on the VPS — that is acceptable for an early DNS+TLS smoke run; rerun before Smithery submission.

**Edge cases:**
- DNS propagation can take up to 24h; the user-spec risk table line 277 calls this out — schedule the A-record update at least a day before the demo.
- Certbot rate-limits: max 5 duplicate certs per week per domain; if a previous attempt failed, wait or use `--dry-run` first.
- Smithery review may reject crypto framing — fall back to mcp.directory in P1.5 (tech-spec line 280).
- The existing `mnemonik.xyz` block must keep serving the webapp `dist/` static files. Do not point `mnemonik.xyz` traffic at `localhost:3000` — only the new `mcp.` subdomain proxies to MCP.
- code-research.md §7 has the wrong domain (`mcp.mnemonic.dev`); tech-spec Deviation 2 (line 298-300) makes `mcp.mnemonik.xyz` canonical — do not copy the URL verbatim from §7.

**Implementation hints:**
- Validate `smithery.yaml` locally with `python3 -c "import yaml, sys; yaml.safe_load(open('smithery.yaml'))"` before committing.
- Test the nginx block with `sudo nginx -t` before `systemctl reload`. A bad config takes the main `mnemonik.xyz` site down too.
- After certbot, the server block in `/etc/nginx/sites-available/mnemonic` is rewritten in place; capture a `git diff`-style note in `deployment.md` showing the final form.
