# Task 9: Pre-demo manual smoke checklist

## Required Skills

Before starting, load: `/skill:documentation-writing` — [SKILL.md](/Users/syi/.claude/skills/documentation-writing/SKILL.md)

## Description

Author `work/mnemonic-integrations/tasks/smoke-checklist.md` — an exhaustive, unambiguous, manual end-to-end smoke test that walks a single human operator through the full Phase-1 happy path on Cursor and Claude.ai Pro. The checklist is the gate document for the pre-release smoke run and the live-demo dry-run; the same document is used by Task 12 (pre-deploy QA) and Task 14 (post-deploy QA).

The flow under test is the deferred-sign architecture introduced by Decision 4 of tech-spec (line 104-109): `sign_memory` returns `awaiting_signature` + `approve_url`, the user opens `/sign/<id>` in the webapp, WASM signs with the localStorage keypair, the server validates and persists. The checklist must exercise every leg of that flow plus cross-tool (`Cursor → Claude.ai Pro`) and cross-device (`laptop A → laptop B via keypair backup`) recall.

This is a documentation-only task. No code is changed. Output is one Markdown file written so a team member who did not author the spec can execute end-to-end in ≤30 minutes without asking questions.

## What to do

1. **Read context** — user-spec Сценарии 1–4 (lines 29–43), tech-spec "How it works" diagram (lines 35–78), and code-research.md (deeplink + OAuth notes). Internalize the deferred-sign sequence: `tools/call sign_memory → awaiting_signature → /sign/<id> → WASM sign → /api/sign-callback → 200 → recall sees row`.

2. **Create `work/mnemonic-integrations/tasks/smoke-checklist.md`** with the structure below. Use a single top-level title (`# Mnemonic — Pre-demo Manual Smoke Checklist`), a short preamble (purpose, prerequisites, total ETA target ≤30 min), then ten sequential numbered sections — one per step listed in the Description summary above.

3. **Per-step format** — every step is a four-tuple, rendered as a fixed sub-heading set so the operator can scan visually:

   - **Action** — one or two sentences describing exactly what to click/type/run. No hand-waving ("then test it" is not allowed); name the URL, the button label, the env var, the CLI command.
   - **Expected** — what the operator should observe (URL change, JSON shape, toast text, console line). Include verbatim strings the operator can compare against.
   - **Recovery** — if the expected does not happen, the immediate fallback (e.g. "rerun `npm run dev`", "clear localStorage and retry from step 2", "check `journalctl -u mnemonic-mcp`"). Always one concrete next action — never "debug it".
   - **ETA** — seconds budget for this step alone (e.g. `~30s`, `~2m`). Sum across all ten steps must not exceed `1800s` (30 min) for the happy path.

4. **The ten steps** (this is the ordering required — do not renumber):

   1. **Fresh-browser onboarding.** Open Chrome incognito (or a fresh profile). Navigate to `https://mnemonik.xyz/`. Confirm landing renders with a "Get started" CTA. localStorage and cookies must be empty before the test starts.
   2. **Keypair generation via WASM identity panel.** From `/install`, confirm the IdentityPanel auto-runs `generate_keypair()` on first load (no prior keypair in localStorage); a DID/pubkey appears in the panel.
   3. **Keypair backup download.** Click "Download keypair backup" and save the JSON to disk. Open the file in a text editor and confirm it has a non-empty `secret_key` field.
   4. **Install deeplink to Cursor.** Click "Install in Cursor". OS prompts to open Cursor; accept. Cursor displays an "Add MCP connector" dialog naming `mcp.mnemonik.xyz`; accept.
   5. **OAuth approve flow.** Cursor redirects to the browser with `https://mcp.mnemonik.xyz/oauth/authorize?...`; the consent page asks the user to sign the challenge. Click "Approve"; WASM `sign_challenge` runs; the page posts the signature; Cursor receives the JWT and reports the connector as ready.
   6. **`sign_memory` from Cursor → `/sign/<id>`.** In Cursor chat, ask the model to call `mnemonic_sign_memory` with content `"smoke-test memory N"` (replace N with the run number). The tool result is JSON `{status: "awaiting_signature", approve_url, correlation_id, expires_in}`. Open `approve_url`; the `/sign/<correlation_id>` page renders the content preview, the 5-min countdown, and a "Sign with my Mnemonic identity" button. Click Sign. The page should report success (toast or status text) and the server callback should return HTTP 200.
   7. **`recall` in same Cursor session.** In the same chat, ask the model to call `mnemonic_recall(query: "smoke-test memory")` with default limit. The result must include the attestation that was signed in step 6 — verify the content string matches.
   8. **Switch to Claude.ai Pro and add custom connector.** In Claude.ai Pro: Settings → Connectors → Add custom → paste `https://mcp.mnemonik.xyz`. OAuth flow re-runs; the same DID/pubkey is reused (the browser still holds the localStorage keypair). Approve.
   9. **Recall in Claude.ai returns the same attestation.** Open a new Claude.ai chat; ask "recall my smoke-test memory". The model calls `mnemonic_recall` and returns the attestation signed in step 6 — same content, same attestation_id.
   10. **Cross-device flow.** On a second laptop (or a second Chrome profile that is fully clean), open `mnemonik.xyz/install`, click "Restore from backup", upload the JSON saved in step 3. Confirm the panel shows the same DID/pubkey. Install the Cursor connector again (steps 4–5 repeat on the new device). In Cursor, run `mnemonic_recall` — the attestation from step 6 must appear (proves cross-device portability).

5. **Preamble** — at the top, list:
   - Purpose: pre-release smoke + demo dry-run, executed by a team member who did not author the spec.
   - Prerequisites: a Cursor install, a Claude.ai Pro subscription, a fresh Chrome profile (or incognito window) with empty localStorage, the second laptop accessible (for step 10). The MCP endpoint `https://mcp.mnemonik.xyz` must be live (Task 13 deploy must have run) — checklist is run against the deployed system, not localhost. For local-only validation note that step 8 (Claude.ai Pro) is skipped and step 10 simulated with a second profile.
   - Total ETA budget: ≤30 minutes for the happy path. Budget breakdown is the sum of per-step ETAs.
   - Failure policy: if any step's Recovery does not unblock progress within 5 minutes, abort and report which step + what the actual observation was.

6. **Closing section "Run log template"** — provide a copy-paste table the operator fills in: step | start time | end time | pass/fail | notes. This becomes the artifact attached to the QA report (Tasks 12, 14).

7. **Tone and style** — imperative ("Click X", "Run Y"), no second-person hedging ("you may want to..."). Verbatim strings in backticks. URLs in full. No emojis.

**Edge cases the checklist must explicitly call out (in Recovery notes):**

- localStorage already populated from a prior run — Recovery for step 1: open DevTools → Application → Local Storage → clear all entries for `mnemonik.xyz`, then reload.
- Cursor refuses the connector because the OAuth redirect URL is unregistered — Recovery for step 4: confirm the deployed `smithery.yaml` lists the correct redirect URL; rerun deploy if not.
- The 5-minute TTL on PendingBundles expires before the operator clicks Sign — Recovery for step 6: rerun the Cursor tool call (the operator triggers a new `correlation_id`).
- Claude.ai Pro custom connector dialog rejects the URL — Recovery for step 8: confirm `curl -fI https://mcp.mnemonik.xyz/health` returns 200 and that the OAuth metadata at `/.well-known/oauth-authorization-server` is reachable.
- On the second laptop, the imported keypair shows a different DID — Recovery for step 10: this means the import path is broken; abort and file a bug — do not proceed.

**Implementation hints:**

- Mirror the writing style of `deployment.md` and `patterns.md` in `.claude/skills/project-knowledge/references/` — terse, imperative, code-fenced commands.
- Each step's Action should fit on 1–3 lines; Expected on 1–2 lines; Recovery on 1 line; ETA on a single inline value. This is what keeps the file in the 80–120 line target.
- Time-box ETAs realistically: onboarding/install steps `~30s–1m`, OAuth approval `~30s`, Cursor model invocation + sign `~2m` (model latency), recall `~30s`, cross-device step `~5m` (second-laptop setup dominates). Aim for ~20m budget with ~10m slack inside the 30m cap.
- The file is plaintext Markdown; no diagrams. If you would draw an arrow, name the URL transition in prose instead.
- Do not include screenshots — the file lives in the repo, screenshots drift. Verbatim text and URLs only.
