# Task 15: Post-deploy QA (Final Wave)

## Required Skills

Before starting, load: `/skill:post-deploy-qa` — [SKILL.md](/Users/syi/.claude/skills/post-deploy-qa/SKILL.md)

## Description

Live-environment verification on `mcp.mnemonik.xyz` and `mnemonik.xyz` after Task 14 deploy completes. This is the final gate before declaring the hackathon-demo feature shipped: every user-spec success metric and tech-spec acceptance criterion must be confirmed against the production endpoints, not staging or local. The output is a pass/fail report appended to `decisions.md` with concrete evidence (curl output, screenshots, log snippets) for each step.

No code is written in this task. The agent acts as a QA engineer driving real clients (MCP Inspector, fresh Cursor profile, Claude.ai Pro) against live infrastructure and recording results.

## What to do

1. **MCP Inspector validation against the live endpoint.** Run `npx @modelcontextprotocol/inspector@0.6.x --validate https://mcp.mnemonik.xyz/mcp -H "Authorization: Bearer ${TEST_JWT}"`. All schema and protocol checks must pass; capture full stdout/stderr in the report.

2. **End-to-end Cursor connector install on a clean Cursor profile.**
   - Visit `https://mnemonik.xyz/install` in a fresh browser profile (no cookies, no localStorage from prior runs).
   - Generate a keypair via the IdentityPanel; verify `localStorage` stores an AES-GCM-encrypted payload (open DevTools, confirm ciphertext + IV layout, no plaintext seed).
   - Click "Install in Cursor" → deeplink fires → Cursor opens → OAuth approve flow with user-signed challenge → JWT issued. Capture the deeplink URL and the issued JWT's header/payload (redact signature).
   - In a fresh Cursor chat: `save this onchain: hello world from post-deploy QA` → tool call returns `awaiting_signature` with an `approve_url`.
   - Open `approve_url` → `/sign/<id>` page renders with content preview + countdown → click "Sign" → 200 OK from sign-callback. Screenshot the approval page.
   - Back in Cursor: `recall my recent saves` → returns the attestation just signed. Capture the tool-call response.

3. **Repeat step 2 from the Claude.ai Pro path** (custom connector via Settings → Connectors → Add custom MCP). Same end-to-end signal: install, sign, recall. Document any UX differences from the Cursor flow.

4. **Smithery listing live verification.**
   - `curl -fsSL https://smithery.ai/mcp/mnemonic | grep -q "mcp.mnemonik.xyz"` — confirms the listing's HTML references the correct subdomain in its install-deeplink. The endpoint serves static HTML (no JSON API), so the check is content-based, not status-only.
   - Fallback: if Smithery's static HTML structure changes and the grep no longer matches even though the page is correct, manual verification by visiting `https://smithery.ai/mcp/mnemonic` in a browser and inspecting the install button's deeplink target is acceptable. Record the manual-verification choice and the observed deeplink in the report.
   - From a separate machine/profile, complete a self-install from Smithery without any manual config. Confirm the issued JWT works against `mcp.mnemonik.xyz/mcp`.

5. **Security live spot-checks (must all pass).**
   - Anonymous call: `curl -X POST https://mcp.mnemonik.xyz/mcp -d '{"jsonrpc":"2.0","method":"tools/call","params":{"name":"mnemonic_recall","arguments":{"query":"x"}},"id":1}'` → expect HTTP 401.
   - Cross-tenant: generate two distinct test JWTs (users A and B); `recall` from B must not return A's attestations.
   - Rate limit: fire 6 `sign_memory` requests from the same IP within 60s; the cap is **5/min** (per tech-spec AC), so the 6th must return HTTP 429. Recall stays uncapped at this volume (recall cap is 30/min).
   - Headers: open `https://mnemonik.xyz/install` and inspect response headers for CSP including `frame-ancestors 'none'` and `default-src 'self'` (plus the rest of the locked-down policy from tech-spec §Security).

6. **Mark all user-spec success metrics measurable** (install counter wired up).
   - Server logs a counter for `/oauth/token` issuances (proxy for "MCP install events through webapp install-hub").
   - Server logs a counter for `sign_memory` calls per user.
   - Server logs a counter for `recall` calls per user.
   - These counters dump to `tracing` output, so `journalctl -u mnemonic-mcp | grep "metric:"` aggregates them. Capture a sample line per counter in the report.
   - **Note (KNOWN GAP handling):** `deployment.md` states "No app-level metrics for MVP." If `journalctl -u mnemonic-mcp | grep "metric:"` returns empty, this means the counters were not wired up by upstream tasks (track in backlog). Record this as a **KNOWN GAP** in the report — it is not a blocking failure for the demo verdict, but it must be flagged so the success-metrics line in user-spec is updated to reflect the manual-counting fallback (e.g., counting JWT issuances from systemd logs of the OAuth route directly).

## Details

**Output artifact:** a single `## Post-deploy QA report` section appended to `work/mnemonic-integrations/decisions.md`, dated, with one subsection per numbered step. Each subsection contains: status (pass/fail), command run, captured output (truncated where huge), and a short note. End with a roll-up verdict: GO / NO-GO for demo.

**Dependencies:**
- Hard dep on Task 14 (deploy) being green: `mcp.mnemonik.xyz` and `mnemonik.xyz` must be live and serving 200s on `/health` and `/install` before this task starts.
- Requires `TEST_JWT` env var in the QA agent's environment (issue via webapp install-hub once before starting; reuse for steps 1, 5).

**Edge cases:**
- If a step fails, do not stop — continue running the rest, then mark the overall verdict NO-GO and list every failure with reproduction command.
- For the rate-limit check, use a single source IP. If the QA runner is behind a NAT shared with other test traffic, use a dedicated VM or document the IP in the report.
- The cross-tenant test must use two genuinely distinct keypairs, not the same keypair re-encoded; otherwise the isolation guarantee is not exercised.
- CSP header check is on the webapp origin (`mnemonik.xyz/install`), not the MCP origin. Do not confuse the two.

**Implementation hints:**
- Run all six steps from a clean shell session. Capture `set -x` style logs into a buffer file under `work/mnemonic-integrations/logs/post-deploy-qa-<date>.log` and link from the report.
- For Smithery self-install, use a different OS user or a fresh container so cached deeplinks don't shortcut the flow.
- The `metric:` log lines are emitted via `tracing::info!` with structured fields; `journalctl ... | grep "metric:"` is sufficient for the sample-line evidence — no Prometheus needed for the hackathon demo.
