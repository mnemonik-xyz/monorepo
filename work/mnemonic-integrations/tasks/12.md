# Task 12: Test Audit (Audit Wave)

## Required Skills

Before starting, load: `/skill:test-master` — [SKILL.md](/Users/syi/.claude/skills/test-master/SKILL.md)

## Description

Test quality and pyramid balance audit. The reviewer reads every test file written by Tasks 1-9 and appends findings to `work/mnemonic-integrations/decisions.md`. This is an audit task — there is no separate review step; the audit *is* the review.

The audit checks two things at once: (a) every test is meaningful (it actually exercises behaviour we wrote, not crate defaults), and (b) the test suite as a whole has the right shape for a size-L hackathon MVP — light enough to run fast, dense enough to prove every user-spec MUST and every tech-spec Decision (9, 10, 11, 12).

## What to do

1. **Inventory all tests.** Walk every test module written by Tasks 1-9 and count: unit tests, integration tests, wasm-bindgen-tests, webapp component tests, manual smoke steps. Record raw counts plus per-area distribution (OAuth, WASM, COSE-via-proxy, recall, stdio, rate-limit, CORS, auth allowlist, deferred-sign, pending expiry, MCP Inspector CI, manual smoke). Compare against the size-L MVP target (~25-30 unit, ~12 integration, manual E2E only).

2. **Per-area quality review.** For each focus area below, read the tests and grade them on a pass/fail per criterion. Cite file:line for every finding.

   - **OAuth flow** — 12 unit tests + integration coverage. Verify each of: `alg=none` rejection, alg-confusion attack rejection, replay / single-use enforcement, tampered `sub` rejection, missing-`state` CSRF rejection, expired-code rejection, concurrent-`jti` handling. Flag any test that only verifies `jsonwebtoken` crate defaults without exercising our own logic.
   - **WASM wrappers** — 6 wasm-bindgen-tests. Verify `sign_attestation_bundle` round-trips through the native verifier (correctness, not just type-checks). Verify malformed input returns `Err`, never panics across the FFI boundary.
   - **COSE-via-proxy mock realism** — read the mock and confirm it actually mutates JSON byte order / whitespace differently from `serde_json` defaults. A mock that re-emits identical bytes proves nothing about byte-stability.
   - **`recall` ownership isolation** — there must be an explicit cross-tenant assertion: a row owned by user A must not appear in user B's `recall` result. Implicit "we filter by owner" is not enough.
   - **stdio backward-compat** — uses a pre-built binary (not `cargo run`), sets `EMBED_PROVIDER=mock`, wraps the handshake in `tokio::time::timeout`, and is free of race conditions on stdin/stdout buffers.
   - **Rate-limit wired test** — boots the actual axum router, not just the limiter logic in isolation. Asserts a real 429 response from a real handler.
   - **CORS test** — preflight assertions for both an allowed origin and a rejected origin; both `Access-Control-Allow-Origin` presence/absence and the response status.
   - **Auth allowlist** — verifies `tools/list` and `initialize` remain accessible without an auth header (paid tools must still 401).
   - **Deferred-sign flow** — full lifecycle: create pending → fetch → sign → submit → assert 410 on second submit (single-use), 403 on cross-user fetch.
   - **Pending bundle expiry** — uses `tokio::time::pause()` + `advance()`, never `std::thread::sleep` against real time.
   - **MCP Inspector CI step** — `npx` invocation pins a version (no floating `latest`), and a `wait-for-port` (or equivalent) readiness probe with a timeout precedes the validate call.
   - **Manual smoke checklist** — every step is unambiguous, executable by a stranger with no project context, and the stated ETA is realistic.

3. **Test pyramid balance.** Compute the actual unit:integration:E2E ratio. Compare to size-L MVP target (~25-30 unit, ~12 integration, manual E2E only). Flag inversion (e.g. too many integration tests, no unit tests) or absence (e.g. zero wasm-bindgen-tests).

4. **Coverage matrix — user-spec MUST items.** Build a traceability matrix: every MUST line in `user-spec.md` → one or more test names that prove it. Mark any MUST without a test as a coverage gap with a concrete suggested test name.

5. **Coverage matrix — tech-spec Decisions 9, 10, 11, 12.** Same traceability matrix for these four decisions. Each decision must map to at least one test that would fail if the decision were silently reverted.

6. **Write the report.** Append a new section to `work/mnemonic-integrations/decisions.md` titled `## Test Audit — <date>`. Structure: pyramid summary, per-area pass/fail table, coverage gaps with suggested test names, MUST traceability matrix, Decision-9/10/11/12 traceability matrix.

## Details

**Approach.** Read first, judge second. Inventory every test file before grading any of them — pyramid balance is invisible from a single file. Use `grep -rn "#\[test\]\|#\[tokio::test\]\|#\[wasm_bindgen_test\]"` over `core/`, `mcp/`, `webapp/` to find every test, then map each to a focus area.

**Edge cases:**
- A test may belong to multiple focus areas (e.g. an OAuth integration test that also exercises rate-limit). Count it once for pyramid math, but list it under every area it covers in the per-area table.
- `tests/` files prefixed `_helpers` or `common.rs` are fixtures, not tests — exclude from the count.
- `#[ignore]`-marked tests count as zero (they do not run in CI).
- `webapp` may have zero `*.test.tsx` files. That is acceptable for size-L MVP if the manual smoke checklist covers UI behaviour — flag it but do not fail the audit on it.
- Integration tests that boot the full router and assert via HTTP count as integration, not E2E. True E2E in this MVP is manual only.

**Implementation hints:**
- For the COSE-via-proxy realism check, look for the mock's mutation strategy explicitly. If the mock re-serializes via `serde_json::to_vec` with default options, it produces identical output to the original — that is the failure mode to catch.
- For the user-spec MUST matrix, copy MUST lines verbatim into the matrix as the row key, then map by test name. Do not paraphrase — exact-match makes the matrix auditable in the next QA pass.
- For Decision 9/10/11/12 mapping, read each Decision section in `tech-spec.md` first and write down what behaviour it mandates, then find the test that would fail if the behaviour were reverted. If no such test exists, that is a gap.
- The report goes into `decisions.md`, which is append-only. Do not edit existing entries.
