# Task 6: Extract storage with trait split

## Required Skills

Before starting, load: `/skill:code-writing` — [SKILL.md](/home/claude/.claude/skills/code-writing/SKILL.md)

## Description

This task extracts the SQLite storage layer from `mcp/src/db.rs` into a standalone module in `core/src/storage/`. The extraction introduces a clean trait abstraction: `AttestationStore` and a minimal `LineageStore` trait defined in `core/src/storage/traits.rs`, with a concrete SQLite implementation in `core/src/storage/sqlite.rs`.

Currently, ALL methods — including the 8 payment methods (`create_api_key`, `deduct_balance`, `credit_deposit`, `mark_x402_nonce`, `record_attestation_cost`, `get_pnl_stats`, `get_owner_pubkey`, `get_balance`) — live on the `AttestationStore` struct in `mcp/src/db.rs`. This task moves ONLY the non-payment methods into core traits, and moves the payment methods from `db.rs` into `mcp/src/payment.rs`. The split ensures core never contains payment logic: after this task, `grep -r "create_api_key\|deduct_balance\|...\|get_balance" core/src/` must return empty.

Authorization is deliberately excluded from the traits: trait methods operate on the full database without per-signer scoping. This matches the existing `db.rs` behavior and is explicitly documented in trait-level rustdoc. The MCP server enforces authorization via the keypair loaded at startup.

**Important: `LineageStore` scope in Task 6 is intentionally minimal.** The lineage query types (`LineageResult`, `LineageNode`, `LineageEdge`, `ParentRef`) are currently defined in `mcp/src/lineage.rs` and will not move to `core/src/lineage/` until Task 9. To avoid pulling those types into core prematurely (or creating placeholder structs that would need replacement), `LineageStore` in this task exposes only the raw storage-level operations that work with primitive types: `save_edge`, `get_edges`, `clear_edges`. The higher-level query methods (`get_lineage`, `get_ancestry`, `validate_chain`) are added in Task 9 when the lineage types are in core. The trait body includes a `// TODO(task-9): add get_lineage, get_ancestry, validate_chain methods after lineage types are in core` comment.

After this task, `mcp/src/tools.rs`, `mcp/src/mcp.rs`, and `mcp/src/main.rs` import storage types from `mnemonic_core::storage::` instead of the local `db` module. The SQLite dependency moves to `core/Cargo.toml`. The `cargo test -p mnemonic-core -- storage` suite is green, and `grep -r "create_api_key\|deduct_balance\|credit_deposit\|mark_x402_nonce\|record_attestation_cost\|get_pnl_stats\|get_owner_pubkey\|get_balance" core/src/` returns empty.

## What to do

2. In `traits.rs`, define two public traits with full rustdoc:

   - `LineageStore` — minimal storage-level lineage operations only (no lineage result types needed): `save_edge(parent_id: &str, child_id: &str, depth: i64) -> anyhow::Result<()>`, `get_edges(child_id: &str) -> anyhow::Result<Vec<(String, i64)>>`, `clear_edges(artifact_id: &str) -> anyhow::Result<()>`. Same authorization note. Include a `// TODO(task-9): add get_lineage, get_ancestry, validate_chain methods after lineage types are in core` comment inside the trait body.

   - Implement `LineageStore` with only the three minimal methods: `save_edge`, `get_edges`, `clear_edges` — raw SQL against the `lineage_edges` table
   - Do NOT include any payment methods (`create_api_key`, `deduct_balance`, `credit_deposit`, `mark_x402_nonce`, `record_attestation_cost`, `get_pnl_stats`, `get_owner_pubkey`, `get_balance`)

## Details

**Files and what to do:**

`core/src/storage/traits.rs` — Define two public traits. Each trait method signature is derived from `db.rs` public API (see code-research.md section 5, `db` module). Methods for `AttestationStore`: `save_attestation` (takes attestation fields by value or reference — match the existing `db.rs` signature exactly), `find_by_tx(&self, tx_id: &str) -> anyhow::Result<Option<AttestationRow>>`, `count(&self, signer: &str) -> anyhow::Result<i64>`, `search(&self, query_embedding: &[f32], signer: &str, limit: usize) -> anyhow::Result<Vec<SearchResult>>`. For `LineageStore`: only `save_edge(&self, parent_id: &str, child_id: &str, depth: i64) -> anyhow::Result<()>`, `get_edges(&self, child_id: &str) -> anyhow::Result<Vec<(String, i64)>>`, `clear_edges(&self, artifact_id: &str) -> anyhow::Result<()>`. These use only primitive types and are self-contained. Include the TODO comment for Task 9 methods. Data types `AttestationRow` and `SearchResult` are defined here or in `mod.rs` (whichever keeps the code cleaner).

`core/src/storage/sqlite.rs` — `SqliteStore` struct wrapping `rusqlite::Connection`. The `open` constructor creates the directory if it does not exist (using `std::fs::create_dir_all`) and applies the schema (all `CREATE TABLE IF NOT EXISTS` statements from `db.rs`, including `lineage_edges`). The `in_memory` constructor opens `:memory:` and applies the same schema. All SQL is parameterized — never format strings into SQL queries. The cosine search in `search()` fetches all embeddings then scores them in Rust (matching existing db.rs behavior) — do not try to do cosine math in SQL. Implement `LineageStore` with three direct SQL methods against `lineage_edges`: `save_edge` inserts a `(parent_id, child_id, depth)` row, `get_edges` selects all rows for a given `child_id`, `clear_edges` deletes all rows where `parent_id = ?` or `child_id = ?`.

`mcp/src/db.rs` — Read carefully before making any changes. Map every public method: `save_attestation`, `find_by_tx`, `count`, `search` go to core; `create_api_key`, `deduct_balance`, `credit_deposit`, `mark_x402_nonce`, `record_attestation_cost`, `get_pnl_stats`, `get_owner_pubkey`, `get_balance` move to `payment.rs`. Remove the payment methods from `AttestationStore` only after they are fully ported to `payment.rs` and compile.

`mcp/src/payment.rs` — The 8 payment methods (`create_api_key`, `deduct_balance`, `credit_deposit`, `mark_x402_nonce`, `record_attestation_cost`, `get_pnl_stats`, `get_owner_pubkey`, `get_balance`) currently live on the `AttestationStore` struct in `db.rs` and must be moved here. After the split, `payment.rs` needs a DB connection handle — accept `&SqliteStore` (from `mnemonic_core::storage`) as a parameter or wrap it in a local struct. Whatever approach compiles without breaking payment.rs callers is correct. Keep all SQL logic from the original `db.rs` methods intact.

`mcp/src/mcp.rs` — Imports `db::AttestationStore` (direct module path). Update to import `mnemonic_core::storage::AttestationStore` instead. Also check if it references `db::SqliteStore` or the concrete struct — update those to `mnemonic_core::storage::SqliteStore`.

**Dependencies:**

**Storage lock discipline (from patterns.md):**
`rusqlite::Connection` is `!Send`. In async contexts, callers must wrap `SqliteStore` in `std::sync::Mutex` and never hold the lock across an `.await` point. Document this constraint in the `SqliteStore` rustdoc. The trait methods themselves are synchronous — no `async fn` in the traits.

**Edge cases to handle:**
- Concurrent access (two `SqliteStore::open()` on the same file path): enable WAL mode (`PRAGMA journal_mode=WAL`) on connection open, or document that callers must serialize access — write a test that opens two instances and writes from both without panicking
- `find_by_tx` with no matching row: return `Ok(None)`, not an error
- `search` with empty embedding store: return `Ok(vec![])`, not an error
- Duplicate `attestation_id` in `save_attestation`: return a descriptive `Err`, not a panic — rusqlite will return a constraint violation error which should be propagated via `?`

**Implementation hints:**
- Read `mcp/src/db.rs` in full before writing a single line — map every public method to either the core traits or the payment layer
- The cosine similarity scoring loop in `search()` is pure Rust over fetched embeddings — no SQL math
- The `lineage_edges` table schema is created inside `SqliteStore::open` and `SqliteStore::in_memory` as part of the standard schema setup (same `CREATE TABLE IF NOT EXISTS lineage_edges (...)` SQL that `init_lineage_schema` in `lineage.rs` runs today) — there is no `init_lineage_schema` trait method in Task 6
- For test contract: use `SqliteStore::in_memory()` — no temp files needed for unit tests (except the concurrent access test which needs an actual file)

**Lineage types timing (decision — use minimal trait):**
`LineageResult`, `LineageNode`, `LineageEdge`, `ParentRef` are currently in `mcp/src/lineage.rs` and will not move to `core/src/lineage/` until Task 9. Therefore, `LineageStore` in Task 6 is deliberately minimal — it exposes only the three raw storage methods (`save_edge`, `get_edges`, `clear_edges`) that use primitive types (`&str`, `i64`, `Vec<(String, i64)>`). No lineage result types are referenced.

Task 9 will expand `LineageStore` with the full query methods (`get_lineage`, `get_ancestry`, `validate_chain`) once those types are in core. The `// TODO(task-9): add get_lineage, get_ancestry, validate_chain methods after lineage types are in core` comment inside the trait body signals exactly where Task 9 should add methods.

The free functions in `mcp/src/lineage.rs` (`record_parents`, `get_parents`, etc.) continue to operate directly on the SQLite connection through `mcp/src/db.rs` until Task 9 moves them — do not attempt to wire them through `LineageStore` in this task.
